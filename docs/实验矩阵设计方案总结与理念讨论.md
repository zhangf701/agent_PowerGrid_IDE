# 第一部分　现有设计（事实总结）

> 本部分只陈述**已实现 / 已定稿**的事实，不含价值判断。标 ★ 者为**刻意设计决定**（有明确理由，非疏漏）。

## 1.1 它在整体中的位置

| 维度 | 值 |
|---|---|
| 路线 | **P2** · 内核视图 **④**（与 ③ 对话分析并列，均为内核能力） |
| 承载判据 | **#2「能组织研究」· #3「能批量跑」**（方案 §12） |
| 设计依据 | 科研场景 8「批量算例扫描与数据集构建」（🚧 需先构造数据集） |
| 当前状态 | V1 网关 ①a/①b/①c + 前端 ④ 视图已交付；V2 提案/校验/编译/不可变定义/Observation/确定性分析 MVP 已交付；**待人工验收 V2 UI 与真实 Agent 回流** |

## 1.2 数据模型（契约）

```
Experiment(case_ids[], factors[], steps[])
  ├─ Factor(name, values[])            ← 纯标签维度（无语义）
  └─ Step(server, tool, args_template) ← 显式声明的工具调用
        └─ Cell(case_id, bindings, cache_key) ← 网格展开后的一格
```

| 要点 | 说明 |
|---|---|
| 网格 | `case_ids × factors` 的笛卡尔积 |
| ★ 一格 = **一条显式声明的步骤序列** | 不是单步；`steps[]` 有序，**顺序参与身份** |
| ★ 全部步骤须**同一 server** | 跨 server → 400（引擎状态边界） |
| ★ **不保留**旧的单值 `step` 形式 | ①a 时期的旧记录会列出但不可执行（`/run` → 409） |
| 参数渲染 | 静态模板替换：`{case_path}` / `{case_id}` / `{因子名}`；**无表达式、无条件、无自适应** |
| ★ 整串占位符**保类型** | `"{lv}"` → `1.1`（float），不是 `"1.1"` |
| ★ 未知占位符**必须报错** | 否则留下 `{xxx}` 当字面量发出去 → "跑成功但没生效" |

## 1.3 端点

| 端点 | 作用 |
|---|---|
| `POST /experiments` | 登记定义（新定义 201 / 重复 200） |
| `GET /experiments` · `GET /experiments/{eid}` | 列表 / 详情（格子**现算**）+ `by_status` |
| `POST /experiments/{eid}/run` | **串行执行**全部格子 |
| `GET /experiments/{eid}/results` | **格级对比表** |
| `GET /experiments/{eid}/export?format=csv\|md` | 导出（PDF 不在网关做） |
| `DELETE /experiments/{eid}` | 删除定义 + 结果目录（不删算例源文件） |

错误映射：400 定义非法 · 404 未知 id · **409 状态不允许**（算例不可读 / 空步骤 / 正在执行）· 500 索引损坏 · 503 配置失败。

## 1.4 执行模型

| 规则 | 不这么做会怎样 |
|---|---|
| **串行**执行（方案 §4.4 裁决：先串行跑通，再评估并发） | — |
| **一格一个会话** | 跨格复用 → 某格 `load_network` 失败后，下一格跑在**上一格残留的网络**上（结果张冠李戴） |
| **失败即停本格后续步骤**（但继续跑其他格） | 后续步骤只会产出无意义结果，并把"没加载网络"伪装成业务失败 |
| **`remounted=True` 判该格失败** | 重连意味着进程死过、会话状态已丢 → 会让"可能是空网络跑出来的结果"冒充成功 |
| **多步实验无会话池 → 503** | 静默降级成"每步各起一个进程" → 产出"跑成功但没加载网络"的假结果 |
| **空 `steps` → 409** | 步骤循环不跑会让格子得到"成功且 0 步"= **「跑了 0 步却说成功」的假绿灯** |
| 同一实验不并发（`_RUNNING` → 409） | — |

★ **执行时无 LLM 参与**：`execute_cells` 逐格调 `run_step(sid, server, tool, args)`，纯机械。

## 1.5 可复现性

```
cache_key = H(算例当前 sha256 + steps 规范化序列 + core_version)
```

| 要点 | 说明 |
|---|---|
| ★ **不含引擎版本 / IR 版本** | 网关无可靠来源 → **不假装有**（缺的量写在响应 `notes` 里） |
| ★ 结果按 `cache_key` 落盘 | `~/.powermcp_gateway/experiments/<eid>/results.json`，**不是**格子序号 |
| 算例/模板一改 | 该格算出新 key → 显示 `never_run`；旧记录进 `orphaned`（**不冒充当前条件，也不丢弃**） |
| ★ 格子现算、**不存快照** | 每次 `GET` 按当前算例哈希与模板重算 |
| ★ 未引用因子 → **告警** | 模板里没写 `{因子}` ⇒ 各格 `cache_key` 相同（重复格）却看着正常 |

## 1.6 结果表与导出

| 要点 | 说明 |
|---|---|
| `/results` 是**格级对比表** | 不是越限明细表 |
| 指标提取**通用** | 从引擎返回 JSON walk 出标量与**列表长度**；键统一 `metric.` 前缀 |
| ★ **不发明派生量** | 如「最大负载率」是模块语义，内核不替它猜（与"不做语义因子"同口径） |
| 列由**各格指标并集**决定 | 不预设任何领域列 |
| ⚠️ **越限明细级 `result_tables` 透视**（模块列定义 / G-2 pivot） | **属 P3，未实现** |
| 导出 | Markdown + CSV（PDF 走 HTML+Chrome headless，**禁用 pandoc**） |

## 1.7 前端视图

`views/ExperimentsView.tsx` + `components/ExperimentGrid.tsx`；导航「实验矩阵」；深链 `#experiments/<eid>`（**只在全新加载生效**）。

UI 规范 §4.7.5 三条约束已逐条落地：
1. **失败逐格可见**（行内给失败步骤 + 引擎错误原文 + `remounted` 解释；总计数只是补充）
2. **结果绑 `cache_key`**（`never_run` / `orphaned` 显式标注）
3. **串行优先**（无并发控件，写明「一格一个会话」）

## 1.8 三条刻意设计决定（可复核）

1. **一格 = 一次显式声明的工具调用；因子只是标签维度**
   ★ 刻意**不做**「负荷水平」这类语义因子 —— 那等于**替引擎声称一个未核实的能力**。
2. **`cache_key` 只含可确证的量**（不含引擎 / IR 版本）
   ★ 宁可让 key 保守失效，也不让它冒充可复现性。
3. **格子现算、不存快照**
   ★ 副作用正是要的效果：算例一改 → 新 key → 旧结果即陈旧。

## 1.9 诚实边界

- 执行是**串行**的（§11.2 并发隔离已补齐网关侧，但**并发开关未打开**）。
- 越限明细 `result_tables` 透视属 **P3**，未做。
- 租约是**进程内**的，跨机文件租约未做。

# 第二部分　设计理念讨论（2026-09-28）

## 2.1 事实前提：两条路径，谁在环内

| | **Agent 路径（③ 对话）** | **实验矩阵路径（④）** |
|---|---|---|
| 谁决定跑什么 | **LLM 自主**（`run_turn`：多轮、动态选工具与参数） | **预定义的 JSON**（`steps[]` 写死 server/tool/args_template） |
| 执行时 LLM 在环吗 | **在** | **不在**（纯机械） |
| 参数能否自适应 | 能（看中间结果改下一步） | **不能**（只有静态模板替换） |
| 可复现性 | 低（每次可能不同） | **高**（`cache_key` 内容寻址） |
| 一次处理几个 | 一个（一次对话） | **多个**（网格） |

★ **两条路径零衔接** —— 这是核实所得的事实，不是推测。

## 2.2 质疑一：静态 JSON 定义，是否丧失了 agent 的实验设计优势？

**成立，而且比"丧失优势"更严重 —— 是"没有衔接"。**

- 实验矩阵**完全不调用 agent**。它假设"实验方案已经想好了"，只负责机械跑。
- 从 agent 探索到实验矩阵，中间**必须人工把流程手抄成 JSON** —— 这一步**确实**丢掉了 agent 的优势。
- 若期望是"让 agent 自主设计并迭代实验"，当前设计**不提供**。

**但静态不是疏忽，是有代价换来的**：`cache_key` 要成立，实验定义就必须**确定**；若实验由 agent 每次动态决定，"同一个实验"就无法复现，可复现性基础设施（§11.6）就塌了。

⇒ 真正的问题不是"静态错了"，而是：**探索（动态）与确认（静态）本该分工，当前只有静态这一半，且不接两头。**

## 2.3 质疑二：只有几个 metrics，对研究助力多大？

要分两种情况：

**（a）作为"数据集构建器" —— 够用，且自洽。**
场景 8 的**原始目标**就是「构建可用于机器学习（N-1 快速筛选代理模型）的**标注数据集**」。产出 metrics 表格，对"造数据集"是**对得上**的。

**（b）作为"研究洞察工具" —— 不够。**
- 研究者要的是**解释**（为什么这格越限？哪条支路？）、**对比**（跨格差异的成因）、**迭代**（下一步试什么）。
- 当前 `/results` 只有扁平标量 + 导出；**越限明细 `result_tables` 属 P3 未做**。
- 更要紧：**批量结果没有回到对话**。单次对话里 agent 能解释一个结果；但跑完 46 格之后，**没有任何机制**把这批结果交给 agent 解释。

## 2.4 结构性诊断：研究闭环的两个断点（已补第一段）

一个完整的研究闭环应当是：**探索 → 提案 → 校验/预览 → 固化 → 批量执行 → Observation/分析 → Agent 解释**（并回到探索迭代）。

```text
① 探索       ② 提案/固化                 ③ 批量执行              ④ 观察/解释
agent 自主 ─▶ ExperimentProposal ─────▶ immutable Experiment ─▶ Observation ─▶ Agent
                  ✅ V2 MVP                  ✅ V2 MVP             ✅ V2 MVP       ⏳
                  validate/preview           serial executor       deterministic   未接回 Agent
```

| 环节 | 状态 | 缺口 |
|---|---|---|
| ① 探索 | ✅ 已实现（③ 对话） | session trace 尚不能自动生成提案 |
| ② 提案/固化 | ✅ V2 MVP 已实现 | 当前由 API/UI 创建提案，尚未接 `propose_experiment_from_session` |
| ③ 批量执行 | ✅ 已实现 | 仍串行；并发开关未打开 |
| ④ Observation/确定性分析 | ✅ V2 MVP 已实现 | artifact 与更丰富的 result_tables 仍未做 |
| ⑤ Agent 解释/下一提案 | ⏳ 未接线 | 缺 summary/analysis 上下文注入 Agent 与 follow-up proposal |

⇒ **当前已从原来的中间一段扩展为可提交、可冻结、可观察、可分析的 V2 MVP；真正的 Agent 研究闭环仍缺最后的结果回流。**

## 2.5 一个被文档掩盖的张力：语义因子被砍 vs 场景 8 原设计

- 场景 8 原文写的是「39/118/300 节点 × **负荷水平** × **故障集**」—— 它**预设了"负荷水平"这类语义维度**。
- 而实现为了"不替引擎声称未核实的能力"，**刻意砍掉了语义因子**，只留"显式工具调用枚举"。
- ⇒ 结果是：实验矩阵**只能表达"把值一个个写死"的扫描**，**不能表达"按负荷水平缩放"这类语义化实验设计**。表达力被压到了最保守的形式。

这是"诚实"换来的**表达力代价**，而现有文档里**没有写明这一条**。

# 第三部分　判断与待裁决

## 3.1 我的判断

当前实验矩阵的定位是「**可复现的批量执行器 + 数据集构建器**」，这个定位**本身自洽**。但它与项目 2026-09-25 定下的「**通用研究工作台**」之间存在张力：

> 如果工作台的核心价值是"**用 agent 做研究**"，那实验矩阵（静态批处理、无 agent、只出 metrics）**偏离了主轴** ——
> 它是研究流水线里的一个**配角**，却被放在 P2 当作核心交付。

它**不是错的**，但**不足以承载 agent 的优势**。缺的正是 §2.4 里那两条虚线。

## 3.2 三条候选路线与当前实现选择

| 路线 | 含义 | 当前结论 |
|---|---|---|
| **A · agent 主导** | agent 设计实验、执行、解释；矩阵退为"落盘格式" | 未采用：会削弱确定性与可复现性 |
| **B · 矩阵主导** | 人设计好、批量跑；agent 只做单点辅助 | 作为 V1 兼容路径保留 |
| **C · 分工** | agent 探索 → **提案/一键固化** → 批量 → **结果回流给 agent 解释** | **采用；2026-09-28 已实现提案/固化、批量、Observation/分析，结果回流待后续** |

## 3.3 当前待办（替代原待裁决问题）

1. 实现 `propose_experiment_from_session`：从 session trace 生成 Proposal，但不自动 commit；
2. 增加 Agent 查询工具：summary / design / observations / cell / analysis；
3. 将确定性分析上下文注入 Agent，支持 follow-up proposal；
4. 完成真实 artifact manifest、hash 和 artifact 查询；
5. 评估 `result_tables` 模块透视；
6. 保持实验定义静态、commit 后不可变；不因接入 Agent 而把 LLM 放进执行循环。
