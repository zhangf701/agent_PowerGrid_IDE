## 1. 选题的约束条件：这个项目能给什么、不能给什么

选题不是自由的 —— 它被已实测的能力边界框住。先明确边界，后面的候选筛选才有意义。

### 1.1 已具备的能力（可作为选题的「实验平台」）

| 能力 | 实测状态 | 来源 |
|---|---|---|
| PowerMCP 运行时 | ✅ 16 server / 约 250 工具，`list_tools` 运行时核验 5 server 全部 MATCH | 仓库扫描 + 环境搭建 |
| 隔离环境 | ✅ `PowerMCP/.venv`（Python 3.12.6，核心 + `[hope,surge]`） | 环境搭建 |
| 跨引擎数据契约 | ✅ **PowerIO IR gen 2** 往返保真 —— pandapower ↔ PyPSA 母线电压 **Δ = 6.98e-11 pu** | 示例验证 |
| 全流程算例 | ✅ case30 走通：IR 解析 → 潮流 → PTDF/LODF → N-1（41 场景/32 越限） | case30 验证 |
| 中文标准算例 | ⚠️ 5 套 CSEE 算例已获取，但 **CSEE-FS 解析失败** | case30 验证 §二 |

### 1.2 已实测的能力边界（会直接排除某些选题）

这些是**实测缺陷**，不是猜测 —— 它们既是选题的障碍，也是选题的素材（见 §5.2）：

| 缺陷 | 实测证据 |
|---|---|
| **API 漂移** | `panda_mcp.py:180,191` 的 `net.deepcopy()` 在 pandapower 3.x 已移除 → N-1 工具必然失败 |
| **文档/实现不符** | `opendss/SKILL.md` + README 引用的 **6 个工具名全部不存在** |
| **静默参数忽略** | PyPSA 的 `linearized` 参数**不存在但被静默忽略** → 曾导致「DC OPF infeasible」的错误结论被写进指南（后已作废） |
| **求解成功却误报失败** | `Network.status` 已移除 → pypsa 的 N-1 脚本**求解成功却报「未收敛」** |
| **工具名跨 server 冲突** | `load_network` / `add_bus` / `run_contingency_analysis` 等重名，**语义可能不同** |
| **编号约定不统一** | pandapower 0-based vs PyPSA 1-based → 字面比对把偏差**放大 3.1 亿倍** |
| **无 CI 且无版本上界** | PowerSkills 仓库无 CI，依赖不钉版本 → 上述缺陷长期存活 |
| **商业/许可阻塞** | Gurobi 许可过期（2026-03-31）；Ipopt 不可用；PowerWorld 仅 Education 版无 SimAuto |

> 这个观察是后续候选收敛到 MCP 接口方向的**经验基础**（见 §4）。

## 2. 调研方法的三轮演进（方法论结论）

这是本次调研**最可复用的产出** —— 它解释了为什么前期的判断会错。

| 轮次 | 方法 | 结果 | 教训 |
|---|---|---|---|
| 1 | 关键词检索 | ❌ **七轮错六轮** | 单轮关键词检索 **≠ 新颖性证明**（前作用不同措辞，如说 `energy sector` 而非 `power system`） |
| 2 | 论文引文链出发 + future work 系统提取 | ⚠️ 找到议程，但**高频 ≠ 空白** | 高频议题是**「热门延伸」**而非缺口；权威工具给的**否定性证据也可能错**（曾据 "no source focuses on…" 误判人机协同仍开放） |
| 3 | + OpenAlex **引用图遍历**（锚点*说的* vs 引用者*做的* 差集） | ✅ **差异化最大** | 「自己社区已占」= **自证新颖性风险**（Power-Agent 生态的候选可能已被本社区占据） |

**方法结论**：最终采用的是 **第 3 轮方法** —— 不看论文「说要做什么」，而看**谁真的接着做了**，取差集。

**方法级的三条红线**（已写入交付技能 `finding-research-gaps`）：

1. 不采信单轮关键词检索的"空白"结论；
2. 不采信权威综述的否定性断言（需引用图交叉验证）；
3. **引用图返回「命中 0」时必须先排除限流** —— OpenAlex 匿名限流会返回"命中 0"，**看起来像空白实则不是**（该失败模式由 GREEN 阶段 agent 发现，实测确认后已做两层修复）。

## 4. 存活候选：MCP 接口标准化

### 4.1 权威依据

来源：`2511.14478`（Frontiers in AI, 2026 综述），原文：

> *"…the **lack of official standardized Model Context Protocols (MCPs) from engineering software vendors such as PSS®E, PowerWorld, CDEGS is a major barrier for standardized deployment**. Future research must focus on developing open, stable, and secure standards for agent-tool interaction…"*

**这句话与本项目实测高度吻合**：本项目遇到的 `PowerWorld 仅 Education 版无 SimAuto`、`HOPE/GenX 缺 Julia`、`Gurobi 许可过期` —— 全部是**厂商侧接口不可用**造成的，而非算法问题。

### 4.2 引用图验证

**种子锚点（5 篇）→ 144 篇唯一引用者**：

| 锚点 | 被引 |
|---|---:|
| PowerAgent 路线图（IEEE P&E Magazine, 2025） | 11 |
| LLM 应用于电力的安全威胁（IEEE TSG, 2024） | 79 |
| 变压器与 LLM 能源领域系统综述（Applied Energy, 2025） | 58 |
| 电力网基础模型（Joule, 2024） | 40 |
| LLM 电力调度智能体（IJEPES, 2026） | 5 |

**144 篇引用者的主题分布**（记录值）：

| 主题 | 篇数 | | 主题 | 篇数 |
|---|---:|---|---|---:|
| 基础模型 / 微调 | **50** | | **技能 / 工具 / 编排** | **14** |
| 调度 / 运行 | 25 | | **可解释 / 审计** | **3** |
| 规划 / 优化 | 22 | | **人机协同** | **2** |
| RAG / 检索 | 21 | | | |

**摘要级复核**：母论文引用的 11 篇中，摘要提及 **MCP 的仅 1 篇**（Grid-Orch），提及 **skill 的仅 1 篇**。

> **读法**：矩阵类/调度类方向**已高度拥挤**（50 + 25 + 22 + 21 = 118/144）；
> 而「**技能/工具/编排**」（14）与「**可解释/审计**」（3）、「**人机协同**」（2）合计仅 19/144，且后两者近乎空白。

**锚点检索记录**：`work/cite/anchors.json` 共 **254 个锚点**，其中以 `Model Context Protocol` 为检索词的锚点仅 **12 个**（`power system`×9 / `power grid`×2 / `energy system`×1）——
即 **MCP × 电力方向本身是一个小空间**（记录值：约 10–12 个去重工作，全部为 2026 年）。

### 4.3 ⚠️ 两个必须原样保留的局限

调研记录中明确写出的三条，**不得淡化**：

1. **「0 引用」部分源于时间偏差** —— 该空间绝大多数是 2026 年论文，被引 0 属**正常滞后**，**不能**当作"无人问津"的证据。
2. **空间极小** —— MCP × 电力全空间仅约 **10–12 个去重工作**，全部 2026 年。**小 = 机会，也 = 被并行工作抢先的风险**。
3. **邻近领域更成熟** —— **建筑能源领域的 MCP 更成熟**：`EnergyPlus-MCP` 被引 **24**，高于电力最高值（11）。**这意味着"电力是该技术最前沿"的判断不成立。**

> ⚠️ **第 3 条尤其重要**：它意味着若把选题表述为「电力领域的 MCP 标准化」，需要正面回答
> **「为什么建筑能源已经做得更好，而电力还值得单独做一轮」**。

## 5. 结论与建议

### 5.1 建议的选题表述（三个递进层次）

调研记录中给出的方向是：把问题从「找空白」升级为「定义可形式化验证的性质」。三个层次：

| 层次 | 表述 | 风险 |
|---|---|---|
| **L1（最保守）** | 「电力工程软件 MCP 接口的现状测绘与缺陷分类」 | 偏 survey，**创新性弱** |
| **L2（推荐）** | 「**面向工程软件的 agent-tool 接口标准应满足哪些可形式化验证的性质**」 | 需先做新颖性专查（见 §6） |
| **L3（最大胆）** | L2 + 提出一套**可执行的接口一致性校验套件**（用本项目实测缺陷做测试用例） | 工作量最大，但**有本项目作为现成实验台** |

> ⚠️ **溯源标记**：**仅 L2 直接来自调研记录**（原话为「可考虑把问题表述为…」）。
> **L1 与 L3 是本报告的综合推断**，未经调研验证 —— 使用前需自行判断。

> *（推断）* **L2 与 L3 的结合是本项目最自然的位置** —— 理由：本项目已经积累了一套**真实、可复现、带根因的接口失效案例**（§1.2 表中 8 项），
> 这些不是虚构的测试用例，而是从 4 个真实仓库的实测中挖出来的。这是纯理论组**不具备**的素材优势。

### 5.2 本项目已实测的「接口失效模式」—— 可作为研究素材

以下**「失效模式」与「实测证据」两列全部来自本项目实测**（来源见 §1.2 表），
**「是否可形式化描述」一列是本报告的*推断***（未经形式化验证，需在 L3 落地时逐条确认）。
它们可作为 L3 中校验套件的测试用例来源：

| 失效模式 | 是否可形式化描述 | 本项目实测证据 |
|---|---|---|
| 已移除 API 仍被调用 | ✅ 可（API 版本契约） | `net.deepcopy()` / `Network.status` / `mremove()` 三处 |
| 文档声明的工具不存在 | ✅ 可（文档-实现一致性） | opendss 6 个工具名全部不存在 |
| 参数不存在但被静默忽略 | ✅ 可（参数契约） | PyPSA `linearized` |
| 求解成功却报失败 | ✅ 可（状态映射契约） | pypsa N-1 脚本误报「未收敛」 |
| 跨 server 工具名冲突、语义不同 | ✅ 可（命名空间契约） | `load_network` / `add_bus` / `run_contingency_analysis` |
| 跨引擎编号约定不一致 | ✅ 可（标识符契约） | 0-based vs 1-based，放大偏差 3.1 亿倍 |
| 过载判据单位不一致（MVA/MW） | ✅ 可（量纲契约） | 142% 会误判为 98% |
| 厂商接口不可用（许可/版本） | ⚠️ 部分可（能力声明契约） | Gurobi 过期 / PowerWorld 无 SimAuto / HOPE 缺 Julia |

**这张表是本报告最可操作的产出** —— 它把「MCP 接口标准化」从一句综述里的口号，
变成了 **8 条有实测支撑、可逐条形式化的契约类型**。

### 5.3 建议的下一步（按优先级）

1. **【必须先做】** 用 `finding-research-gaps` 技能对 §5.1 的 L2 表述做**新颖性专查** ——
   **不得跳过**。理由：本次调研的错误率是 *七轮错六轮*，任何未经专查的"空白判断"都不可信。
   专查时特别注意：检索词**不要**含 `power system`（避免只召回本社区工作），要覆盖 `engineering software` / `simulation tooling` / `scientific computing` 等措辞。
2. 若专查通过 → 以 §5.2 的表为骨架，起草研究问题定义（**下一个任务，颗粒度：单文档**）。
3. 若专查不通过 → 回到 §3 的候选池重新筛选（候选池已归档，见附录 A）。
