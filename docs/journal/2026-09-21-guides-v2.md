## 四、技术要点

### 🚫 PDF 生成：pandoc 已被禁（2026-09-21 用户指令）

本轮的 PDF 是用 **pandoc + MiKTeX xelatex** 生成的，**此后禁止再用 pandoc 生成 PDF**。
相关命令与 `docs/pandoc-header.tex` 均作废，仅作历史记录。**今后需要 PDF 时先向用户确认生成方式**，不要自行选引擎。

仍然有效、与引擎无关的经验（供将来任何方案参考）：

- 字体必须**同时覆盖拉丁与 CJK**。Microsoft YaHei 缺 ⚠(U+26A0) ✅(U+2705) ❌(U+274C) 🔴🟠 ⌈⌉(U+2308/2309) 及全部 emoji；**安全符号集**：★ → ← ↓ ①-⑩ ℃ ° ± ≈ Δ ≤ ≥ · × ÷ √ ∞ Ω μ σ 「」《》。若拉丁部分退回不含符号的默认字体（如 lmroman10），→ ≤ ≥ ≈ Δ μ Ω 会整体缺失。
- 代码块/等宽字体若无 CJK 字形，块内中文会变豆腐块，须单独指定 CJK 等宽字体。
- 表格：CJK **显示宽 ≠ 字节宽**，靠字符数对齐的表格易破坏边框；稳妥做法是**列数压到 4~5 列以内**，长标识符不要塞进窄列。

### 只读校验链路（不受禁令约束）

对**已有** PDF 做抽取 / 页数核对 / 转图目视，用 MiKTeX 自带的 `pdftotext` / `pdfinfo` / `pdftoppm`：

`pdfinfo` 看页数与纸张 → `pdftotext -enc UTF-8` 回读确认 U+FFFD 为 0 且地标字符串命中 → `pdffonts` 查异常字体 → `pdftoppm` 出图目视（低分辨率下等宽字体可能看着像斜体，**需 300 dpi 裁剪复核才能定论**）。

**路径陷阱**：pandoc / pdftotext / pdftoppm 等原生 Windows 工具**不认 Git Bash 的 `/d/...` 虚拟路径**（报 `withBinaryFile: does not exist`），必须传 `D:/...`；中文输出路径对 pdftotext 会报 I/O Error，中间产物用 ASCII 名。
