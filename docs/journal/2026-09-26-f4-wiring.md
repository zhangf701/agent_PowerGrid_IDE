## 背景与诊断回顾

判据 #1 验收时实测：模型报「最低电压 0.943 pu @ **母线 78**」，直接读 surge
结果数组却是 `bus_numbers[75] = 76`。错因是模型拿**数组位置**当**母线编号**，
且语气确定、只在被提示"注意编号约定"时才做对 ⇒ 提示词治不了，
**结果呈现必须走结构化通道**（§4.3 的 `Quantity`/`Identifier` 接线）。

## 交付内容（两个半边）

### 网关半边（`f7f3ced`，proxy.py + test_proxy.py）

`tool_call` 事件新增 `result_excerpt` 字段（前端要原始结果才能结构化呈现）：

- **`_json_safe`**：NaN/Infinity → null。★ Python `json.dumps` 默认放行
  `NaN` 字面量，**JS 的 `JSON.parse` 会直接抛错** —— surge 的 N-1 结果
  实测含 `min_vm_pu: NaN`，不消毒则前端整条 SSE 解析失败。
- **`_result_excerpt`**：有界摘要，32 KB 上限；超限只给形状
  （`__truncated__` + bytes + keys），**不给半截数组**（半截比没有更危险）。
- ★ **MCP 包装在网关侧拆包解析内层 JSON** —— `content[0].text` 是 JSON
  字符串，若原样放进去会**二次转义**，实测 23 KB 膨胀到 36.5 KB 顶破上限。
  解析为 `{is_error, inner}`（内层 JSON）/ `{is_error, text}`（纯文本）/
  `{raw}`（非 MCP）。
- ★ **解析后必须二次消毒**：首轮消毒只做在包装层，内层解析后 NaN 重新
  出现 —— **被测试抓出**（`test_result_excerpt_parses_mcp_inner_json`
  断言内层 vm 的 NaN 也是 null）。
- 网关全量 **523 passed**（516 → +7）。

## 端到端验证（决定性）

同一轮对话（case118 基态潮流）：

| 通道 | 结果 |
|---|---|
| **结构化通道**（事件 `result_excerpt` → 适配层） | `0.943000 pu @ bus 76`（1-based）✅ |

⇒ F-4 诊断**再次坐实**，且结构化通道**不依赖模型自述**地给出了正确值。

## 测试迭代中抓出的问题（都当场修了）

1. 夹具含字面 `NaN`（Python 生成）→ JS 解析失败 → 改从**已消毒的网关**重抓
2. N-1 摘要 36.5 KB 超限 → 根因是二次转义 → 网关侧解析内层
3. 内层解析后 NaN 复活 → 二次消毒
4. 前端测试输入用旧 MCP 形状 → 更新为新契约（`{is_error, inner}`），
   并让"长度不一致"用例真正测到长度检查（原来靠 null→[] 侥幸通过）
