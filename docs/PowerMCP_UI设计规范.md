# 一、总则与适用范围

## 1.1 本规范解决什么问题

《前端设计方案》§七 的「视觉规范」是**提案级**的：它给出了语义色的四态、排版的两条规则、和三条硬规则，但**没有给出任何可直接写进代码的数值**，也没有定义组件。

其后果是：三个不同的开发者会实现出三套不同的「状态徽章」，而状态恰恰是**需要跨视图保持一致**的东西（方案 v4 §三：五个视图 + 校验层共享同一组件库）。本规范的作用就是把「视觉规范」这一段**补完到可开发**。

> **v2 修订**：v1.x 的落点写的是「契约状态」需要跨视图一致。v4 之后**跨视图一致的是「状态签名」本身**
> （§3.8）—— 契约状态只是它的**一种用法**，与「引擎可用性」「算例可用性」「模块装配状态」并列。

## 1.2 与方案的关系

本规范是方案的**下游**，不是替代。两条约束：

- **尽力不引入方案没有的概念**。方案已有的内容都追溯到具体章节（[附录 B](附录-b与前端设计方案的追溯表)）；**本规范新增的部分集中登记在 [附录 B.4](附录-b与前端设计方案的追溯表)**，与"方案要求"明确区分。

> ⚠️ 首版此处写的是「**每个**组件、**每条**规则都能追溯到方案的某一节」并配以"无依据者不予收录"——
> **与事实不符**：令牌体系、布局尺寸、断点、基础件规格、图型选择判据等均为本规范新增，方案中并无对应物。
> 独立审查指出这一点后，已收窄措辞并补建 B.4 登记表。
- **不与方案冲突**。发现方案内部不一致时，在本规范中**显式标出并说明取舍**，不回改方案。目前已发现并处理 **一处冲突**（§3.8.3）与 **一处补完**（附录 B.3）。

> **v2 修订**：上游已由方案 v3 换为 **v4**。v4 与 v3 的差异属**定位级**
> （第一公民、契约层级、模块化），逐条对照见 [重定位提案 §五](PowerMCP_前端方案重定位提案.md)。
> 本规范对 v4 的追溯见 [附录 B](附录-b与前端设计方案的追溯表)（已按 v4 章节号重排）。

## 1.3 技术栈与版本锁定

| 层 | 选型 | 说明 |
|---|---|---|
| 应用框架 | **Vite + React + TypeScript** | 方案 §七 原选。构建产物为静态文件，由 FastAPI 单进程 serve |
| 组件栈 | **shadcn/ui + Radix UI** | 组件源码进仓库，可改；Radix 提供行为原语 |
| 样式 | **Tailwind CSS** | token 以 CSS 变量注入，见 §8.1 |
| 图表 | **ECharts** | 方案 §七 原选 |

> **为什么不是 Next.js**：方案 §六 形态 A 是 `powermcp ui` 仅绑 `127.0.0.1` 的本地单机工具，
> 用户 `pip install` 后不应再维护一个 Node 服务。SSR/RSC 解决的「公网、多用户、远端数据源」问题在本场景收益为零。

## 1.4 范围排除（明确写出，避免预期错位）

以下内容**本版不做**，不是遗漏：

| 排除项 | 理由 |
|---|---|
| **无障碍规范（WCAG）** | 本版范围外。**但方案 v4 §七.1 的「颜色不得单独承载信息」保留**，因为它是方案明文约束，且是状态签名机制（§3.8）的载体 —— 删了它，四态徽章就只剩颜色 |
| 对比度比值验算 / 键盘导航 / 屏幕阅读器 / `prefers-reduced-motion` | 随 WCAG 一并排除 |
| **v4 P2 的组件**（实验矩阵格、并发进度） | 方案 v4 §十：P2 才交付 |
| **v4 P3 的组件**（导出报告预览、可复现记录） | 方案 v4 §十：P3 才交付 |
| **模块注入的 L2 组件**（槽位内容由模块自带） | 本规范只固定**槽位契约**（§4.7.6），不规定模块自己写什么组件 —— 那是模块作者的自由，也是「内核不含领域知识」的延伸 |
| 视觉稿 / 高保真设计图 | 本规范给的是**规格**（数值 + 行为 + 属性），不是效果图 |

## 1.5 术语表

| 术语 | 含义 |
|---|---|
| **契约** | 方案 §2.2 的 8 类接口契约（API 版本 / 文档-实现 / 参数 / 状态映射 / 命名空间 / 标识符 / 量纲 / 运行时依赖） |
| **状态签名** | 「色 + 图标 + 标签」的三元绑定。契约状态**只能**通过完整签名表达，不提供单独的颜色 |
| **降级** | 契约未满足但**不阻断**调用（如参数被静默忽略） |
| **未知态** | 无法给出判定的状态。**必须可见**，见 P5 |
| **结构性未知**（`structural`） | 未知的一种成因：**引擎能力本身给不出判定**。长期存在、无信息量（如契约 4 无法推断返回码语义）。**不升至主徽章** |
| **事故性未知**（`incident`） | 未知的另一种成因：**本应能判定却拿不到**（契约引擎崩溃、SSE 边界校验失败）。含义是"整体不可信"，**必须升至主徽章** |
| **主徽章 / 次级标记** | 行级汇总的**双轨呈现**：主徽章承载"多严重"，次级标记 `+?N` 承载"多不确定"。见 §4.3 |
| **审计行** | Tool Call 列表中的一行，含工具名、参数、契约状态 |
| **断言值** | 带判据的比值，如负载率 `142.47%`（MVA 判据） |

# 二、设计原则

每条原则都给出**它防的是什么** —— 没有实测依据的原则不写进规范。

## P1 · 研究流程是第一公民

**说明**：方案 v4 §1.4 的核心命题 —— 前端的价值不在「又一个图表工具」，而在**把「研究流程」显式化**：
环境就绪 → 算例组织 → 提问拿结果 → 批量实验 → 用对方法 → 留痕产出（v4 §1.1 的六类活动 A–F）。
**契约状态是其中「结果可不可信」这一环的呈现**，而非全部。

**防的是**：两件事，**方向相反** ——
1. 把前端做成「又一个电力数据的图表工具」，与 Grid-Orch 及通用客户端重复；
2. **把前端做成「一个契约审计器」** —— 那是 v1–v3 的定位（服务论文选题），
   会让「用 PowerMCP + PowerSkills 做**任何**研究」这个目标落空。

**落地**：五个内核视图（环境就绪 / 算例库 / 对话分析 / 实验矩阵 / 技能手册）**必须先于**校验层成立；
契约状态默认**折叠**在可开关的校验层里（§4.7.1），**不阻断**结果呈现。

> ⚠️ **v2 修订（定位级）**：v1.x 此条为「**契约状态是第一公民**」，并明文要求
> 「契约状态**先于**图表渲染」。该落地条款在 v4 §4.3 已**废除** ——
> 它会让每一次结果呈现都先过一次契约，把工作台退化成审计器。
> **能力一个不丢**：契约面板 / 跨引擎一致性 / 能力矩阵 / IR 检查器全部保留，
> 只改变**层级与默认呈现**（见 §4.7.1）。
>
> ⚠️ **但本条的"防"并没有变弱**：契约状态仍是**唯一**能回答「这个结论可不可信」的东西，
> 只是它从"挡在前面"变成"随叫随到"。

## P2 · 颜色不单独承载信息

**说明**：方案 v4 §七.1 的明文约束。每个状态必须同时含**图标 + 文字**。

**防的是**：色觉障碍用户无法区分 ✅/⚠️/❌；以及黑白打印/截图后信息丢失。

**落地**：不以「颜色 token」形式对外提供契约色，只提供**状态签名**（§3.8）。组件层无从只取颜色。

## P3 · 让违规写法在关键调用点上不易顺手写出

> ⚠️ **原则名称**：首版名为「违规写法**不可表达**」。经独立审查（实测编译验证）后改为此名 ——
> 「不可表达」是过度承诺，实际的约束边界比它窄得多。**改名是为了让规范与事实一致。**

**说明**：方案 v4 §七.3 的三条硬规则原本是**文档约定**，靠开发者自觉。本规范把它们中的一部分提升为**类型约束**。

**防的是**：文档约定在人身上必然失效。三条硬规则各自对应一个**本项目实测的真缺陷**（见下表）。

| 硬规则（方案 v4 §七.3） | 实测依据（方案 v4 §1.2 / §七.3 规则 1–2） | 类型/结构约束 | 实际能兑现多少 |
|---|---|---|---|
| 数值必须与单位同时出现 | 过载判据用 MW 会把 **142% 看成 98%** | §4.4 `Quantity`：`of: Measured`，由 `measure()` 唯一构造；`unit` 无默认值 | ⚠️ **约 40%** —— 保证"写了标注"，**不保证标注正确** |
| 标识符必须标注编号约定 | 字面比对把跨引擎偏差**放大 3.1 亿倍** | §4.5 `Identifier`：`engine` 为字面量联合（编译期挡大小写）；查表未命中 → `unknown`（**不猜**） | ✅ **约 60%** —— 见 §4.5「三重防护」 |
| 颜色不单独承载信息 | — | §3.8 状态签名：不提供单独取色 API | ⚠️ **约 50%** —— CSS 变量仍可按名取色（见下） |

### ⚠️ 本原则的边界（必须与事实一致）

类型约束**只作用于「属性清单的完整性」，不作用于「属性值的正确性」**。已知逃逸路径：

| 逃逸路径 | 说明 | 状态 |
|---|---|---|
| `JSON.parse` 的 `any` | **SSE 是项目唯一真实数据入口**，边界处的类型检查全部失效 | ✅ **已闭合** —— §8.4 强制 Zod 运行时校验，失败降级为 `incident` |
| 非 JSX 渲染 | `<span>` 字面量、ECharts 轴名、SVG、**LLM 流式 Markdown 正文** —— 逐一不受约束 |
| CSS 变量 | §8.1 生成全局 `--c-contract-*`，Tailwind 暴露为工具类 → 两行 JSX 即可只用颜色 |
| 组件可选 | 契约约束只在**使用组件时**成立，而组件本身可选 |

> **结论**：本规范把三条规则收窄成了「三个组件调用点上的属性清单完整性」。
> 这比纯文档约定**确实更强**（实测 13 类写法编译报错），但**不是"不可表达"**。已在 §二 各条中逐项标注兑现程度。

## P4 · 证据可下钻

**说明**：任何契约判定、任何数值，都必须能回到**产生它的那次工具调用**。方案 §4.2「查看实测记录」、§4.3「每行可下钻到原始工具调用」都出自这一条。

**防的是**：审计工具给出结论却无法验证，退化为「另一个会撒谎的面板」。

**落地**：契约卡片的 `evidenceRef`、审计行的 `callId`、数值的 `Measured.source`（§4.4）均为**必填**属性（§4.2 / §4.3 / §4.4）。

> ⚠️ **首版此处有缺陷**：曾写作「数值的 `source`」，但 §4.4 的属性表里**根本没有这个属性** —— 声称的防护在组件层并不存在，且交叉引用漏了 §4.4。已随 §4.4 重写修正（`source` 现为 `Measured` 必填字段）。

## P5 · 未知态必须可见

**说明**：方案 §11.3 规定契约引擎崩溃时 **fail-loud but non-blocking** —— 不阻塞调用，但界面明确标注「契约状态未知」，且未知态入审计。

**防的是**：契约引擎**静默 fail-open**。方案原文：*「那会退化成『没有契约引擎』，用户以为有保护实际没有，比明确的故障更危险」*。

**落地**：`unknown` 是**与三态并列的第四态**，有独立的签名与视觉（§3.8.3）。组件接收的状态类型是四值判别联合，**不允许**用 `null` / `undefined` 表示未知。

**v1.2 补充**：未知态按成因分 `structural` / `incident` 两类（§3.8.2）。**事故性未知（`incident`）必须升至主徽章** ——
契约引擎崩溃、SSE 边界校验失败都属于这一类。若把它降级为次级标记，即构成本原则禁止的静默 fail-open 的另一种形式。

## P6 · 单一真源

**说明**：所有数值型 token 只在 `design/tokens.json` 定义一处；本文档的 token 表由该文件抄录，并由脚本校验一致。

**防的是**：文档与代码两处手抄同一份色值而漂移。**本项目根目录非 git 仓库**（2026-09-24 已发生过一次交付物被覆盖且无法恢复的事故），漂移没有任何版本控制兜底。

# 三、设计令牌

## 3.1 三层架构

```
primitive（原始层）  →  semantic（语义层）  →  component（组件层）
--p-neutral-200          --c-border-subtle        （按需，本版未启用）
```

| 层 | 命名 | 规则 | 组件可否直接引用 |
|---|---|---|---|
| **primitive** | `--p-{组}-{名}` | 与主题**无关**的原始值 | **颜色**：❌ 不得<br>**尺寸 / 字体 / 动效 / 层级**：✅ **可以** |
| **semantic** | `--c-{路径}` | 承载语义的角色 | ✅ 只允许引用这一层（**颜色**） |
| **component** | `--{组件}-{属性}` | 仅当某组件需要偏离语义层时启用 | 本版未启用任何组件级 token |

> ⚠️ **这条规则只对颜色成立，首版写成了通用语，是错误的。**
>
> **为什么颜色必须走语义层**：颜色是**被主题化的** —— 一旦组件写死 `--p-green-50`，深色主题就失效，
> 换主题要改组件代码而非换变量值。强制颜色只引用语义层，是「深色可加、组件零改动」的实现前提。
>
> **为什么尺寸类不必走语义层**：间距 `--p-space-4`、圆角 `--p-radius-md`、字号、动效时长、z-index
> **在两个主题下取值完全相同**，不存在需要重新解析的角色。给它们再套一层 `--c-space-4` 是纯增熵。
> 这也是为什么本规范的令牌命名里，尺寸类全部是 `--p-*` 且明文规定组件使用（§3.4–§3.7、§4.6.1、§8.1）。

## 3.8 状态签名

### 3.8.1 定义

**状态签名 = 颜色三元组 + 图标 + 标签**，三者**作为一个整体**提供，不拆分。

| 签名 | 图标 | 标签 | 颜色三元组 | 含义 |
|---|---|---|---|---|
| `satisfied` | `✔` | 满足 | `--c-contract-satisfied-{bg,border,fg}` | 契约已满足 |
| `degraded` | `▲` | 降级 | `--c-contract-degraded-{bg,border,fg}` | 未满足但不阻断 |
| `violated` | `✖` | 违反 | `--c-contract-violated-{bg,border,fg}` | 明确违反 |
| `unknown` | `?` | 未知 | `--c-contract-unknown-{bg,border,fg}` | **结构性未知**（引擎级无法判定） |
| `incident` | `!` | 事故 | `--c-contract-incident-{bg,border,fg}` | **事故性未知**（本可判定却拿不到） |

**图标字符的选择理由**（非任意）：`✔` / `▲` / `✖` / `?` / `!` 五者在**形状**上互不相似 —— 即使去掉颜色、缩到 12px，仍可区分。
若选用 `✔ / ⚠ / ✖` 这类同族符号，在灰度打印下会退化为三个相似的方块。

> **`unknown` 与 `incident` 是同一个数据状态（`state: 'unknown'`）的两种成因**，不是两个并列状态。
> 分叉发生在**渲染签名**与**汇总**两层，由 `reason` 字段决定 —— 详见 §3.8.2 与 §4.3。
> 视觉上必须可区分，因为**两者的用户动作完全不同**：结构未知要"绕开该能力"，事故要"等重启 / 查网关"。

### 3.8.2 实现约定

```ts
/** 三种"有判定"的状态 */
export type KnownState = 'satisfied' | 'degraded' | 'violated';

/** ★ 未知的两分 —— 决定它是否升级为主徽章 */
export type UnknownReason = 'structural' | 'incident';

/** 单条契约的状态。四值，不含 null / undefined */
export type ContractState = KnownState | 'unknown';

/** 渲染签名键 —— 与 ContractState 的唯一区别是 unknown 按 reason 分叉 */
export type SignatureKey = KnownState | 'unknown' | 'incident';

/** 签名是整体，不从外部拼装颜色 */
export interface StateSignature {
  key: SignatureKey;
  icon: string;   // ✔ ▲ ✖ ? !
  label: string;  // 满足 / 降级 / 违反 / 未知 / 事故
}
```

> **不提供 `getContractColor(state)` 这类 API**。一旦提供，就会有人只用颜色。
> 这是 P2 与 P3 在实现层的强制手段。

#### 未知态为什么必须分两半

单条契约的未知只有一个数据状态（`state: 'unknown'`），但成因有两种，**信息量相反**：

| reason | 含义 | 典型来源 | 是否升级为主徽章 |
|---|---|:--:|:--:|
| `structural` | 引擎能力本身给不出判定 | 契约 4 无法推断返回码语义（方案 §11.1 已接受其长期未知） · OpenDSS 工具面未核实 · 该引擎编号约定未实测 | ❌ **不升级**，降为次级标记 |
| `incident` | 本应能判定，却拿不到判定 | 契约引擎崩溃（§4.6.6）· 契约引擎熔断 · **SSE 边界 Zod 校验失败**（§8.4） | ✅ **升级** |

> **为什么 `structural` 不升级**：它长期存在且无信息量 —— 让它常年占据主徽章，
> 会把真正偶发但具体的 `degraded`（如参数被静默忽略）淹没。工程师会对问号产生免疫，
> 从此不再下钻 —— 这就是**告警疲劳**，它比漏报更隐蔽。
>
> **为什么 `incident` 必须升级**：它的含义是「**下面的契约状态整体不可信**」。
> 把它降级成一个小标记，等于把 P5 禁止的静默 fail-open 换个形式放回来。
> 事故的定义就是"不该发生的、系统级的意外" —— 它必须喧宾夺主。

### 3.8.3 ⚠️ 与方案的差异说明（五签名 vs 三态）

**方案内部存在一处不一致，本规范在此显式处理：**

| 出处 | 说法 |
|---|---|
| 方案 §2.2 | 「**状态三态**：`✅ 满足` · `⚠️ 降级可用` · `❌ 违反`」 |
| 方案 §11.1 | 残余风险处理：「**降级为「未知」态而非阻塞**」 |
| 方案 §11.3 | 契约引擎崩溃 → 「界面明确标注**「契约状态未知」**」 |

**取舍**：本规范采用**四态数据模型 + 五套渲染签名**：

| | 方案 | 本规范 | 变化 |
|---|---|---|---|
| 数据状态（单条契约） | 3 | **4** | + `unknown` |
| 渲染签名 | 3 | **5** | + `unknown`(`?`) + `incident`(`!`) |

**理由**：§11.1 与 §11.3 两处都要求 `unknown` 作为**对外可见的状态**存在。若它只是「三态之外的特殊情况」，实现时必然被当作异常分支处理（如渲染为 `null` 或灰色占位），而这正是方案 §11.3 明令禁止的静默 fail-open 的界面版本。

**v1.2 追加**：`unknown` 进一步按成因分为 `structural` / `incident`（§3.8.2）——
**`incident` 是需要抢主徽章的**（契约引擎崩溃、SSE 边界校验失败），
**`structural` 则必须让位给已知告警**（否则告警疲劳）。二者共用 `state: 'unknown'`，靠 `reason` 字段区分。

**给方案的回馈**：建议方案 §2.2 的「状态三态」表述改为「三态 + 未知态（结构 / 事故）」。本规范不回改方案，仅在此标注。

# 四、组件规范

## 4.0 本节的组织方式

每个组件按固定六段写：**功能说明 / 为什么需要 / 使用场景 / 状态与变体 / 属性表 / 示例与反例**。

「为什么需要」一律追溯到方案的某一节或某个实测缺陷 —— **没有依据的组件不写进规范**。

> ## ★ v2 修订：组件分为两组
>
> | 组 | 组件 | 默认可见性 | 说明 |
> |---|---|---|---|
> | **A. 常驻组件** | `Quantity` · `Identifier` · 基础件（§4.6） | **始终可见** | 它们约束的是**数值与标识符的写法**，在任何视图都适用 |
> | **B. 校验层组件** | `ContractBadge` · `ContractCard` · `ToolCallRow` | **默认折叠**在可开关的校验层里 | 能力一个不丢，只改变**层级与默认呈现** |
> | **C. 研究视图组件**（v2 新增） | 算例卡片 · 技能卡片 · 结果表 · 实验矩阵格 · 模块卡片 | 随所属视图 | 见 **§4.7** |
>
> **为什么 `Quantity` / `Identifier` 不从 B 组降级**：它们防的是两个**实测缺陷**
> —— 量纲误判（142% 看成 98%）与标识符偏差放大 3.1 亿倍。
> 这两个缺陷**与是不是"契约视角"无关**，在任何研究结果里都会犯。
> 把它们折叠进校验层，等于让最常见的两个错误失去防护。

## 4.1 ContractBadge · 契约徽章 ★

### 功能说明

以「色 + 图标 + 标签」三合一的**状态签名**形式，渲染一个契约状态。它是整个界面里**契约语义的最小载体**，出现在聊天内联、审计行、契约卡片、导出报告中。

### 为什么需要

方案 §三 要求五个视图**共享同一组件库**，「同一个契约徽章在聊天内联、契约面板、导出报告中渲染完全一致」。
若各视图各自实现，会出现同一条契约在两个位置的图标或措辞不同 —— 而契约状态正是最需要跨视图一致的信息。

### 使用场景

| 该用 | 不该用 |
|---|---|
| 标注某次工具调用触发的契约状态 | 标注非契约的一般性状态（如「加载中」用 §4.6 的 `LoadingState`） |
| 标注某条具体契约的类型 + 状态 | 用颜色块代替徽章（违反 P2） |
| 表格/列表中的紧凑标注（`size="sm"`） | 需要长文本说明时（应用 §4.2 契约卡片） |

### 状态与变体

| 维度 | 取值 |
|---|---|
| `state` | `satisfied` / `degraded` / `violated` / `unknown` |
| `size` | `sm`（12px，行内） / `md`（14px，卡片标题行） |
| 主题 | 自动跟随，无需属性 |

> **标签在任何尺寸下都不可省**。`size="sm"` 只缩小字号与内边距，**不隐藏文字** —— 隐藏文字即违反 P2。

### 属性表

| 属性 | 类型 | 必填 | 默认 | 说明 |
|---|---|:--:|---|---|
| `state` | `ContractState` | ✅ | — | 四值联合，无默认值 |
| `reason` | `UnknownReason` | **条件** | — | **`state === 'unknown'` 时必填** —— 决定渲染 `? 未知` 还是 `! 事故`（§3.8.2） |
| `contractType` | `1..8` | — | — | 契约编号。传入时徽章显示为「契约 N · 标签」 |
| `size` | `'sm' \| 'md'` | — | `'md'` | |
| `title` | `string` | — | 自动 | 悬停提示，默认由签名生成 |

### 示例

```tsx
// ✅ 正例：契约 3（参数契约）降级
<ContractBadge state="degraded" contractType={3} />
// 渲染：[▲ 契约 3 · 降级]

// ✅ 正例：审计行内的紧凑用法
<ContractBadge state="satisfied" contractType={7} size="sm" />
// 渲染：[✔ 契约 7 · 满足]
```

### 反例

```tsx
// ✖ 反例 1：只用颜色。本组件不提供此 API —— 写不出来
<span style={{ color: 'green' }}>✔</span>

// ✖ 反例 2：把标签省略。若实现允许 label={false}，即违反 P2
<ContractBadge state="degraded" showLabel={false} />

// ✖ 反例 3：缩小尺寸时隐藏文字
<ContractBadge state="violated" size="sm" showLabel={false} />
```

## 4.2 ContractCard · 契约卡片 ★

### 功能说明

呈现**一条契约告警的完整证据链**，并让工程师**显式承接风险**。

### 为什么需要

方案 §4.2 定义了它的四要素，并指出「标记已确认」是 **human-in-the-loop 在界面上的落点** ——
方案 **§4.2 的设计要点**指出 Grid-Orch *「承认需要 human-in-the-loop，但未说明界面上如何呈现」*。这个组件就是那个缺口。
（方案 §十 另把 Grid-Orch 的「可用性验证」列为**未做**，是相关的另一条缺口。）

### 四要素（方案 §4.2，缺一不可）

| 要素 | 内容 | 本项目实例 |
|---|---|---|
| **涉及** | 哪个 server / 哪条契约 | `pypsa` · 契约 3 参数契约 |
| **证据** | 实测到的具体现象 | 入参 `linearized` 未被引擎接受，且无报错 |
| **影响** | 对结论的后果 | DC OPF 结论可能不成立 |
| **建议** | 可执行的替代方案 | 改用 pypsa 支持的等价参数，或改用 pandapower |

> **「建议」是最容易被省掉的一栏，也是最重要的一栏**。没有建议的告警只是噪音 —— 用户知道有问题但不知道怎么办，最终会学会忽略所有告警。

### 状态与变体

| 变体 | 触发 | 渲染 |
|---|---|---|
| 默认 | — | 折叠展开由 `state` 决定 |
| 已确认 | `acknowledged === true` | 降饱和 + 显示确认人与时间 |

**折叠规则**（方案 §4.2）：默认只展开 `degraded` 与 `violated`；`satisfied` 默认折叠；`unknown` **展开**（P5：未知态必须可见）。

### 属性表

| 属性 | 类型 | 必填 | 说明 |
|---|---|:--:|---|
| `contractType` | `1..8` | ✅ | 契约编号 |
| `state` | `ContractState` | ✅ | |
| `servers` | `string[]` | ✅ | **涉及**。至少一个 |
| `evidence` | `string` | ✅ | **证据**。P4：不可为空 |
| `impact` | `string` | ✅ | **影响** |
| `suggestion` | `string` | ✅ | **建议** |
| `evidenceRef` | `string` | — | 证据下钻的目标（工具调用 ID） |
| `acknowledged` | `boolean` | — | 默认 `false` |
| `onAcknowledge` | `() => void` | — | 传入时显示「标记已确认」 |

## 4.3 ToolCallRow · Tool Call 审计行 ★

### 功能说明

审计**一次工具调用**：工具名、参数、以及这次调用触发的契约状态。

### 为什么需要

方案 §4.1 的对照表指出，Grid-Orch 的 Tool Call 面板只「列工具 + 参数 + 原始 JSON」，
本项目要升级为**契约级审计** —— 每一行额外标注契约状态。方案 §十 把这条列为「继承并加深」。

### 结构

```
▸ Tool Call (3)                                    ⚠️ 1 项契约告警
  ├─ pandapower.run_power_flow   [✔ 契约 1,3,4 满足]
  ├─ pypsa.optimize_network      [▲ 契约 3 降级：参数 `linearized` 不存在但被静默忽略]
  │    args: {network: ..., linearized: true}     ← 已标注
  └─ powerio.calc_matrix         [✔ 契约 6 已归一（1-based → 0-based）]
       args: {matrix: "lodf", powerio_ir: ...}
```

### 关键设计点

1. **工具名用等宽**（§3.3.1）：`pandapower.run_power_flow` 需要逐字符核对。
2. **触发了契约的参数必须行内标注**。方案示例中 `linearized: true` 后被标了 `← 已标注` ——
   若只把契约状态挂在行级，用户仍需自己猜是哪个参数出的问题。
3. **组头显示告警计数**（`⚠️ 1 项契约告警`），让用户不必展开就能看到问题。
4. **参数区默认折叠**，但**触发契约降级的参数在折叠状态下也要可见**（在行摘要中提示）。

### 属性表

| 属性 | 类型 | 必填 | 说明 |
|---|---|:--:|---|
```ts
export type ContractType = 1 | 2 | 3 | 4 | 5 | 6 | 7 | 8;   // 与方案 §2.2 严格一致

// 契约命中 —— 参数名与契约类型建立了引用关系，不再靠自由字符串关联
// ★ 判别联合：unknown 必须说明 reason，不允许存在"未分类的未知"
export type ContractHit =
  | { type: ContractType; state: KnownState; arg?: string; note?: string }
  | { type: ContractType; state: 'unknown'; reason: UnknownReason; arg?: string; note?: string };

/** ★ 行级汇总结果 —— 双轨：主徽章 + 次级标记 */
export interface RowSummary {
  /** 主徽章。事故 > 已知告警；无任何判定项时为 'unknown'（绝不取 satisfied） */
  primary: KnownState | 'unknown' | 'incident';
  /** 次级标记：结构性未知条数。**不参与主徽章竞争** —— 这是告警疲劳的解法 */
  structuralUnknown: number;
  /** 事故性未知条数。> 0 时 primary 强制为 'incident' */
  incidentUnknown: number;
}

/** ★ 导出纯函数 —— 汇总规则只有这一处实现 */
export function summarize(hits: readonly ContractHit[]): RowSummary;
```

| 属性 | 类型 | 必填 | 说明 |
|---|---|:--:|---|
| `server` | `EngineId` | ✅ | server id（小写）。与 `Identifier.engine` 同源 |
| `tool` | `string` | ✅ | 如 `optimize_network` |
| `contracts` | `readonly ContractHit[]` | ✅ | ⚠️ **允许空数组**，但空数组的汇总为 `unknown`（见下） |
| `args` | `Record<string, unknown>` | ✅ | 调用参数 |
| `callId` | `string` | ✅ | 下钻目标（P4） |
| `durationMs` | `number` | — | |
| `defaultExpanded` | `boolean` | — | 默认 `false` |

> ❌ **不提供 `state` 属性**（v1.0.0 草案曾有，已删除）。
> 原设计让 `state`（"汇总状态"）与 `contracts` 同时作为必填 prop —— **同一件事有两个来源，且组件不做计算**，
> 于是"汇总规则"沦为散文，每个调用点各自手算 `violated > unknown > degraded > satisfied`，必然漂移。
> 结果可能是行级徽章显示「✔ 满足」而展开明细里赫然一条「✖ 违反」——
> 而徽章恰恰是用户第一眼看到的东西。现在状态**由组件从 `contracts` 派生，调用点无从谎报**。

### 汇总规则（双轨，重要）

行的呈现由 `summarize(contracts)` 得出，**只有这一处实现**。

**① 主徽章 `primary`**（用户第一眼看到的唯一状态）：

```
incidentUnknown > 0        →  'incident'
否则 取 known 项最差        →  violated > degraded > satisfied
无任何 known 项             →  'unknown'        ← 不是 satisfied
```

**② 次级标记**（`structuralUnknown > 0` 时显示 `+?N`）：

| 情形 | 主徽章 | 次级标记 |
|---|---|---|
| `[契约7 满足, 契约4 unknown/structural, 契约3 degraded]` | `▲ 降级` | `+?1` |
| `[契约7 满足, 契约1 满足, 契约4 unknown/structural]` | `✔ 满足` | `+?1` |
| `[契约7 满足, 契约4 unknown/structural, 契约3 unknown/incident]` | `! 事故` | `+?1` |
| `[全部 incident]`（契约引擎崩溃） | `! 事故` | — |
| `[]`（空集） | `? 未知` | — |

**空集的汇总（必须显式定义）**：

```
summarize([]).primary === 'unknown'      // ✅ 规范定义
summarize([]).primary === 'satisfied'    // ❌ 错误的自然实现
```

> ⚠️ **为什么必须写死这条**：`hits.reduce(worst, 'satisfied')` 是最自然的写法，
> 空数组会返回 `'satisfied'` —— **"没检查"被渲染成"检查过且没问题"**。
> 而契约引擎崩溃时（方案 §11.3）后端恰恰不再推送契约事件，`contracts` 就是空的。
> 一个乐观的幺元，会把 P5 明令禁止的静默 fail-open 从后门放进来。**空集 = 未知，不是满足。**

### 为什么是双轨而不是单标量（原「已知局限」的解法）

**原设计的缺陷**：方案 §11.1 自陈契约 4（状态映射）"若返回码语义不明则需额外探测 →
**降级为未知态而非阻塞**"，即**契约 4 长期 `unknown` 是设计已接受的常态**。

原设计用**一个标量** `violated > unknown > degraded > satisfied` 汇总。后果：
「契约 4 常态未知」（无信息量）会**常年压过**「契约 3 降级」（具体、有建议、有后果），
几乎所有审计行都挂着一个问号或黄色 → 工程师对问号**免疫**，不再下钻 →
**P5 的"未知最危险"被自我拆解成告警疲劳**（Alert Fatigue by Design）。

**根因**：单标量试图同时表达**两个正交维度** —— 「多严重」与「多可信」。硬塞进一个全序必然牺牲一边。

**解法**：拆成两个维度，各自有独立的呈现位：

| 维度 | 承载 | 呈现位 |
|---|---|---|
| **严重度**（有多糟） | `known` 项的最差值 | **主徽章** |
| **可信度**（有多确定） | 未知项的条数与成因 | **次级标记 `+?N`** |

> **P5 有没有被削弱？没有。** 未知项**依然可见** —— 只是从"抢主位"移到"常驻次级位"，
> 而它本来就不该抢主位（结构性未知长期存在，抢主位等于天天喊狼来了）。
>
> **但 `incident` 例外：它必须抢回主位。** 因为它不是"某一条契约不确定"，
> 而是"**整个契约判定链条失效**"—— 让这种状态只显示一个小标记，就等于把静默 fail-open 换个形式放回来。
> 这正是把它从 `unknown` 里拆出来的目的：**让该闭嘴的闭嘴，让该喊的喊得更响。**

### 反例

```tsx
// ✖ 反例 1：只列工具名，不标契约 —— 退化为方案 §4.1 批评的 Grid-Orch 做法
<ToolCallRow server="pypsa" tool="optimize_network" args={...} />

// ✖ 反例 2：参数区显示未标注的原始 JSON，用户需自行发现哪个参数有问题
<pre>{JSON.stringify(args)}</pre>
```

## 4.4 Quantity · 数值单元 ★

### 功能说明

渲染一个**数值**，并**结构性保证**它与单位（以及需要时的判据）同时出现。

### 为什么需要

**实测缺陷**：过载判据用 MW 而非 MVA，会把 `142.47%` 看成 `98.16%`，进而**误判为正常**。

方案 v4 §七.3 规则 1 因此规定「数值必须与单位同时出现 —— 须写 `142% (MVA 判据)`」。
本组件把这条规则变成**类型约束**：裸数值**写不出来**。

### ⚠️ 判别联合挡得住「忘写判据」，挡不住「判据写错」

首版设计用判别联合让 `unit="%"` 时 `criterion` 必填。但审查发现一个更根本的漏洞：

```tsx
// 编译通过 —— 而这正是原缺陷本身
<Quantity value={98.16} unit="%" criterion="MW" />
// 渲染：98.16% (MW 判据)      ← 带上判据后缀，反而比裸的 98.16% 更可信
```

**写下这行的人，正是当初用 MW 算负载率的那个人。** 他不知道判据选错了，
所以会从 `'MVA' | 'MW' | 'pu'` 里随手挑一个 —— 而三个选项里有他正在犯的那个错。
**把正确值与错误值并列成同一枚举，等于给错误值发了一张合法性证书。**

根因：`criterion` **不是展示属性，而是关于数值物理来源的断言**。
类型里没有任何东西携带来源，所以任何"在渲染点写判据"的设计都防不住它。

### 修法：数值由数据层构造，组件只渲染

```ts
type Unit = 'MW' | 'MVA' | 'MVar' | 'kV' | 'A' | 'pu' | 'MW·h';
type Criterion = 'MVA' | 'MW' | 'pu';

// 单位与判据的约束 —— 判别联合决定 criterion 何时必填
type UnitSpec =
  | { unit: Unit;            criterion?: never }   // 有量纲：单位即判据
  | { unit: '%';             criterion: Criterion }; // 比值：脱离判据无意义

/** ★ 不可在渲染点构造的数值对象 */
export interface Measured extends UnitSpec {
  readonly value: number;
  /** P4：回到产生它的那次工具调用。**必填** —— 这是"证据可下钻"的落点 */
  readonly source: string;        // CallId
  readonly __measured: unique symbol;
}

/** ★ 唯一构造入口 —— 只在数据适配层调用（工具结果 / SSE 事件 → 可渲染对象） */
export function measure(
  raw: unknown,                   // 工具结果字段；内部做运行时校验
  spec: UnitSpec,
  source: string,                 // CallId
): Measured;                      // '%' 无 criterion → 抛错并落 unknown

/** 组件只渲染，不判定 */
export function Quantity(props: {
  of: Measured;
  precision?: number;
  delta?: boolean;                // 渲染为 Δ = ... 形式
  alarm?: { level: 'warn' | 'over' };
}): JSX.Element;
```

**这样改的收益**：把"判据写错"从 **N 个渲染点收敛到 1 个数据适配点**，成为一处可审计、
可加运行时校验、可写单元测试的地方。

> ⚠️ **必须如实说明的边界**：类型系统**仍然不能验证判据是否正确**。
> 它只能保证判据来自一个显式声明的来源，且来源集中。
> 本组件**不再宣称"判据错误不可表达"** —— 那是它做不到的。

> ❌ **v1.0.0 草案的 `state` 属性已删除**，两个原因：
> ① 它只做"着色"，没有图标与标签 —— 正是 P2 与 §3.8.2 明令禁止的「颜色单独承载信息」，
> 且规范自己的正例就违反了规范自己的原则；
> ② 语义被混用 —— `142%` 超载是**物理越限**，不是**契约违反**，不该共用 `ContractState`。
> 需要同时表达契约状态时，在 `Quantity` **旁边**挂 `<ContractBadge>`，不要让 `Quantity` 内嵌徽章。

### 渲染规则

| 输入 | 渲染 |
|---|---|
| `{ value: 142.47, unit: '%', criterion: 'MVA' }` | `142.47% (MVA 判据)` |
| `{ value: 958.49, unit: 'MW' }` | `958.49 MW` |
| `{ value: 6.98e-11, unit: 'pu' }` + `delta` | `Δ = 6.98e-11 pu` |
| `{ value: 142.47, unit: '%', criterion: 'MVA' }` + `alarm: {level:'over'}` | `142.47% (MVA 判据) 超限` |

- **数值与单位均为等宽**（§3.3.1）。
- 判据后缀 `(MVA 判据)` 用 `--c-text-muted`，不削弱主数值的可读性。
- `alarm` **必须渲染文字标签**（`接近限值` / `超限`），不得只改颜色（P2）。

### 属性表

| 属性 | 类型 | 必填 | 默认 | 说明 |
|---|---|:--:|---|---|
| `of` | `Measured` | ✅ | — | **只能由 `measure()` 构造**。`{value, unit, criterion, source}` 一并注入 |
| `precision` | `number` | — | 自动 | 有效数字位数 |
| `delta` | `boolean` | — | `false` | 渲染为 `Δ = ...` 形式 |
| `alarm` | `{ level: 'warn' \| 'over' }` | — | — | **物理越限**（非契约）。渲染文字标签 |

> `value` / `unit` / `criterion` / `source` **不再是 `Quantity` 的属性** —— 它们在 `Measured` 里，
> 由 `measure()` 一次性构造。渲染点无法单独覆写判据。

### 示例与反例

```tsx
// ✅ 数据适配层：唯一构造点
const pct = measure(row.loading_pct, { unit: '%', criterion: 'MVA' }, callId);

// ✅ 渲染层：只消费
<Quantity of={pct} alarm={{ level: 'over' }} />
// 渲染：142.47% (MVA 判据) 超限

// ✅ 有量纲量
<Quantity of={measure(row.flow_mw, { unit: 'MW' }, callId)} />

// ✖ 反例 1：裸百分比 —— 编译错误：property 'criterion' is missing
<Quantity of={measure(v, { unit: '%' }, callId)} />

// ✖ 反例 2：在渲染点手写判据 —— 旧 API 已删除，写不出来
<Quantity value={98.16} unit="%" criterion="MW" />

// ✖ 反例 3：把单位并进字符串 —— `measure` 的 spec 参数是判别联合，挡得住
measure("142.47%", ...)

// ✖ 反例 4：直接写字面量 —— 本规范不禁止，但 code review 应拒绝
<span>最大过载 142.47%</span>
```

> ⚠️ **反例 4 是已知的逃逸路径**：`<span>` / ECharts 轴名 / SVG / **LLM 流式 Markdown 正文**都不经过本组件。
> 其中 **LLM 散文里的数值是用户读数最多的地方**，却完全不受类型约束 —— 那部分只能靠提示词约定 +
> 渲染后校验。**本规范不声称已覆盖它。**

## 4.5 Identifier · 标识符 ★

### 功能说明

渲染一个**元件标识符**，并标注其**编号约定**。约定缺省时查表推导（提供 `outputKey` → 查 `byOutput`；
否则由 `engine` 查 `byEngine`，见「引擎与约定的绑定」）——
**查不到就显示「约定未知」，绝不猜一个值**。

### 为什么需要

**实测缺陷**：pandapower 用 **0-based 索引**，PyPSA 沿用 IR 的 **1-based 标识**。
按字面键直接比对，会把跨引擎偏差**从 8.84e-11 pu 放大到 0.027806 pu —— 放大 3.1 亿倍**，且会拿不同物理元件做对比。

方案 v4 §七.3 规则 2 因此规定「标识符必须标注约定 —— 须写 `12 (0-based)` 或 `13 (1-based)`」。

### 属性表

| 属性 | 类型 | 必填 | 默认 | 说明 |
|---|---|:--:|---|---|
```ts
// 9 个 server id 的字面量联合 —— 与 registry.py 一致，杜绝写显示名
export type EngineId =
  | 'pandapower' | 'pypsa'  | 'surge'   | 'andes' | 'egret'
  | 'opendss'    | 'hope'   | 'genx'    | 'powerio';

// 三态，含 unknown —— 与 ContractState 的四态同理：未知必须可表达
export type Convention = '0-based' | '1-based' | 'unknown';
```

| 属性 | 类型 | 必填 | 默认 | 说明 |
|---|---|:--:|---|---|
| `id` | `number \| string` | ✅ | — | 元件编号。PyPSA 的元件名可为字符串（如 `"line_0"`） |
| `convention` | `Convention` | — | **查表推导；查不到 → `'unknown'`** | 编号约定。**不得猜测** |
| `engine` | `EngineId` | — | — | 引擎名（**小写 server id**）。无输出键时参与推导，并在显式传 `convention` 时校验冲突 |
| `outputKey` | `string` | — | — | ★ 输出键 `server.tool.field`（F-5）。提供时**优先查 `byOutput` 表**；未命中 → `'unknown'`（**不回退** `byEngine`） |
| `kind` | `string` | — | — | 元件类型。**不作封闭枚举** —— 引擎实际类型含 `line`/`trafo`/`trafo3w`/`ext_grid`/`sgen`/`shunt`/`storage` 等，封闭枚举会逼出 `as any` 强转 |

### 引擎与约定的绑定

> ⚠️ **键必须用 `powermcp/registry.py` 的 server id（小写），不得用显示名。**
> 若绑定表写 `PyPSA` 而真源键是 `pypsa`，运行时查表未命中 → 落到兜底分支 →
> **静默标错约定**。这恰是本组件要防的那个缺陷（偏差放大 3.1 亿倍）在实现层的重演。

**★ F-5（2026-09-26 实测裁定）：约定是「输出」的属性，不是「引擎」的属性。**
同一引擎的不同输出约定可以不同 —— surge 的**矩阵索引**是 0-based（case30 PTDF/LODF 实测），
但其**母线号输出**是 1-based（case118 实测：`bus_numbers` = 1…118；N-1 的 `bus_number` 出现 118，
而 0-based 最大只能是 117 —— 决定性）。单张按引擎的表表达不了这件事。

**第一优先：`byOutput` 表**（`tokens.json#identifierConvention.byOutput`，键 `server.tool.field`，**只收实测条目**）：

| 输出键 | 约定 | 实测依据 |
|---|---|---|
| `surge.run_ac_power_flow.bus_numbers` | **1-based** | case118：`bus_numbers` = 1…118（源文件编号） |
| `surge.run_n1_branch_contingency.bus_number` | **1-based** | case118 N-1：`bus_number` 出现 118 —— 0-based 最大只能是 117 |

**回退：`byEngine` 表**（仅在调用**未提供**输出键时使用；语义 = 该引擎**数据模型下标**的约定）：

| server id | 约定 | 实测依据 |
|---|---|---|
| `pandapower` | 0-based | case30 跨引擎比对实测（数据模型下标） |
| `surge` | 0-based | case30 PTDF/LODF 实测 —— ⚠️ **只对「矩阵索引」成立**，母线号见 byOutput |
| `pypsa` | 1-based | case30 跨引擎比对实测 |
| `andes` · `egret` · `opendss` · `hope` · `genx` · `powerio` | **`unknown`** | ⚠️ **未实测** |

> **为什么后 6 个标 `unknown` 而不是猜一个**：本项目只实测过 pandapower / PyPSA / surge 三者。
> 给未实测的引擎编一个约定值，等于把「**确定语气下的假声明**」重演一遍 —— 而那是这条规则当初要消灭的东西。
> `unknown` 是类型系统支持、界面也渲染得出的**第三态**，比猜一个值诚实且同样可用。

**推导规则**（`convention` 未显式传入时）：

```
带输出键：  convention = BY_OUTPUT[server.tool.field]   // 查 tokens.json#identifierConvention.byOutput
                       = 'unknown'                      // ★ 未命中 → unknown，**不回退 byEngine**
                                                        //   （两表语义不同：输出字段 vs 数据模型下标，混用正是 F-5 的错因）
仅引擎：    convention = BY_ENGINE[engine]              // 查 tokens.json#identifierConvention.byEngine
                       = 'unknown'                      // engine 缺省 或 查表未命中
```

> ⚠️ **兜底是 `unknown`，不是 `0-based`。** 本规范草案曾兜底为 `0-based` ——
> 那会把 PyPSA 的 `13` 渲染成 `13 (0-based)`，一条**语气确定的假声明**，比显示「未知」危险得多。

### 三重防护

| # | 机制 | 生效时机 | 防的是 |
|---|---|---|---|
| 1 | `engine` 的类型是 9 个 server id 的**字面量联合** | **编译期** | 写 `engine="PyPSA"` 直接编译错误 |
| 2 | 查表未命中 → `unknown`（byOutput 未命中**不回退** byEngine） | 运行时 | 接入新引擎/新输出时不会静默标错 |
| 3 | 显式传 `convention` 且与（输出/引擎）查表结果矛盾 → 抛错 | 运行时 | 人工断言与事实冲突 |

第 1 条把「大小写写错」从**运行时静默错误**提前成了**编译错误** —— 这是本组件防线的关键一环。

### ⚠️ 已知残余代价（v1.0.0）

`convention` **带默认值**（用户决策）：由 `engine` 查表推导，查不到则 `unknown`。

| 情形 | 后果 |
|---|---|
| 传了 `engine` 且表中有绑定 | ✅ 正确推导 |
| 传了 `engine`，表中为 `unknown` | ✅ 渲染 `(约定未知)`，**不产生假声明** |
| `engine` 缺省（类型上允许） | ✅ 兜底 `unknown`，同上 |

**残余代价**：`(约定未知)` 在跨引擎比对表里**比 `(0-based)` 难看**，可能诱发开发者为了让表格好看而随手写死一个 `convention`。`convention` 在类型上仍可由调用点显式传入，**无法禁止**。
→ 因此**这条最终仍要靠 code review**。本规范不再宣称它被类型系统完全覆盖。

### 示例与反例

```tsx
// ✅ 正例 1：显式传约定（最强）
<Identifier id={12} convention="0-based" engine="pandapower" kind="branch" />
// 渲染：12 (0-based)

// ✅ 正例 2：只传引擎，约定自动推导
<Identifier id={13} engine="pypsa" kind="branch" />
// 渲染：13 (1-based)

// ✅ 正例 3：未实测的引擎 —— 诚实显示未知，而不是猜
<Identifier id={7} engine="andes" kind="bus" />
// 渲染：7 (约定未知)

// ✅ 正例 4：engine 缺省 —— 兜底同样是 unknown
<Identifier id={12} />
// 渲染：12 (约定未知)

// ✖ 反例 1：写显示名 —— 编译错误（EngineId 是小写字面量联合）
<Identifier id={13} engine="PyPSA" />

// ✖ 反例 2：裸写编号，绕开组件
<span>关键支路 12/15/33</span>
```

> ⚠️ **反例 2 值得单独说**：方案 §4.3 的示例表格里就有 `关键支路索引 | 12/15/33 | 13/16/34 | 12/15/33` 这种写法。
> 那是**文档中的对照表**，可以省后缀；但**界面上必须逐项标注**，否则用户无法判断两个 `12` 是否指同一条支路。
> 这正是 §3.2 与 §3.3 之间「一致性」判断的前提。

方案 §八 的 P1 包含「契约引擎 + 契约面板 + 聊天面板 + **进程监管**」。下列基础件是支撑它们的**最小集**，全部基于 shadcn/ui，只做 token 覆盖（见 §8.2）。

### 4.6.1 Button

| `primary` | 主操作（发送、确认） | `--c-interactive-*` |
| `secondary` | 次操作 | `--c-surface-raised` + `--c-border-default` |
| `ghost` | 行内操作（展开、下钻） | 透明底，悬停 `--c-interactive-subtle` |
| `danger` | 不可逆操作 | 走 `violated` 状态签名 |

高度 `32px`（sm）/ `40px`（md）；圆角 `--p-radius-md`；字号 `body`。

### 4.6.2 Input / Select / Command

用于控制头部的**五个**内联选择器（方案 §4.1）：**server 多选（9）/ provider / model / 算例 / 契约严格度**。

> ⚠️ 方案 §4.1 对照表里的「4 个内联选择器」是 **Grid-Orch 的做法**那一列，本项目的改造列列了 **5 项**。
> 首版误把 4 当成了本项目的数量。**以本节的五项为准。**
server 多选为 **combobox + 多选 chip**，因为 9 个引擎需要搜索与批量勾选。

### 4.6.3 Dialog

仅用于**不可逆操作**或**需要完整上下文**的操作。
⚠️ 方案 §11.5(b) 明确规定：危险操作的确认**不用通用弹窗**，而用「影响面预评估」——
具体文案见 §7.3。Dialog 仅承载承接到确认后的最终执行。

### 4.6.4 Toast

| 类型 | 用途 |
|---|---|
| `info` | 操作已发生 |
| `success` | 调用成功 |
| `error` | 调用失败（含引擎崩溃） |
| `contract` | **契约状态变化**（如引擎升级导致 ✅→⚠️） |

⚠️ `contract` 类型的 toast **不得自动消失**，必须用户手动关闭或跳转到契约面板 —— 契约状态变化是审计事件，不是通知。

### 4.6.5 EmptyState / LoadingState / ErrorState

三态必须**区分**，不得用同一个灰色占位：

| 状态 | 文案要点 | 依据 |
|---|---|---|
| `EmptyState` | 说明「为什么空」+ 下一步动作（如「尚未选择引擎」） | 空态最容易被写成「暂无数据」四个字 |
| `LoadingState` | 骨架屏；**超过 800ms 才出现**，避免闪烁 | |
| `ErrorState` | 区分**引擎崩溃**（fail-closed，方案 §11.3）与**调用失败** | 二者的用户动作不同：前者等重启，后者改参数 |

### 4.6.6 EngineStatusIndicator · 引擎状态指示器 ★

**P1 必做项** —— 方案 §八 把「进程监管」从可选加固提升为 P1 必做，理由是没有它「任何一次引擎僵死都会让整个网关不可用」。

**引擎状态是独立枚举，不是 `ContractState`** —— 只借用签名的**颜色**，标签用自己的。

```ts
export type EngineStatus =
  | 'running'       // 进程存活，心跳正常
  | 'starting'      // 启动中（HOPE / GenX 的 Julia 子进程启动慢，此态会持续较久）
  | 'degraded'      // 可用但受限（如 Egret 的 Ipopt 不可用）
  | 'crashed'       // 进程崩溃，fail-closed
  | 'circuit-open'; // 熔断已打开

/** 引擎态 → 签名键（仅取色） */
export const ENGINE_SIGNATURE: Record<EngineStatus, SignatureKey> = {
  'running':      'satisfied',
  'starting':     'unknown',    // structural：常态、会自愈，不升级
  'degraded':     'degraded',
  'crashed':      'incident',   // ★ 事故，不是 violated
  'circuit-open': 'incident',   // ★ 事故
};
```

| 状态 | 签名 | 标签（引擎专用） | 说明 |
|---|---|---|---|
| `running` | `satisfied` | 运行中 | |
| `starting` | `unknown` | 启动中 | **结构性**：常态且会自愈，故不升级 |
| `degraded` | `degraded` | 受限 | |
| `crashed` | **`incident`** | 已崩溃 | **fail-closed**：该引擎标记不可用，调用直接拒绝 |
| `circuit-open` | **`incident`** | 已熔断 | 熔断已打开，等待退避重试 |

> ⚠️ **v1.2 修正**：原先 `crashed` 与 `circuit-open` 都映射到 `violated` → 在侧边栏渲染成**同一个「✖ 违反」**，
> 二者的区分（前者等重启、后者等退避）消失。现改用 `incident` 签名，并以**独立标签**区分。
>
> 另外，**进程崩溃本质上不是「契约违反」** —— 没有哪条契约被违反，而是"判定能力没了"。
> 这正是 `incident` 这个签名要表达的东西（§3.8.2）。

### 属性表

| 属性 | 类型 | 必填 | 说明 |
|---|---|:--:|---|
| `engine` | `EngineId` | ✅ | server id（小写），与 §4.5 / §3.2.3 同源 |
| `status` | `EngineStatus` | ✅ | 上表五值 |
| `lastHeartbeatAt` | `string` (ISO) | — | 心跳时间，用于悬浮提示 |
| `reason` | `string` | — | `crashed` / `degraded` 的原因 |
| `blockedToolCount` | `number` | — | fail-closed 下被拒绝的调用数 |
| `onRestart` | `() => void` | — | 传入时显示重启入口 |

**失败语义**（方案 §11.3，必须在界面上体现）：

| 组件 | 失败表现 |
|---|---|
| 引擎进程崩溃 | fail-closed —— 该引擎的调用**直接拒绝**，界面明确不可用 |
| **契约引擎崩溃** | fail-loud but non-blocking —— **不阻塞调用**，但所有契约状态**统一显示为 `unknown`** |

> ❌ **绝不允许契约引擎失败时静默隐藏契约状态**。方案原文：那会退化成「没有契约引擎」，
> 用户以为有保护实际没有，**比明确的故障更危险**。这一条在界面上的落点就是：**契约引擎挂了，徽章全部变成 `? 未知`，而不是消失**。

## 4.7 研究视图组件（★ v2 新增）

> 本节的组件**没有 v1.x 对应物** —— v1.x 的五个签名组件全部围绕契约。
> 它们是「研究流程是第一公民」（P1）在组件层的落地，已登记于 [附录 B.4](附录-b与前端设计方案的追溯表)。

### 4.7.1 VerificationLayer · 校验层容器 ★

**功能说明**：把 v1.x 的全部差异化能力（契约面板 / 跨引擎一致性 / 能力矩阵 / IR 检查器）
收进一个**默认折叠、可整体开关**的容器；折叠时**只保留顶部状态条**。

**为什么需要**：v4 §4.3 **废除**了「契约状态先于图表渲染」。若契约面板仍常驻，
「研究流程」就永远让位于「契约审计」—— 那是 v1–v3 的定位。但**能力一个不丢**：
折叠的是**呈现层级**，不是能力。

**使用场景**：任何视图的右侧；顶部状态条**所有视图共有**。

**属性表**

| 属性 | 类型 | 必填 | 说明 |
|---|---|:--:|---|
| `open` | `boolean` | ✅ | 是否展开（默认 `false`） |
| `summary` | `ContractSummary` | ✅ | 四态计数（`satisfied` / `degraded` / `violated` / `unknown`） |
| `worst` | `ContractState` | ✅ | 主徽章状态（按 `incident > violated > degraded > satisfied` 汇总） |
| `incidentUnknown` | `number` | ✅ | **事故性未知**计数 —— 见下 |
| `onToggle` | `() => void` | ✅ | |
| `disabled` | `boolean` | — | 整体关闭校验层（用户显式选择） |

**★ 硬规则（三条，缺一即违约）**

1. **折叠 ≠ 隐藏**：`open=false` 时**顶部状态条仍必须渲染**，且含完整状态签名。
2. **`incident` 未知态必须升至状态条** —— 契约引擎崩溃、SSE 边界校验失败属于这一类。
   把它降级为"折叠面板里的一个次级标记"，就是 P5 禁止的**静默 fail-open 的另一种形式**。
3. **`structural` 未知态不参与主徽章竞争**（§3.8.2）—— 它长期存在、无信息量，
   抢主徽章只会造成告警疲劳。

**反例**

```
❌ open=false 时整条状态条消失              → P5 违约：未知态不可见
❌ 契约引擎崩溃，状态条显示 "✔5"（只数已知）  → 静默 fail-open，最危险
❌ structural unknown 把主徽章拉成 "?"       → 告警疲劳，真告警被淹没
```

### 4.7.2 CaseCard · 算例卡片 ★

**功能说明**：渲染一个**算例**（v4 引入的一级实体）的元数据与**现算**的可用性。

**为什么需要**：v3 只有 session 粒度，研究无法「组织」。算例是实验矩阵的**主语**。

**使用场景**：② 算例库列表与详情；④ 实验矩阵的因子选择。

**属性表**（字段与 `GET /cases` 一一对应）

| 属性 | 类型 | 必填 | 说明 |
|---|---|:--:|---|
| `id` | `string` | ✅ | 由**规范化绝对路径**派生的稳定 id |
| `label` | `string` | ✅ | 显示名 |
| `format` | `string` | ✅ | 如 `m` / `json` / `nc` |
| `size` | `number` | ✅ | 登记时的字节数 |
| `sha256` | `string` | ✅ | 登记时的内容哈希 |
| `registeredAt` | `string` (ISO) | ✅ | **进入研究的时间**，更新时不被覆盖 |
| `tags` | `string[]` | — | |
| `available` | `boolean` | ✅ | 源文件**现在**是否可读 |
| `drift` | `boolean` | ✅ | 文件在、但内容与登记时**不同** |
| `withinAllowedRoots` | `boolean` | ✅ | server 子进程**能否读到它** |
| `currentSize` | `number \| null` | — | 现算大小 |

**★ 三条硬规则**

1. **`available` / `drift` 必须现算**（由服务端每次读取时计算），**不得缓存**——
   存下来的"文件还在"会过期，而过期的"还在"比不报更危险。
2. **`drift=true` 必须显式呈现**，且文案须说明"结论来自**登记时**的数据"。
3. **`withinAllowedRoots=false` 必须给出可执行指引** —— 而不是只说"读不到"。
   正确文案：*「该目录不在 `POWERIO_MCP_ALLOWED_ROOTS` 内，server 读不到它。
   把 `<目录>` 加入该变量后重启网关。」*

**反例**

```
❌ 只显示 label，不显示 drift            → 用户以为在分析当前文件，其实不是
❌ available=false 时卡片直接消失        → 用户以为算例被删了，其实是路径变了
❌ "算例不可用"（无指引）                 → 用户不知道要改什么
```

### 4.7.3 SkillCard · 技能卡片 ★

**功能说明**：渲染一个 PowerSkills 技能，**含 Escalation triggers 表**与健康信号。

**为什么需要**：★ **这是 v2 相对 v1.x 最重要的补口** ——
21 个技能在 v1.x 中**零覆盖**（`skill` 在本文档出现 0 次），
而 `Escalation triggers`（观测值 → 缓解手册的数字驱动映射）是**「研究方法」最直接的载体**。

**使用场景**：⑤ 技能手册；③ 对话分析里 LLM 触发 escalation 时的建议卡片。

**属性表**（字段与 `GET /skills` 一一对应）

| 属性 | 类型 | 必填 | 说明 |
|---|---|:--:|---|
| `id` / `name` | `string` | ✅ | |
| `kind` | `'tool' \| 'engineering' \| 'meta'` | ✅ | 11 工作流 / 10 缓解手册 / 1 元技能 |
| `description` | `string` | ✅ | 来自 SKILL.md frontmatter |
| `escalation` | `{ observation: string; escalateTo: string }[]` | ✅ | **可点选唤起**目标手册 |
| `health` | `SkillHealth` | ✅ | 见下 |

**★ 两条硬规则**

1. **健康度必须显示，且必须允许 `unknown`**。
   `/skills` 的 `health.level` **恒为 `unknown`**（本模块只报可计算信号，不转录人工审计结论）。
   界面**不得**把它渲染成"正常"—— 那会让用户以为 21 个技能都可靠。
   典型反例：`pypsa` 的 `Network.status` 会**误报失败**，比崩溃更隐蔽
   （Agent 会据此**主动放弃一条其实可行的路径**）。
2. **`escalation` 必须展示 `observation` 原文**（含反引号内的字段名）——
   它是用户判断"我这次是否命中"的唯一依据，转述会失真。

**反例**

```
❌ 技能卡片不显示健康度                → 用户以为 21 个技能都可靠
❌ health.level='unknown' 渲染为绿色 ✔  → 把"不知道"谎报成"没问题"
❌ 只显示目标手册名，不显示触发条件      → 用户无法判断是否命中
```

### 4.7.4 ResultTable · 结果表

**功能说明**：按**模块声明的列定义**渲染结果表，并支持导出。

**为什么需要**：研究结果 90% 是表格与数值。v4 把它做成**数据驱动**（`result_tables` 的
`columns` schema → 内核自动渲染），**这正是让 L1 模块覆盖大部分选题的原因** ——
多数选题无需写任何组件。

**使用场景**：③ 对话分析的模块结果卡片；④ 实验矩阵的结果区。

**属性表**

| 属性 | 类型 | 必填 | 说明 |
|---|---|:--:|---|
| `columns` | `ResultColumn[]` | ✅ | 来自模块 `result_tables[].columns` |
| `rows` | `Record<string, unknown>[]` | ✅ | |
| `metrics` | `Metric[]` | — | 表头摘要（如 `binding_count`） |
| `onExport` | `(format: 'csv' \| 'md') => void` | — | |

`ResultColumn`：`{ key, title, type: 'text' \| 'number' \| 'quantity' \| 'identifier' \| 'state', unit?, criterion?, engine? }`

**★ 硬规则**：`type` 为 `quantity` 的列**必须**走 `Quantity` 组件（单位 + 判据），
`identifier` 的列**必须**走 `Identifier` 组件（编号约定）。
**这是 P1 改写后仍保留 `Quantity` / `Identifier` 为常驻组件的原因**（见 §4.0）。

**反例**

```
❌ quantity 列直接渲染数字 142            → 重现"142% 看成 98%"的实测缺陷
❌ identifier 列直接渲染 12               → 重现"偏差放大 3.1 亿倍"的实测缺陷
```

### 4.7.5 ExperimentGrid · 实验矩阵格（**P2，2026-09-27 已实现**）

**功能说明**：渲染「算例 × 因子」的批量实验网格与进度。

**为什么需要**：科研场景 8「批量算例扫描与数据集构建」—— 这是「任何研究」都需要的实验矩阵。

**三条约束及其落地方式**（`frontend/src/components/ExperimentGrid.tsx`）：

1. **进度必须可观测**，且**失败必须逐格可见**（不得只给一个总进度条）。
   → 每格一行、行内自带 `Signature` 状态；`failed` 的格子**在行内**给出失败步骤与引擎错误原文；
   总计数（"共 N 格 · 成功 X · 失败 Y"）只是**补充**，不是唯一信息。
   ⚠️ 未映射的网关状态**原样显示 + `unknown` 签名**（不猜、不静默当成功）。
2. **结果必须绑定 `cache_key`**（v4 §11.6），陈旧结果须标注"来自旧契约状态"。
   → 每行显式显示 `cache_key`；`never_run` 表示"当前 `cache_key` 无存档结果"；
   存档里对不上任何当前格子的记录由 `orphaned` 单独标注为**来自旧条件**，不与当前结果并列。
3. **执行模型为串行优先**（v4 §4.4 已裁决）；并发需先完成 §11.2 的并发隔离。
   → 界面**不做任何并发暗示**（无并行度/并发数控件），并如实写明"串行执行（不并发）"。

**已实现**：`ExperimentGrid` 组件 + ④ 实验矩阵视图（`views/ExperimentsView.tsx`）。
数据来自 `POST/GET /experiments` · `GET /experiments/{id}` · `POST /experiments/{id}/run` ·
`GET /experiments/{id}/results` · `GET /experiments/{id}/export?format=csv|md`。

⚠️ **两处诚实边界**（都在界面上写明，不静默）：
- 结果表是**格级对比表**；越限明细级的 `result_tables` 透视（模块列定义 / G-2 pivot）属 **P3**，未做。
- 行内只展示**前 4 项指标**（数值优先），其余以"共 N 项指标，见结果表"明示 —— 截断必须可见。

### 4.7.6 ModuleBadge · 模块徽章 + 槽位契约

**功能说明**：渲染一个选题模块的装配状态（id / name / kind / maturity / enabled / failures）。

**为什么需要**：模块机制（v4 §六）必须让用户看得见"哪些模块装上了、哪些坏了"。
**失败必须 fail-loud** —— 装配失败的模块不能被静默忽略。

**属性表**（字段与 `GET /modules` 一一对应）

| 属性 | 类型 | 必填 | 说明 |
|---|---|:--:|---|
| `id` / `name` | `string` | ✅ | |
| `kind` | `'research' \| 'engineering'` | ✅ | |
| `maturity` | `'L0' \| 'L1' \| 'L2'` | ✅ | 三层成熟度 |
| `enabled` | `boolean` | ✅ | 被显式禁用的模块**仍要显示**（禁用是正常状态） |
| `failure` | `{ error: string } \| null` | ✅ | 装配失败原因 |

**★ 两条硬规则**

1. **装配失败的模块必须显示**，且带上 `error` 原文 —— 否则用户会以为"这个模块不存在"。
2. **`enabled=false` 的模块仍要显示**（置灰）—— 禁用是**正常状态**，
   内核不依赖任何模块（自证条件）。

**槽位契约（模块注入 UI 的唯一入口）**

| 槽位 | 位置 | 内核保证 |
|---|---|---|
| `nav.extra` | 主导航 | 无模块时不占位；多模块按 `order` 排序 |
| `case.detail.tabs` | 算例详情 | 槽位容器由内核提供，内容由模块自带 |
| `chat.result.after` | 对话结果之后 | 同上 |
| `experiment.result.columns` | 实验结果表 | 同上 |
| `verification.extra` | 校验层 | 同上 |

> ⚠️ **槽位清单尚未冻结**（v4 §3.3）：须先由 **2 个真实模块**验证后再定。
> 本规范在此**只固定"槽位是内核提供的稳定锚点"这一契约**，不承诺上表为最终集合。

# 六、数据可视化规范

## 6.1 原则：图不是默认选择

方案 §1.2 的核心判断是 **「前端若只做图表就是重复劳动」**。因此本节的第一条规则是**图型选择判据**：

| 数据特征 | 应使用 | 理由 |
|---|---|---|
| 需要**逐位核对**的数值（电压、潮流、负载率） | **表格 + Quantity** | 图表无法精确读数 |
| 需要**判断一致/不一致**的少量数值 | **表格**（差异列高亮） | 一致性是布尔判断，不是趋势 |
| 跨多个引擎的**同一指标** | 分组柱状 或 表格 | 引擎数 9 时表格更清晰 |
| **时序**（QSTS 类） | 折线 / 面积 | 唯一真正需要图的场景 |
| **拓扑** | SVG 拓扑图 | P2 起 |
| **矩阵**（母线 × 时间） | 热力图 | P2 起 |

> **默认用表**。只有当数据的**形态本身**（趋势、分布、拓扑）才是信息时，才用图。

## 6.2 ECharts 主题

必须注册两套主题（`powermcp-light` / `powermcp-dark`），配色取自 `--c-chart-cat-1..9`。

| 项 | Light | Dark | 对应令牌 |
|---|---|---|---|
| 网格线 | `#DDE3EA` | `#2C3441` | `--c-chart-grid` |
| 坐标轴 | `#6B7686` | `#6B7686` | `--c-chart-axis` |
| 提示框底 | `#FFFFFF` | `#1A1F28` | `--c-surface-raised` |
| 提示框字 | `#12161D` | `#EDF1F6` | `--c-text-primary` |
| 字体 | `-apple-system, BlinkMacSystemFont, "PingFang SC", "Microsoft YaHei", "Noto Sans SC", "Segoe UI", Roboto, sans-serif` | 同左 | `--p-font-sans` |

## 6.3 Δ 值与一致性表达

> 📌 **范围说明**：跨引擎一致性视图是方案 §八 的 **P2** 交付物，本节属**前瞻规格**。
> 在 P1 中，Δ 只出现在 Tool Call 审计行（比较同一次调用在不同引擎下的往返值）。
> 提前写出是为了固定**表达方式**，避免 P2 实现时各行其是。

跨引擎对比时，**Δ 值必须显示**（方案 §4.3：这是 PowerIO IR 往返保真的证据，实测 `Δ = 6.98e-11 pu`）。

```
母线 8 电压   pandapower 1.0234567   PyPSA 1.0234567   Δ = 6.98e-11 pu   [✔ 满足]
```

- Δ 用 `<Quantity delta />` 渲染，**等宽**。
- **一致性判断不得只用颜色**：`[✔ 满足]` / `[✖ 违反]` 徽章必须同时给出。
- ⚠️ 方案 §4.3 的警示：**并发执行时结果到达顺序不确定**，必须靠**单调序列号**排序后再渲染，
  否则可能显示**错配的对比** —— 不报错、不变慢，**静默给出错误的一致性结论**。这是 P1 就需在数据层处理的约束，界面层无法补救。

## 6.4 导出（P3 交付，此处只固定约束）

导出 CSV / JSON 时，**导出内容必须包含契约快照**（方案 §11.6：`cache_entry = (结果, provenance, 契约快照)`）。
导出的表格若缺少契约状态列，则该导出**不可用于论文** —— 因为无法判断结果是在什么契约状态下产生的。

# 七、文案规范

## 7.1 中英混排

| 类别 | 规则 | 示例 |
|---|---|---|
| 工具名 / 参数名 | **保留原文**，等宽 | `run_power_flow` · `linearized` |
| 契约类型名 | 中文（按 §1.5 术语表 / `tokens.json#contractTypes` 的 8 类） | 参数契约 |
| 引擎名 | **保留原文** | pandapower · PyPSA · surge |
| 数值单位 | **保留国际符号** | MW · MVA · pu · kV |
| 句式 | 中文，中英文之间加空格 | 「改用 `pypsa` 支持的等价参数」 |

## 7.2 数字与单位书写

由 `Quantity` / `Identifier` 组件保证（§4.4 / §4.5），文案层面只需遵守：

- 百分比：`142.47%`，判据恒以 `(MVA 判据)` 形式紧随。
- 科学计数：`6.98e-11`（不用 `6.98×10⁻¹¹`，后者在等宽字体下易错位）。
- 编号：恒带约定后缀。
- **阈值必须写出**：说「超限」时同时给出限值与实测值，如 `45.59 / 32.0 MVA`。

## 7.3 契约告警文案模板

**四要素固定顺序**（方案 §4.2），每条**不得省略**：

```
涉及：{server} · 契约 {N}（{类型名}）
证据：{实测现象，可复现}
影响：{对结论的后果}
建议：{可执行动作}
```

**影响面预评估文案**（方案 §11.5(b)）—— 危险操作确认时，**替代通用弹窗**：

> 📌 **范围说明**：影响面预评估组件本身是方案 §八 的 **P3** 交付物。
> 此处只固定**文案形态**，因为它的写法（必须给出具体后果）与 P1 的契约告警文案同源，**早定早一致**。

```
❌ 通用弹窗：  "确定要执行该修改吗？"                       → 用户无脑点确认
✅ 影响面提示："将断开支路 12 (0-based)（端点 9–11），
              导致母线 8 失负荷 30 MW（全网最大负荷点），
              唯一备用通路 8–28 额定仅 32 MVA。"
```

> 注意上例中 `12 (0-based)` 与 `30 MW` / `32 MVA` 的写法 —— 这不是文案习惯，是 §4.4 / §4.5 两个组件在文案层的必然产物。

## 7.4 每次 LLM 回答的结尾（★ v2 改为**可选**）

> **★ v2 修订（定位级）**：v4 §7.3 规则 3 已把「每次 LLM 回答末尾附契约摘要」
> 从**必须**改为**可选**（默认关闭，可在校验层开启）。
> 理由：v1.x 的强制摘要会让**每一次回答**都带上契约视角 —— 那是"审计器"的定位。
> **但一旦开启，下面四条全部适用**，一条都不能少。

开启时的格式（方案 v4 §7.3 规则 3 的原文格式）：

```
本次分析：契约 ✔5 ▲2 ✖0 ?0 !0   [查看校验层]
```

> ⚠️ **三处与方案原文的差异**（均已记入附录 B.3）：
> ① 符号：方案原文用 `✅5 ⚠️2 ❌0`，本规范改用 `✔ ▲ ✖`（理由见 B.3 #2）；
> ② **新增 `?` 计数**：方案原文只有三态，但本规范是四态（B.3 #1）；
> ③ **新增 `!` 计数**：事故性未知单独计数（v1.2，§3.8.2）。

- **五签名全列**，**即使为 0 也要显示**（`✔0` / `▲0` / `✖0` / `?0` / `!0` 五项恒在）。
- `!n` 非 0 时**整条摘要使用 `incident` 签名着色并加粗** —— 事故不能在摘要里被平铺成第四个数字。
- 可点击跳转**校验层**（v1.x 写的是"契约面板"）。
- **关闭时不得渲染任何契约字样** —— 包括不得渲染成 `✔0 ▲0 ✖0` 这类"空摘要"。

> **★ 为什么"关闭"必须彻底**：`✔0 ▲0 ✖0` 看起来是「检查过且一切正常」，
> 而实际是「**没检查**」。半开的摘要比不显示更危险 —— 它给出**虚假的安心**。
> 这正是 P5 禁止的静默 fail-open 的又一形态。

## 8.4 ★ SSE 数据边界运行时校验（强制）

> **本条是可执行约束，不是建议。** 它是 P3 逃逸分析中「`JSON.parse` 的 `any`」那一条的**闭合手段**。

### 问题

前端有一条**类型系统够不着**的数据入口：SSE 长连接。

```ts
// 后端推来一个事件
const evt = JSON.parse(raw);        // evt: any
<ContractBadge state={evt.state} /> // ✅ 编译通过 —— 哪怕 evt.state 是 undefined
```

`JSON.parse` 返回 `any`，**所有编译期守卫在运行时全部穿透**。而 SSE 是长连接流式推送，
网关层任何微小漂移都会直达 React 状态树：

| 漂移 | 后果 |
|---|---|
| 后端发 `server_id`，前端读 `server` | 取到 `undefined` → 引擎名渲染为空 |
| `contracts` 字段被序列化为 `null` | `.map()` 抛 `TypeError` → **整棵子树崩溃（White Screen）** |
| 枚举值多加一个（如 `state: 'stale'`） | 签名表查不到 → 渲染 `undefined` 图标 |
| 事件 `type` 是前端不认识的 | 未处理分支 → 静默丢弃或崩溃 |

**长连接的特殊性**：这些事件是**陆续到达**的，一次格式漂移会在整个会话期间反复触发；
而白屏发生的那一刻，用户正在看的那屏审计证据也一起没了。

### 规则

**① 唯一入站通道**

所有 SSE 事件必须经 `fetch-event-source` / TanStack Query 的**适配层**统一入口，
**先过 `safeParse`，再进入任何 React 状态**：

```ts
import { z } from 'zod';   // 或 valibot，二者皆可

// 事件信封 —— 判别联合；未知 type 必须走失败分支，不得崩溃
const ContractHitSchema = z.discriminatedUnion('state', [
  z.object({ type: z.number().int().min(1).max(8),
             state: z.enum(['satisfied', 'degraded', 'violated']),
             arg: z.string().optional(), note: z.string().optional() }),
  z.object({ type: z.number().int().min(1).max(8),
             state: z.literal('unknown'),
             reason: z.enum(['structural', 'incident']),   // ★ 必填，不给默认
             arg: z.string().optional(), note: z.string().optional() }),
]);

const ToolCallEventSchema = z.object({
  type: z.literal('tool_call'),
  callId: z.string(),
  serverId: z.string(),                 // ★ 与 registry.py 的 server id 一致
  tool: z.string(),
  args: z.record(z.unknown()),
  contracts: z.array(ContractHitSchema),
});

const SseEventSchema = z.discriminatedUnion('type', [
  ToolCallEventSchema,
  ContractStateEventSchema,
  EngineStatusEventSchema,
]);
```

```ts
// 适配层 —— 唯一允许消费原始事件的地方
function onMessage(raw: string) {
  const parsed = SseEventSchema.safeParse(JSON.parse(raw));

  if (!parsed.success) {
    // ❌ 绝不 throw（会炸掉整个流）；❌ 绝不静默丢弃（等于 fail-open）
    audit.append({ kind: 'sse_schema_violation', raw, issues: parsed.error.issues });
    store.pushUnknown({ reason: 'incident', source: parsed.error });  // ✅ 降级为事故未知
    return;
  }
  store.push(parsed.data);          // ✅ 此后类型才是可信的
}
```

**② 只有通过校验的数据才允许进入 `measure()`**

`measure()`（§4.4）的入参类型**必须是 Zod schema 的推断输出**，而不是手写 interface：

```ts
type ToolCallEvent = z.infer<typeof ToolCallEventSchema>;
// measure 只接受来自 schema 的字段
export function measure(raw: ToolCallEvent['args'][string], spec: UnitSpec, source: string): Measured;
```

这样"schema 改了但接口没改"这类漂移会被编译器挡住 —— **把运行时契约与编译期类型绑到同一处**。

**③ 解析失败一律降级为 `incident`，不得降级为 `structural`**

| 失败类型 | 归因 | 理由 |
|---|---|---|
| SSE schema 校验失败 | **`incident`** | 含义是「网关给的东西不符合契约，我们不知道发生了什么」—— 这是本可判定却拿不到，**且必须升级为主徽章**（§3.8.2） |
| 引擎能力本身给不出判定（契约 4） | `structural` | 长期、已知、无信息量 |

> 这条分工很重要：**边界失败不能混进结构性未知**，否则会被"钝刀子"淹没 ——
> 而那恰恰是改动 2 要解决的问题。边界失败按定义就是事故。

### 反例

```tsx
// ✖ 反例 1：直接消费 JSON.parse 的结果
const evt = JSON.parse(raw);
if (evt.type === 'tool_call') { /* evt 仍是 any —— 守卫是幻觉 */ }

// ✖ 反例 2：用 as 断言代替校验
const evt = JSON.parse(raw) as ToolCallEvent;   // 编译通过，运行时照样炸

// ✖ 反例 3：校验失败时静默丢弃
if (!parsed.success) return;                     // 等于 fail-open
```

### 与方案的关系

方案 §2.3 规定「契约求值不得出现在 tool call 的返回路径上」、SSE **双通道**（A 证据不可丢 / B 遥测可丢）。
**本节的 schema 校验属于通道 A 的处理链**：校验失败事件必须**入审计**，不可随遥测丢弃 ——
否则「网关发了不合规数据」这件事会连痕迹都不留。

### ★ v2 补充：新增端点的入站边界

v1.x 的边界校验只覆盖 SSE（契约事件）。v4 之后前端有**更多 JSON 入站口**，
它们**同样绕不过 `any`**，必须逐个建 schema：

| 端点 | 关键判别联合 / 必填字段 | 特别要求 |
|---|---|---|
| `GET /environment` | `server_env.will_pass` | **`llm.endpoint` 只含 `scheme://host`**；schema 里**不得出现 `api_key` 字段**（服务端已不返回，前端也不许加） |
| `GET /skills` | `kind: 'tool' \| 'engineering' \| 'meta'`；`health.level` | `health.level` 用**字面量 `'unknown'`** 而非 enum —— 若后端将来开始给 `ok`，编译期就报错，强迫我们同步界面 |
| `GET /modules` | `maturity: 'L0' \| 'L1' \| 'L2'`；`enabled: boolean`；`failure: { error } \| null` | 装配失败**必须能渲染**（fail-loud），故 `failure` 为必填（可为 `null`） |
| `GET /cases` | `available` / `drift` / `withinAllowedRoots` 均为必填 `boolean` | 三者**不得给默认值** —— 缺任何一个都说明后端漂移了，必须走失败分支 |
| `GET /cases/{id}/ir` | `irParsed: boolean`；`ir: unknown` | `irParsed=false` 时 `ir` 是**字符串**，界面须**原样展示**（不得假装解析成功） |
| `POST /sessions/{sid}/chat` 的 SSE | `event:` 名 ∈ {`text` `notice` `tool_call` `tool_error` `final` `error`} | **白名单**：未知 `event` 名走失败分支并报 `incident`，不得静默丢弃 |

> ★ **为什么 `available` / `drift` / `withinAllowedRoots` 必须必填且无默认值**：
> 它们是「文件还在不在、有没有变、server 读不读得到」的**现算**结论。
> 给默认值（如 `available ?? true`）会把"不知道"渲染成"没问题" ——
> 与 §4.7.2 硬规则 1 直接冲突，也正是 P5 禁止的静默 fail-open。

> ★ **为什么未知的 `event:` 名要报 `incident` 而不是丢弃**：v4 §4.3 的对话流有**白名单**
> （`_CHAT_EVENT_KINDS`）。若后端新增了一个事件名而前端不认识，丢弃等于**看不见的降级**；
> 报 `incident` 则会把"界面落后于后端"这件事暴露出来 —— 这正是"事故性未知"的定义。

**① §8.4（新增）SSE 数据边界运行时校验（强制）**
- 问题：`JSON.parse` 返回 `any`，**编译期守卫在运行时全部穿透**。SSE 是长连接流式推送，网关字段漂移（`server_id` vs `server`、`contracts` 为 `null`）会直达 React 状态树 → **白屏**，且每次漂移在整个会话反复触发
- 规则：所有入站事件必须经适配层 `safeParse`（Zod / Valibot）后才允许进入状态树与 `measure()`；`measure()` 的入参类型改为 `z.infer` 的输出，**把运行时契约与编译期类型绑到同一处**
- **失败一律降级为 `incident`，并入审计（通道 A，不可丢）**；禁止 `throw`（炸掉整个流）与静默丢弃（等于 fail-open）
- 效果：P3 逃逸表中「`JSON.parse` 的 `any`」一条**标记为已闭合**

**② 未知态两分 + 双轨汇总 —— 解决"Alert Fatigue by Design"**
- 问题：方案 §11.1 已接受契约 4 长期 `unknown`。原设计用**单一标量** `violated > unknown > degraded > satisfied` 汇总 → 几乎所有审计行常年挂问号 → 工程师免疫、不再下钻 → **真正偶发的契约 3 参数降级被"钝刀子"淹没**
- 根因：单标量试图同时表达**"多严重"与"多可信"两个正交维度**，硬塞进一个全序必然牺牲一边
- 解法：`unknown` 按成因分 `structural`（引擎级、常态、不升级）/ `incident`（本可判定却拿不到、**必须升级**）；
  汇总改为**双轨** —— 主徽章（已知告警最差值）+ 次级标记 `+?N`（结构性未知计数）
- 新增第 5 个签名 `incident` / `!` / 事故 + 对应双主题色（violet 族，与 violated 的红区分）
