## 一、设计前提

### 1.1 目标与定位

**目标**：一个**通用**的电力系统研究工作台 —— 直观、方便地用 PowerMCP（9 引擎 / 117 工具）与
PowerSkills（21 技能）支撑**任意方向**的电力研究。

研究者的 **6 类活动**（依据 13 步全流程与 20 个场景归纳，是 v4 全部设计的出发点）：

| # | 活动 | 对应 13 步 | 对应场景 |
|---|---|---|---|
| A | 确认**能跑什么** | 1–3 环境就绪 | 前置条件检查清单 |
| B | 把算例变成**可信的统一表示** | 4–5 算例解析 | 科研 4 · 工程 3 |
| C | **提问并拿到结果** | 6–12 | 科研 1/2/3/5/6/7 · 工程 1/4/5/6/7 |
| D | **批量跑并沉淀数据** | — | 科研 8（39/118/300 × 负荷水平 × 故障集） |
| E | 知道**遇到问题该用什么方法** | 10–12 | 10 个缓解手册 + Escalation triggers |
| F | **留痕与产出** | 13 归档 | 全部 |

### 1.2 与 v3 的关系

| 维度 | v1–v3 | **v4** |
|---|---|---|
| 第一公民 | 契约状态 | **研究流程** |
| 契约的角色 | 主界面中心对象（占 5 视图中的 4 个） | **可开关的校验覆盖层**（默认开、折叠为状态条） |
| PowerSkills | **未覆盖**（UI 规范 0 次提及；方案 1 次且仅作契约比对对象） | **一等公民**（§4.5 技能手册） |
| 与论文关系 | 绑定的交付载体 | **解绑**（2026-09-25 张老师裁决） |
| 扩展方式 | 改方案、改内核 | **加模块**（§六） |

> **v3 的工程约束绝大多数继续有效**，v4 只改**定位与信息架构**，不改工程判据。
> 逐条对照见 [重定位提案 §五](PowerMCP_前端方案重定位提案.md)。

### 1.4 为什么不能照搬 Grid-Orch

| 维度 | Grid-Orch | **PowerMCP（开源版）** |
|---|---|---|
| 引擎数 | **1**（OpenDSS） | **9** |
| 工具数 | 36 | **117**（8 个已挂载 server 实测；OpenDSS 未计入） |
| 数据层 | 单一引擎原生 | **PowerIO IR gen 2**（跨引擎交换格式） |
| 核心难题 | 单引擎内"自然语言 → 工具调用" | **跨引擎的契约一致性**（8 类，已实测） |
| 部署形态 | 多租户 Web 平台 | `pip install powermcp` 的**本地工具** |

**关键差异**：Grid-Orch 的仪表盘全部围绕**单一引擎的物理量**，这类分析现有 LLM 客户端已能做。

> **v4 的核心命题**：前端的价值不在「又一个图表工具」，而在**把「研究流程」显式化** ——
> 环境就绪、算例组织、批量实验、方法手册、结果留痕。
> **契约状态是其中「结果可不可信」这一环的呈现**，而非全部。

### 1.5 范围收窄的代价评估

放弃商业软件**不削弱契约研究的基础** —— 8 类契约的实测证据里，**7 条完全来自开源引擎**：

| 契约 | 实测证据 | 来源引擎 | 收窄后 |
|---|---|---|---|
| API 版本 | `net.deepcopy()` / `Network.status` / `mremove()` | pandapower · PyPSA | ✅ 保留 |
| 文档-实现一致性 | opendss 工具名与文档不符（**待挂载后核验**） | OpenDSS | ⚠️ 待核验 |
| 参数 | PyPSA `linearized` 静默忽略 | PyPSA | ✅ 保留 |
| 状态映射 | pypsa N-1 脚本求解成功却报「未收敛」 | PyPSA | ✅ 保留 |
| 命名空间 | `load_network` / `add_bus` / `run_contingency_analysis` 等重名 | **pandapower · PyPSA · surge** | ✅ 保留 |
| 标识符 | 0-based vs 1-based | pandapower · PyPSA | ✅ 保留 |
| 量纲 | 142% 误判为 98% | 开源 | ✅ 保留 |
| 运行时依赖（v3 重新定义） | **Egret 的 Ipopt 不可用** / surge 要求 Python 3.12–3.14 | Egret · surge | ✅ 保留 |

**命名空间契约的证据在收窄后反而更强** —— 重名全部发生在**开源引擎之间**（本次实测确认）：
`load_network`（pandapower · PyPSA · surge 三者同名）、`add_bus` / `add_generator` / `add_line` / `add_load`（PyPSA · surge）、
`create_empty_network`（pandapower · surge）、`run_power_flow`（pandapower · PyPSA · ANDES）、
`run_contingency_analysis`（pandapower · PyPSA）、`get_network_info`（pandapower · PyPSA · surge）。

> ✅ **结论**：契约研究的实验基础**不依赖商业软件**。
> ⚠️ 但**能力覆盖**有真实缺口，见 §5.3 与 §十四-2。

## 二、架构设计

### 2.1 四层结构

```
┌─────────────────────────────────────────────────────────────┐
│  Layer 3  选题模块 Modules（可插拔 · 一个选题 = 一个模块）      │
│  N-1 排序 · 配网承载力 · …（声明式 manifest + 可选组件）        │
└───────────────────────────┬─────────────────────────────────┘
                            │ 四类扩展点（装配 / 数据 / 视图 / 交付）
┌───────────────────────────▼─────────────────────────────────┐
│  Layer 2  内核 Kernel（新增 · 不含任何领域知识）                │
│  环境就绪 · 算例库 · 对话分析 · 实验矩阵 · 技能手册 · 校验层      │
│  ── 对外只暴露版本化的 kernel.* 接口                          │
└───────────────────────────┬─────────────────────────────────┘
                            │ REST + SSE（双通道，见 §2.6）
┌───────────────────────────▼─────────────────────────────────┐
│  Layer 1  Gateway / Orchestrator                              │
│  ✅ 已交付（子项目 2/3）：MCP Client（stdio）· 契约引擎 ·        │
│     会话 / SSE 双通道 / NDJSON 审计                            │
│  ✅ 已交付（2026-09-25 · P0-1）：LLM Provider Adapter +        │
│     Agent 循环 + POST /sessions/{sid}/chat                    │
│  ⏳ 待建：进程监管（心跳 / 重启 / 熔断）★ 见 §11.3               │
└───────────────────────────┬─────────────────────────────────┘
                            │ MCP (stdio)
┌───────────────────────────▼─────────────────────────────────┐
│  Layer 0  开源 MCP Servers × 9（零改动）                       │
│  pandapower · PyPSA · PowerIO · ANDES · Egret · OpenDSS ·     │
│  surge · HOPE · GenX                                          │
└─────────────────────────────────────────────────────────────┘
```

**硬约束**：
- Layer 0 **一行不改**（继承 PowerMCP 既有的 *zero source mutation* 哲学）。
- **Layer 3 不得访问 Layer 0/1**，不得写 `~/.powermcp/`，不得 import 内核内部模块（§6.4）。

> **v3 → v4 的结构变化**：v3 是三层（Server / Gateway / Web UI）。v4 把原「Web UI」层**一分为二** ——
> **内核**（稳定、与选题无关）与**模块**（可插拔、承载选题）。

### 2.2 内核六模块

内核承载 §1.1 的 6 类活动，**不得包含任何领域知识**：

| 内核模块 | 职责 | 视图 |
|---|---|---|
| `env` | server / 引擎 / 求解器 / 依赖 / 路径围笼 | §4.1 环境就绪 |
| `cases` | 算例登记 · 解析 · 诊断 · 版本 | §4.2 算例库 |
| `chat` | 会话 · 工具轨迹 · 结果呈现 | §4.3 对话分析 |
| `experiments` | 参数网格 · 队列 · 结果表 · 导出 | §4.4 实验矩阵 |
| `skills` | 技能索引 · Escalation triggers | §4.5 技能手册 |
| `verification` | 8 类契约 · 跨引擎一致性 · 能力矩阵 | §五 校验层 |

**★ 自证条件**：**禁用全部模块后内核仍可用**。若禁用模块内核即不可用，说明内核被领域知识污染了 ——
这是「内核稳定」从口号变成可检验判据的方式。

### 2.3 选题模块（摘要）

**一个选题 = 一个模块**。模块通过四类扩展点接入内核：

| 扩展点 | 内容 | 需要写代码？ |
|---|---|---|
| **装配** | `servers` / `tools` / `skills` / `solvers` / `prompts` / `checks` / `exports` | ❌ 仅 YAML |
| **数据** | `entities` / `result_tables` / `metrics` → 内核**自动渲染**成表与图 | ❌ 仅 JSON Schema |
| **视图** | `nav.extra` + 4 个槽位（§3.3） | ✅ React 组件 |
| **交付** | `exports`（报告模板）/ `datasets` | ❌ 仅模板文件 |

**★ 三层成熟度（可降级）** —— 这是「按需加入 UI 组件」能够成立的关键：

| 层 | 模块需提供 | 成本 | 占比 |
|---|---|---|---|
| **L0 声明式** | 仅 `module.yaml` | 极低 | **多数选题** |
| **L1 数据式** | + 实体 / 结果表 schema | 低 | 部分 |
| **L2 组件式** | + React 组件 | 高 | 少数 |

> **完整设计见 [前端模块化架构](PowerMCP_前端模块化架构.md)**；本文 §六 只给摘要与边界。

### 2.4 ★ 契约引擎（Contract Engine）

| # | 契约类型 | 检测手段 | 节拍 | 输出状态 |
|---:|---|---|:--:|---|
| 1 | API 版本契约 | 比对 `list_tools` 实际返回 vs 工具实现调用的 API | **T0** | ✅ / ❌ |
| 2 | 文档-实现一致性 | 比对 `SKILL.md`/README 声明 vs `list_tools` 实际 | **T0** | ✅ / ⚠️ / ❌ |
| 3 | 参数契约 | ★ **声明 schema 差分**（非行为探测，见 §2.5） | **T2** | ✅ / ⚠️ |
| 4 | 状态映射契约 | 求解器返回码 vs 引擎实际状态 | **T2** | ✅ / ⚠️ |
| 5 | 命名空间契约 | 跨 server 同名工具做语义指纹比对 | **T0** | ✅ / ⚠️ |
| 6 | 标识符契约 | 校验 0-based / 1-based 约定并归一 | **T0** | ✅ / ⚠️ |
| 7 | 量纲契约 | 校验过载判据等单位的 MVA/MW 一致性 | **T0** | ✅ / ❌ |
| 8 | **运行时依赖契约** | 校验引擎的外部运行时依赖是否就绪 | **T1** | ✅ / ⚠️ / ❌ |

**状态四态**：`satisfied`（满足）· `degraded`（降级可用）· `violated`（违反）· `unknown`（无法判定）
- `unknown` **必须**带 `reason: 'structural' | 'incident'`
- 汇总优先级：`incident > violated > degraded > satisfied`；**结构性未知不参与主徽标竞争**

> ⚠️ **契约 3 在事件流上有两个 `kind`**（`contract_violation` / `contract_unknown`），
> payload 同为 `ContractFinding` 同形。前端 Zod 入站边界须**按 `kind` 分派、按 `state` 汇入双轨汇总**。

**v4 变更**：契约引擎的求值结果**仍必须与 LLM 的回答解耦**，但呈现方式由「主界面中心对象」
改为「**可开关的校验层**」（§五）。

**已交付状态**：契约 1 / 2 / 4 / 5 / 6 / 7 已注册进 `REGISTRY`；契约 3 为事件驱动（不注册）；
契约 8 属 T1，未实现。

### 2.5 契约求值的三级节拍（性能硬约束）

| 级 | 触发时机 | 覆盖契约 | 成本量级 | 缓存策略 |
|:--:|---|---|---|---|
| **T0 静态** | 启动时 / server 版本变更时，**一次** | 1, 2, 5, 6, 7 | 纯本地计算，毫秒级 | 按 `(server, 版本)` 持久缓存 |
| **T1 会话级** | 会话开始 / server 组合变更 | 8（运行时依赖探测） | 可能秒级（需拉起引擎 / 探测 Julia） | 会话内复用；**绝不逐调用** |
| **T2 逐调用** | 每次 tool call | 3, 4 | **必须 O(1)** | 无缓存需求 |

**T2 契约 3 的正确实现——不做行为探测**：PyPSA `linearized` 案例的本质是
**声明的 `inputSchema` 与实际函数签名不一致**，可静态差分检出：

```
declared = list_tools() 返回的 inputSchema.properties
actual   = inspect.signature(工具实现函数).parameters
diff     → 声明了但实现不接收的参数 = 静默忽略风险
```

**TTFT / RTT 不变量（硬约束）**：

> **契约求值不得出现在 tool call 的返回路径上。** 工具结果先返回；契约状态作为**旁路事件**异步推送。

### 2.6 SSE 背压与通道分级（硬约束）

| 通道 | 内容 | 背压策略 |
|---|---|---|
| **A 证据通道** | 审计证据（调用记录、契约判定、edits 轨迹） | **不可丢弃**；落盘队列 + 批量 fsync |
| **B 遥测通道** | UI 装饰态（进度、临时状态） | **可丢弃**；合并 / 降采样 |

> ⚠️ 二者**必须物理分离**。**审计一旦可丢，审计就不可信**，校验层全部结论随之失效。

**★ 记录与投递解耦（已交付）**：`publish` **不再因满队列拒绝** —— 记录永远先发生，
滞后订阅者被标记并计数（`lagged_queues` 现状量 / `lagged_deliveries` 累计量），
由历史重放兜底。这是子项目 3 收尾审查的 I-2 修复，**v4 继续依赖该不变式**。

### 2.7 并发隔离与命名空间

`runs_dir(tool)` 目前是 **per-tool**（`~/.powermcp/runs/<tool>`），非 per-session / per-case。目标命名空间：


**★ v4 优先级变更**：§11.2 的并发隔离措施**从 P2 提升为实验矩阵（§4.4）的前置条件** ——
批量参数扫描必然并发，而全仓**无任何锁机制**。

### 4.2 ② 算例库

| 要素 | 设计 |
|---|---|
| **算例登记** | 路径 / 格式 / 来源 / 标签 / 版本 hash |
| **解析** | → PowerIO IR（跨引擎统一表示） |
| **诊断** | `diagnostics` 按 `severity` 排序；`fidelity` 徽章（`exact_same_format` / `canonical`） |
| **摘要** | 母线 / 支路 / 机组 / 负荷计数 + 基态体检 |
| **下钻** | 每次解析的原始工具调用可追溯 |

**★ v4 引入的新一级实体**：v3 只有 session 粒度，研究无法「组织」——
你无法说「这是 case39 那组实验」。算例库是 §4.4 实验矩阵的**主语**。

**数据来源**：**`GET /cases` · `POST /cases` · `GET /cases/{id}` · `DELETE /cases/{id}`**
（✅ 2026-09-25 交付 —— 登记 / 列举 / 详情 / 注销；**索引为可读 JSON + 原子替换**，见 §11.4）。
**`POST /cases/{id}/parse` · `GET /cases/{id}/ir` · `GET /cases/{id}/diagnostics`**
（✅ 2026-09-25 交付 —— 解析为 PowerIO IR 并落盘；产物记 `source_sha256`，源文件改动即报 `stale`）。

> ★ **PowerIO 的返回值是双层编码**（实测）：`parse` 的文本是 JSON，其 `powerio_ir` 字段
> **又是一个 JSON 字符串**。故产物**原样保存该字符串**，任何"顺手解析一下"都会让
> `diagnostics` 拿到错的东西。缺该字段即报 502 并指明"上游形态可能已变"。
> ⚠️ `POST .../parse` **会真实拉起 powerio**（秒级）且**每次重新解析**；
> 响应**不内联 IR**（约 60KB），IR 走 `GET .../ir`。
> ⚠️ **前置条件显式检查**：源文件不在 `POWERIO_MCP_ALLOWED_ROOTS` 内时返回 409
> 并**指出该把哪个目录加进去** —— 而不是让用户看一个看不懂的沙箱错误。

**三个关键设计决定**：
1. **按路径引用，不复制文件** —— 算例就是你的那个文件；复制会在数据旁悄悄多出一份，
   且你改了原文件而库里还是旧的（**静默不一致**）。代价是"可复现依赖源文件在位"，
   故**登记时记录 sha256、读取时现算比对**，把 `drift` 显式报出来。
2. **`DELETE` 只注销登记，绝不删除源文件** —— 一个 HTTP 动词不该能删掉磁盘上的算例。
3. **`within_allowed_roots` 必须现算且与 `config.server_env()` 同源** ——
   否则会声称"可读"而 server 实际读不到（本会话实测过的正是这类"设了不生效"的坑）。

⚠️ **已知限制（必须显示）**：
- IR → PyPSA 导入**不携带** `q_min_pu` / `q_max_pu`（无功能力限值）
- 中文标准算例 **CSEE-FS 解析失败**（§十四-8）
- `Package` / `model-json` / `package_json` / `study_commit` 为**已退役格式**，需重新 parse 原算例

**硬约束**：算例库存储于**独立目录** `~/.powermcp_gateway/cases/`，
**不写进 `~/.powermcp/runs/`**（严守 `PowerMCP/` 0 行改动）。
✅ **2026-09-25 已实测确认**：不需要改动 `PowerMCP/` 一行 ——
网关只是把 `POWERIO_MCP_ALLOWED_ROOTS` **透传**给 server 子进程（见 §4.1 与 §十一）。
⚠️ 由此暴露并修复了一个真缺陷：MCP SDK 只继承**白名单**环境变量，
`POWERIO_MCP_ALLOWED_ROOTS` 与 `HIGHS_LIB_DIR` **都不在其中** ——
不显式传就等于"父进程设了也不生效"，路径围笼形同虚设。

- 单元格**可点击下钻**：显示探测依据（`powermcp doctor` 输出）
- `⚠️` / `❌` 必须给出**可执行修复路径**（安装 Julia / 换求解器 / 调整 Python 版本）
- 复用现有 `powermcp doctor` 探测逻辑，**不新增探测机制**

### 5.4 IR 检查器

| 字段 | 展示方式 |
|---|---|
| `value_type` | 标签（被选中的 PowerIO 结构类型） |
| `selection` | 树形展开 |
| `diagnostics` | 列表，按 `severity` 排序；含 `code` / `target` / `spans` / `suggested action` |
| `fidelity` | 徽章：`exact_same_format`（回显原始字节）/ `canonical`（新生成） |
| `edits` | ★ **编辑轨迹时间线**（12 种 typed ops；连续同类更新作为**原子批**） |
| `warnings` | 折叠列表 |

**数据来源**：`GET /cases/{id}/ir`（✅ 2026-09-25 交付）—— 返回 `ir`（已解析对象）、
`ir_parsed`（解析失败时为 `false` 并**原样给字符串**，不假装成功）、`value_type`、
`parsed_at`、`ir_bytes`。

> ⚠️ **危险 edits 需影响面预评估**，不能直接执行。见 §11.5

### 6.3 装配与冲突规则

| 项 | 规则 |
|---|---|
| 扫描 | 启动时扫描 `modules/*/module.yaml` |

## 十一、工程加固设计

### 11.1 性能：契约求值的延迟与竞态

**缓解措施**：
1. **三级节拍**（§2.5）—— T0/T1 不落在调用路径上，只有契约 3/4 逐调用且为 O(1)
2. **契约 3 改静态 schema 差分** —— 微秒级，无需行为探测
3. **TTFT 不变量** —— 契约求值不得出现在返回路径上
4. **SSE 双通道** —— 证据不可丢、遥测可丢，物理分离

**残余风险**：T2 契约 4 需读引擎返回码，若返回码语义不明则需额外探测。
→ 处理：**降级为"未知"态而非阻塞**。

### 11.2 并发隔离：既有沙箱的边界与扩展

**★ v4 优先级：从 P2 提升为实验矩阵（§4.4）的前置条件。**

**既有实现（已核实）**：

| 机制 | 位置 | 覆盖范围 | 缺口 |
|---|---|---|---|
| 路径包含 | `powermcp/sandbox.py`（re-export `powerio.mcp.sandbox`） | `POWERIO_MCP_ALLOWED_ROOTS`；**解析 symlink 与 `..` 后比对真实目标** | 只防**越界**，不防**同名** |
| 单文件原子安装 | `staged_file_write` | `overwrite=False` 硬链接**不覆盖并发创建的目标**；`overwrite=True` 用 `os.replace` | **单文件 ≠ 多文件事务** |
| per-tool 运行目录 | `paths.runs_dir(tool)` = `~/.powermcp/runs/<tool>` | 按**工具**隔离 | ⚠️ **非 per-session / per-case** |
| Egret 写入 | `tempfile.mkstemp(prefix="egret_case_")` | 天然唯一名，**碰撞安全** | — |
| ANDES 写入 | `os.path.join(runs_dir("andes"), name)` | 按名字拼路径 | ⚠️ 与 Egret **不一致** |
| 锁机制 | 全仓检索 | PowerMCP **自身代码 0 命中**（仅 `.venv` 第三方库） | ⚠️ **无任何序列化** |

**★ 诊断**：

> 既有沙箱解决的是 **「安全」（防路径穿越）+「文件级原子性」**；
> 而问题是 **「并发隔离」+「事务性」**。
> **两个不同层次，不能靠同一机制解决** → 修法是**扩展现有机制的 scoping**，不是新建沙箱。

**设计方案**：

| # | 措施 | 说明 |
|---:|---|---|
| 1 | **命名空间加 session 维度** | `runs_dir` 升级为 `~/.powermcp/runs/<session_id>/<tool>/<case_hash>/` |
| 2 | **租约锁** | 每 `(engine, case_hash)` 一把；本地 `fcntl` / `portalocker`，跨机文件租约 |
| 3 | **工作流级事务** | 产物写 staging；整体成功才 `os.replace` 提交；失败丢弃 staging |
| 4 | **引擎实例串行化** | 单实例 + 请求队列；跨机每容器一实例 + 负载均衡 |
| 5 | **统一写入方式** | 把 ANDES 等按名字拼路径的写法统一到 `mkstemp` / `staged_*_write` |

**残余风险**：`ALLOWED_ROOTS` 检查**无法阻止另一进程在验证后替换路径**（PowerIO 源码已自陈）。
→ 租约锁 + 事务提交可缓解，**不可宣称完全消除**。

### 11.3 进程生命周期：心跳、重启、熔断

| 类型 | 引擎 | 管理要点 |
|---|---|---|
| **Julia 子进程** | HOPE · GenX | 启动慢、内存占用高；需独立超时与回收策略 |
| Python 子进程 | 其余 7 个 | 常规 stdio 管理 |

| 措施 | 设计 |
|---|---|
| **心跳** | MCP 有 `ping`；网关侧**主动周期轮询**，不能只依赖被动读超时 |
| **自动重启** | 指数退避 + 上限；**重启后必须重新求值 T0/T1 契约**（进程换了，版本可能变） |
| **熔断** | 连续 N 次失败 → 打开熔断 → **直接驱动能力矩阵降级**（与 `doctor` 同源） |
| **主动回收** | Julia 子进程启动慢且占内存 → 按**空闲时长**回收（而非等它崩）；阈值按引擎分别标定 |

**★ 失败语义（关键设计决策）**：

| 组件 | 失败策略 | 理由 |
|---|---|---|
| 引擎进程崩溃 | **fail-closed** | 该引擎标记不可用，调用直接拒绝。不得返回可疑结果 |
| 契约引擎崩溃 | **fail-loud but non-blocking** | 不阻塞调用，但界面明确标注"**契约状态未知**"，且未知态入审计 |

> ❌ **绝不允许契约引擎静默 fail-open** —— 那会退化成"没有契约引擎"，
> 用户以为有保护实际没有，**比明确的故障更危险**。

**v4 追加**：**模块装配失败**同样 **fail-loud** —— 标记该模块不可用并在环境视图显示，
**不影响内核与其他模块**（§6.3）。

### 11.4 审计存储：NDJSON + SQLite WAL 分离

**WAL 是必要不充分的**：WAL 允许单写多读，但**写仍串行**；高频审计写入依然争用。

| 数据 | 存储 | 理由 |
|---|---|---|
| **审计证据流**（append-only 事件） | **NDJSON 追加文件** | OS 保证小写入的 append 原子性；**无跨写者锁争用** |
| **会话元数据**（需查询 / 事务） | SQLite **WAL** | 需要索引与事务语义 |
| **算例元数据**（v4 新增） | **JSON + 原子替换**（`cases.json`） | ★ **有意偏离原「SQLite WAL」**：本地单用户、量级为几十到几百条，JSON 可读、可 diff、可手工核对；SQLite 会引入连接/迁移/锁开销与不可读的二进制。量级或并发真需要时再换，届时 `CaseStore` 接口不变 |

补充：**单写线程 + 内存环形缓冲**批量 flush；背压按 §2.6 通道分级；审计文件按会话切分。

**★ 已交付的审计降级可观测性**：`AuditLog.append()` 返回 `bool`，失败计数 `append_failures` +
`last_error` + `logger.error`（**不抛**）；`stats()` 经 `GET /health` 暴露。
这消除了「I-2 之后唯一残留的静默路径」（审计写失败只在内存、NDJSON 里没有、且无任何计数）。

### 11.5 安全与合规

#### (a) 开源许可证 —— 待核实开放问题

| 项 | 说明 |
|---|---|
| 事实 | 9 个引擎的上游许可证**未在本仓库中声明**（各引擎目录内无 `LICENSE` 文件） |
| 风险 | 若各引擎许可证不一致（如存在 GPL 类传染性许可），**合并分发**可能有合规含义 |
| 处理 | ⚠️ **列为待核实开放问题**（§十四-4），**不得在未核实前断言**全部可自由分发 |
| 设计影响 | 前端**不做许可证展示**（开源许可不影响运行时可用性） |

#### (b) 危险操作二次验证 —— 用「影响面预评估」替代通用弹窗

**危险操作在开源侧依然存在**，且 `edits` 机制在 PowerIO 与 surge 中都有：
`set_branch_in_service: false`（断线）· `set_generator_in_service: false`（切机）· `set_switch_closed: false`

**★ 用影响面计算替代弹窗**：

| 步 | 动作 |
|---:|---|
| 1 | 断开前先算**连通性** → 是否产生孤岛 / 失负荷 |
| 2 | 用 **LODF / PTDF** 快速估算越限（本项目 case30 已验证） |
| 3 | 影响面超阈值才要求二次确认，且**显示具体后果** |

```
❌ 通用弹窗：  "确定要执行该修改吗？"          → 用户无脑点确认
✅ 影响面提示："将断开支路 12（端点 9–11），
              导致母线 8 失负荷 30 MW（全网最大负荷点），
              唯一备用通路 8–28 额定仅 32 MVA。"
```

> **关键优势**：**复用已验证的 PTDF/LODF 能力**（case30 三条独立证据链），**不新增算法**。
> 且 **surge 原生提供 `compute_lodf` / `compute_ptdf` / `get_islands`** —— 实现路径已在开源侧就绪。

**RBAC** 是粗粒度前置（角色 → 允许的 edits 子集）；影响面预评估是细粒度后置。两者互补。

### 11.6 缓存与可重现性：内容寻址 + 契约快照

```
cache_key = H(算例拓扑 + 引擎版本 + 工具名 + 规范化参数 + PowerIO IR 版本)
```

- **内容寻址而非会话寻址** → 刷新 / 回退会话**不触发重算**
- 复用 PowerIO IR 已有的 **provenance**

**★ 与契约耦合**：`cache_entry = (结果, provenance, 契约快照)`

| 情况 | 处理 |
|---|---|
| 契约快照一致 | 正常复用 |
| 契约状态已变（引擎升级 / ✅→⚠️） | 标注"**结果来自旧契约状态**"，**不得静默复用** |

> 缓存因此从"性能优化"升级为"**可重现性基础设施**"。

**★ v4 扩展**：实验矩阵（§4.4）的结果同样绑定 `cache_key` —— 这是**实验级可复现**的基础，
与 v3 的「契约可重现」是两个不同层次，**两者都需要**。

### 11.7 易被忽略的 5 个问题

| # | 问题 | 严重度 | 处理 |
|---:|---|:--:|---|
| ① | **多步工作流的部分失败与回滚** —— 已产生的副作用如何处置？**比超时更严重** | 高 | 工作流级事务（§11.2-3） |
| ② | **契约引擎自身的失败语义未定义** | 高 | fail-loud but non-blocking（§11.3）；**严禁静默 fail-open** |
| ③ | **事件乱序** —— 多引擎结果到达顺序不确定 → 一致性视图可能**静默给出错误结论** | 高 | 单调序列号 / 逻辑时钟；按序渲染 |
| ④ | **审计完整性 vs 背压的矛盾** | 中 | 双通道物理分离（§2.6） |
| ⑤ | **Julia 子进程的生命周期** —— HOPE / GenX 启动慢、占内存，与 Python 子进程语义不同 | 中 | 独立超时与按空闲时长回收（§11.3） |

> ⚠️ **③ 最易被忽略而后果最重**：不报错、不变慢，只**静默给出错误的一致性结论** ——
> 恰是「求解成功却报失败」那类状态映射契约问题**在界面层的重演**。

## 十二、自用验收判据

> **v4 定位变更**：前端已与论文选题**解绑**（2026-09-25 裁决），
> 故 v3 §九 的「12 人组间设计可用性实验」**不再适用**（其任务集全部围绕契约，与通用目标不符）。
> v4 改为**自用验收判据** —— 用来判断「这个工作台是否真的在帮张老师做研究」。

| # | 判据 | 检验方式 |
|---|---|---|
| 1 | **一个新算例能跑通全流程** | 从 `D:\GridData` 取一份未处理过的算例，走完 13 步的 A–C 阶段，无人工改脚本 |
| 2 | **能组织研究** | 同一算例的多组实验能挂在同一个 case 下，结果可对比 |
| 3 | **能批量跑** | 场景 8 的网格（算例 × 负荷水平 × 故障集）能一次提交并拿到结果表 |
| 4 | **知道该用什么方法** | 遇到越限时，技能手册能按 escalation triggers 给出对应 playbook |
| 5 | **结果可信** | 校验层能报出契约问题；且**报不出问题时不是假绿灯**（`checked == 0` 必须报 unknown） |
| 6 | **能留痕与复现** | 任何一次结果都能追溯到工具调用、参数、契约快照；重跑得到相同结果 |
| 7 | **新选题接入成本低** | 一个新选题能用 `create-module` 在 L0 起步，**不写 UI 代码**即开工 |

> ⚠️ **不得预设结论** —— 若某条判据长期不达标，本身也是有效发现（说明该设计不解决问题）。
