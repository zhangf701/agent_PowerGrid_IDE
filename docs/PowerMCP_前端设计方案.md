### 1.2 为什么不能照搬 Grid-Orch

| 维度 | Grid-Orch | **PowerMCP（开源版）** |
|---|---|---|
| 引擎数 | **1**（OpenDSS） | **9** |
| 工具数 | 36 | **117**（8 个已挂载 server 实测；OpenDSS 未计入） |
| 数据层 | 单一引擎原生 | **PowerIO IR gen 2**（跨引擎交换格式） |
| 核心难题 | 单引擎内"自然语言 → 工具调用" | **跨引擎的契约一致性**（8 类，已实测） |
| 部署形态 | 多租户 Web 平台 | `pip install powermcp` 的**本地工具** |

**关键差异**：Grid-Orch 的仪表盘全部围绕**单一引擎的物理量**。PowerMCP 的同类物理量分析已能由现有 LLM 客户端完成。**前端若只做图表就是重复劳动。**

> **核心命题**：前端的第一公民不是「图表」，而是**「契约状态」**。

### 1.3 ★ 范围收窄的代价评估（先讲清代价）

放弃商业软件**不削弱契约研究的基础** —— 8 类契约的实测证据里，**7 条完全来自开源引擎**：

| 契约 | 实测证据 | 来源引擎 | 收窄后 |
|---|---|---|:--:|
| API 版本 | `net.deepcopy()` / `Network.status` / `mremove()` | pandapower · PyPSA | ✅ 保留 |
| 文档-实现一致性 | opendss 6 个工具名全部不存在 | OpenDSS | ✅ 保留 |
| 参数 | PyPSA `linearized` 静默忽略 | PyPSA | ✅ 保留 |
| 状态映射 | pypsa N-1 脚本求解成功却报「未收敛」 | PyPSA | ✅ 保留 |
| 命名空间 | `load_network` / `add_bus` / `run_contingency_analysis` 等重名 | **pandapower · PyPSA · surge** | ✅ 保留 |
| 标识符 | 0-based vs 1-based | pandapower · PyPSA | ✅ 保留 |
| 量纲 | 142% 误判为 98% | 开源 | ✅ 保留 |
| 能力声明 | ~~Gurobi 过期~~ / ~~PowerWorld 无 SimAuto~~ / **HOPE 缺 Julia** | ~~商业~~ / HOPE | ⚠️ **收窄** |

**命名空间契约的证据在收窄后反而更强** —— 重名全部发生在**开源引擎之间**（本次实测确认）：
`load_network`（pandapower · PyPSA · surge 三者同名）、`add_bus` / `add_generator` / `add_line` / `add_load`（PyPSA · surge）、
`create_empty_network`（pandapower · surge）、`run_power_flow`（pandapower · PyPSA · ANDES）、
`run_contingency_analysis`（pandapower · PyPSA）、`get_network_info`（pandapower · PyPSA · surge）。

> ✅ **结论**：契约研究的实验基础**不依赖商业软件**。
> ⚠️ 但**能力覆盖**有真实缺口，见 §4.6。

## 二、架构设计

### 2.1 三层结构（不改动任何现有 MCP server）

```
┌─────────────────────────────────────────────────────────────┐
│  Layer 2  Web UI（新增）                                      │
│  聊天 · 契约面板 · 跨引擎一致性 · 能力矩阵 · IR 检查器          │
└───────────────────────────┬─────────────────────────────────┘
                            │ REST + SSE（双通道，见 §2.3）
┌───────────────────────────▼─────────────────────────────────┐
│  Layer 1  Gateway / Orchestrator（新增）                      │
│  · MCP Client（挂载 9 个开源 server，stdio）                   │
│  · LLM Provider Adapter（云 / 本地，含气隙）                    │
│  · 契约引擎（Contract Engine）★                                │
│  · 进程监管（心跳 / 重启 / 熔断）★ 见 §11.3                     │
│  · 会话 / 审计持久化（NDJSON + SQLite WAL）★ 见 §11.4          │
└───────────────────────────┬─────────────────────────────────┘
                            │ MCP (stdio)
┌───────────────────────────▼─────────────────────────────────┐
│  Layer 0  开源 MCP Servers × 9（零改动）                       │
│  pandapower · PyPSA · PowerIO · ANDES · Egret · OpenDSS ·     │
│  surge · HOPE · GenX                                          │
└─────────────────────────────────────────────────────────────┘
```

**硬约束**：Layer 0 **一行不改**（继承 PowerMCP 既有的 *zero source mutation* 哲学）。

### 2.2 ★ 契约引擎（Contract Engine）

| # | 契约类型 | 检测手段 | 节拍 | 输出状态 |
|---:|---|---|:--:|---|
| 1 | API 版本契约 | 比对 `list_tools` 实际返回 vs 工具实现调用的 API | **T0** | ✅ / ❌ |
| 2 | 文档-实现一致性 | 比对 `SKILL.md`/README 声明 vs `list_tools` 实际 | **T0** | ✅ / ⚠️ / ❌ |
| 3 | 参数契约 | ★ **声明 schema 差分**（非行为探测，见 §2.3） | **T2** | ✅ / ⚠️ |
| 4 | 状态映射契约 | 求解器返回码 vs 引擎实际状态 | **T2** | ✅ / ⚠️ |
| 5 | 命名空间契约 | 跨 server 同名工具做语义指纹比对 | **T0** | ✅ / ⚠️ |
| 6 | 标识符契约 | 校验 0-based / 1-based 约定并归一 | **T0** | ✅ / ⚠️ |
| 7 | 量纲契约 | 校验过载判据等单位的 MVA/MW 一致性 | **T0** | ✅ / ❌ |
| 8 | **运行时依赖契约**（v3 重新定义） | 校验引擎的外部运行时依赖是否就绪 | **T1** | ✅ / ⚠️ / ❌ |

> **★ 契约 8 的重新定义（v3）**：
> v1/v2 定义为"厂商接口不可用（许可 / 版本）"，其证据含 Gurobi 许可、PowerWorld SimAuto —— 均随商业软件移除而失效。
> 现重新定义为 **「运行时依赖契约」**：引擎声明的能力 vs **其外部依赖是否就绪**。收窄后实测证据为：
> **HOPE / GenX 缺 Julia 运行时**、**Egret 的 Ipopt 不可用**、**surge 要求 Python 3.12–3.14**。
> 这仍是真实的"能力声明 vs 实际可用"错配，只是成因从**许可**变为**运行时依赖**。

**状态三态**：`✅ 满足` · `⚠️ 降级可用` · `❌ 违反`

**关键设计判断**：契约引擎的求值结果**必须与 LLM 的回答解耦**。二者在前端**分区呈现**。

### 2.3 契约求值的三级节拍（性能硬约束）

| 级 | 触发时机 | 覆盖契约 | 成本量级 | 缓存策略 |
|:--:|---|---|---|---|
| **T0 静态** | 启动时 / server 版本变更时，**一次** | 1, 2, 5, 6, 7 | 纯本地计算，毫秒级 | 按 `(server, 版本)` 持久缓存 |
| **T1 会话级** | 会话开始 / server 组合变更 | 8（运行时依赖探测） | 可能秒级（需拉起引擎 / 探测 Julia） | 会话内复用；**绝不逐调用** |
| **T2 逐调用** | 每次 tool call | 3, 4 | **必须 O(1)** | 无缓存需求 |

**T2 契约 3 的正确实现——不做行为探测**：PyPSA `linearized` 案例的本质是**声明的 `inputSchema` 与实际函数签名不一致**，可静态差分检出：

```
declared = list_tools() 返回的 inputSchema.properties
actual   = inspect.signature(工具实现函数).parameters
diff     → 声明了但实现不接收的参数 = 静默忽略风险
```

**TTFT / RTT 不变量（硬约束）**：

> **契约求值不得出现在 tool call 的返回路径上。** 工具结果先返回；契约状态作为**旁路事件**异步推送。

**SSE 背压与通道分级（硬约束）**：

| 通道 | 内容 | 背压策略 |
|---|---|---|
| **A 证据通道** | 审计证据（调用记录、契约判定、edits 轨迹） | **不可丢弃**；落盘队列 + 批量 fsync |
| **B 遥测通道** | UI 装饰态（进度、临时状态） | **可丢弃**；合并 / 降采样 |

> ⚠️ 二者**必须物理分离**。**审计一旦可丢，审计就不可信**，契约面板全部结论随之失效。

### 2.4 并发隔离与命名空间

`runs_dir(tool)` 目前是 **per-tool**（`~/.powermcp/runs/<tool>`），非 per-session / per-case。目标命名空间：

```
~/.powermcp/runs/<session_id>/<engine>/<case_hash>/
```

详见 §11.2。

## 四、各视图设计

### 4.1 聊天面板

| 要素 | Grid-Orch 做法 | 本项目改造 |
|---|---|---|
| 会话侧边栏 | 恢复历史 + circuit/provider/model/profile | 恢复 **server 组合 / provider / model / 算例** 上下文 |
| 控制头部 | 4 个内联选择器 | **server 多选（9）/ provider / model / 算例 / 契约严格度** |
| Tool Call 面板 | 列工具 + 参数 + 原始 JSON | ★ **契约级审计**：每行额外标注契约状态 |

```
▸ Tool Call (3)                                    ⚠️ 1 项契约告警
  ├─ pandapower.run_power_flow   ✅ 契约 1,3,4 满足
  ├─ pypsa.optimize_network      ⚠️ 契约 3 降级：参数 `linearized` 不存在但被静默忽略
  │    args: {network: ..., linearized: true}     ← 已标注
  └─ powerio.calc_matrix         ✅ 契约 6 已归一（1-based → 0-based）
       args: {matrix: "lodf", powerio_ir: ...}
```

### 4.2 ★ 契约面板（差异化核心）

```
┌─ 参数契约 ──────────────────────────────── ⚠️ 降级 ─┐
│ 涉及：pypsa                                        │
│ 证据：入参 `linearized` 未被引擎接受，且无报错        │
│ 影响：DC OPF 结论可能不成立                         │
│ 建议：改用 `pypsa` 支持的等价参数，或改用 pandapower  │
│                          [查看实测记录] [标记已确认] │
└────────────────────────────────────────────────────┘
```

**设计要点**：
- 每条卡片**必须给出可执行建议**
- 「标记已确认」让工程师显式承接风险——**human-in-the-loop 在界面上的落点**
  （Grid-Orch 承认需要 human-in-the-loop，但**未说明界面上如何呈现**）
- 可折叠，默认只展开 `⚠️` 与 `❌`

### 4.3 ★ 跨引擎一致性视图（差异化核心）

| 指标 | pandapower | PyPSA | surge | 一致性 |
|---|---:|---:|---:|---|
| 母线 8 电压 (pu) | 1.0234567 | 1.0234567 | 1.0234567 | ✅ Δ = 6.98e-11 |
| 支路 12 有功 (MW) | 12.3456 | 12.3456 | 12.3456 | ✅ |
| 最大过载 (%) | 142 | **98** | 142 | ❌ **量纲契约违反** |
| 关键支路索引 | 12 / 15 / 33 | 13 / 16 / 34 | 12 / 15 / 33 | ⚠️ **标识符契约**（PyPSA 1-based） |

**设计要点**：
- Δ 值**必须显示**（PowerIO IR 往返保真的证据，实测 `Δ = 6.98e-11 pu`）
- 不一致处**不用颜色单独承载信息**——同时给出文字说明（无障碍要求）
- 每行可下钻到原始工具调用
- ⚠️ **并发执行时的事件顺序**：多引擎结果到达顺序不确定，**必须靠单调序列号排序**，
  否则可能显示**错配的对比**（比"慢"更危险：会给出错误的一致性结论）。见 §11.7-③

| **surge** | ✅ | ✅ | ✅ **含 N-2** | ✅ SCUC | — | ✅ PTDF·LODF·OTDF·ATC | ✅ | Python 3.12–3.14 |
| **pandapower** | ✅ | — | ✅ | — | — | — | ✅ | 无 |
| **PyPSA** | ✅ | ✅ | ✅ | — | — | — | ✅ | 求解器（HiGHS/CBC/GLPK） |
| **PowerIO** | — | — | — | — | — | ✅ | ✅ | 无 |
| **ANDES** | ✅ | — | — | — | ✅ | — | ✅ | 包 `andes`（已装） |
| **Egret** | — | ✅ AC/DC OPF | — | ✅ UC | — | — | ✅ | ⚠️ Ipopt 不可用；另需 `gridx-egret` + `pyomo`（已装） |
| **HOPE** | — | ✅ | — | — | — | — | — | Julia —— **仅求解执行时需要，不影响挂载**（实测可拉起 20 工具） |
| **GenX** | — | ✅ 容量规划 | — | — | — | — | — | Julia + GenX.jl —— **仅求解执行时需要，不影响挂载**（实测可拉起 7 工具） |
| **OpenDSS** | ✅ | — | — | — | — | — | — | ❌ **无法经 mcp SDK 挂载**（见立项文档） |

> 表中能力均由**实测工具名**支撑（如 surge 的 `run_n2_branch_contingency`、`compute_lodf`、`run_scuc`；
> ANDES 的 `run_time_domain_simulation`、`run_eigenvalue_analysis`；PyPSA 的 `optimize_investment`）。
>
> **2026-09-24 实测校正**：原表的"缺 Julia"判断**不成立** —— **HOPE 与 GenX 均可正常挂载**
> （实测 20 / 7 个工具；二者 `probe` 分别是 `yaml` 与 `matplotlib`，与 Julia 无关）。
> 真正拉不起来的是 **andes / egret / opendss**，成因是缺 pip extra
> （`pip install powermcp[andes|egret|opendss]`；**egret 的包名是 `gridx-egret`**，另需 `pyomo`）。
> 三者已按**最小依赖**安装，其中 andes / egret 挂载成功，**opendss 仍失败** ——
> 依赖已满足、协议层正常（裸探针 1.86s 正确响应），但经 mcp SDK 握手超时，属独立缺陷，见
> [opendss 缺陷立项](superpowers/plans/2026-09-24-opendss-sdk-mount-defect.md)。
> ⚠️ "Julia 仅影响求解执行"**尚未验证** —— 本次只验证了挂载，未执行任何求解。

**设计要点**：
- 单元格**可点击下钻**：显示探测依据（`powermcp doctor` 输出）
- `⚠️` / `❌` 必须给出**可执行修复路径**（安装 Julia / 换求解器 / 调整 Python 版本）
- 复用现有 `powermcp doctor` 探测逻辑，**不新增探测机制**

### 4.5 IR 检查器

| 字段 | 展示方式 |
|---|---|
| `value_type` | 标签（被选中的 PowerIO 结构类型） |
| `selection` | 树形展开 |
| `diagnostics` | 列表，按 `severity` 排序；含 `code` / `target` / `spans` / `suggested action` |
| `fidelity` | 徽章：`exact_same_format`（回显原始字节）/ `canonical`（新生成） |
| `edits` | ★ **编辑轨迹时间线**（12 种 typed ops；连续同类更新作为**原子批**） |
| `warnings` | 折叠列表 |

> ⚠️ **危险 edits 需影响面预评估**，不能直接执行。见 §11.5

### 4.6 ★ 能力覆盖缺口分析（v3 新增）

放弃商业软件后，必须**诚实标注**哪些能力无法在开源侧弥补：

| 商业引擎 | 独有能力 | 开源替代 | 缺口判定 |
|---|---|---|---|
| **PSCAD** | **电磁暂态（EMT）** | 无 | ❌ **真实缺口** —— LTSpice 是电路级而非电网级，且亦已移除 |
| PSS/E | 工业级潮流 / 动态 | pandapower · surge · ANDES | ✅ 可替代 |
| PowerFactory | 机电暂态 / 保护 | ANDES（时域仿真） | ⚠️ 部分替代 |
| PowerWorld | 可视化潮流 / N-1 | surge（N-1 + **N-2**） | ✅ 可替代 |
| PLEXOSDB | 市场 / 机组组合优化 | Egret（UC）· GenX（容量规划） | ⚠️ 部分替代 |

> **★ 唯一硬缺口：电磁暂态（EMT）仿真。** 这一点必须在方案与论文中**明确写出**，
> 不得用"开源可替代"含糊带过。其余能力缺口均为"部分替代"，需在能力矩阵中如实标注精度差异。

## 五、视觉规范

### 5.1 语义色（三态优先）

`✅ 满足`（绿）· `⚠️ 降级`（琥珀）· `❌ 违反`（红）

> **约束**：颜色**不得单独承载信息**。每个状态徽章必须同时含图标 + 文字。

### 5.2 排版

| 用途 | 字体 | 理由 |
|---|---|---|
| 正文 / 说明 | 无衬线 | 常规 |
| **工具名 / 参数名 / 数值 / 单位** | **等宽** | ★ 可审计性 |

### 5.3 硬规则

1. **数值必须与单位同时出现**——须写 `142% (MVA 判据)`。
   这是**量纲契约在界面上的强制落地**（该缺陷曾导致"142% 误判为 98%"）。
2. **标识符必须标注约定**——须写 `12 (0-based)` 或 `13 (1-based)`。
   这是**标识符契约在界面上的强制落地**（该缺陷曾把偏差放大 3.1 亿倍）。
3. **每次 LLM 回答末尾附契约摘要**：`本次分析：契约 ✅5 ⚠️2 ❌0`，可点开 4.2 面板。

## 十一、工程加固设计

### 11.1 性能：契约求值的延迟与竞态

**缓解措施**：
1. **三级节拍**（§2.3）——T0/T1 不落在调用路径上，只有契约 3/4 逐调用且为 O(1)
2. **契约 3 改静态 schema 差分**——微秒级，无需行为探测
3. **TTFT 不变量**——契约求值不得出现在返回路径上
4. **SSE 双通道**——证据不可丢、遥测可丢，物理分离

**残余风险**：T2 契约 4 需读引擎返回码，若返回码语义不明则需额外探测。
→ 处理：**降级为"未知"态而非阻塞**。

### 11.2 并发隔离：既有沙箱的边界与扩展

**既有实现（已核实，比初版假设的好）**：

| 机制 | 位置 | 覆盖范围 | 缺口 |
|---|---|---|---|
| 路径包含 | `powermcp/sandbox.py`（re-export `powerio.mcp.sandbox`） | `POWERIO_MCP_ALLOWED_ROOTS`；**解析 symlink 与 `..` 后比对真实目标** | 只防**越界**，不防**同名** |
| 单文件原子安装 | `staged_file_write` | `overwrite=False` 硬链接**不覆盖并发创建的目标**；`overwrite=True` 用 `os.replace` | **单文件 ≠ 多文件事务** |
| per-tool 运行目录 | `paths.runs_dir(tool)` = `~/.powermcp/runs/<tool>` | 按**工具**隔离 | ⚠️ **非 per-session / per-case** |
| Egret 写入 | `tempfile.mkstemp(prefix="egret_case_")` | 天然唯一名，**碰撞安全** | — |
| ANDES 写入 | `os.path.join(runs_dir("andes"), name)` | 按名字拼路径 | ⚠️ 与 Egret **不一致** |
| 锁机制 | 全仓检索 | PowerMCP **自身代码 0 命中**（仅 `.venv` 第三方库） | ⚠️ **无任何序列化** |

**★ 诊断**：

> 既有沙箱解决的是 **「安全」（防路径穿越）+「文件级原子性」**；
> 而问题是 **「并发隔离」+「事务性」**。
> **两个不同层次，不能靠同一机制解决** → 修法是**扩展现有机制的 scoping**，不是新建沙箱。

**设计方案**：

| # | 措施 | 说明 |
|---:|---|---|
| 1 | **命名空间加 session 维度** | `runs_dir` 升级为 `~/.powermcp/runs/<session_id>/<tool>/<case_hash>/` |
| 2 | **租约锁** | 每 `(engine, case_hash)` 一把；本地 `fcntl` / `portalocker`，跨机文件租约 |
| 3 | **工作流级事务** | 产物写 staging；整体成功才 `os.replace` 提交；失败丢弃 staging |
| 4 | **引擎实例串行化** | 单实例 + 请求队列；跨机每容器一实例 + 负载均衡 |
| 5 | **统一写入方式** | 把 ANDES 等按名字拼路径的写法统一到 `mkstemp` / `staged_*_write` |

**残余风险**：`ALLOWED_ROOTS` 检查**无法阻止另一进程在验证后替换路径**（PowerIO 源码已自陈）。
→ 租约锁 + 事务提交可缓解，**不可宣称完全消除**。

### 11.3 进程生命周期：心跳、重启、熔断

**v3 变更**：商业引擎（COM/DLL）移除后，**Windows COM 泄漏与树杀问题基本消失**。
剩余需管理的外部进程类型：

| 类型 | 引擎 | 管理要点 |
|---|---|---|
| **Julia 子进程** | HOPE · GenX | 启动慢、内存占用高；需独立超时与回收策略 |
| Python 子进程 | 其余 7 个 | 常规 stdio 管理 |

| 措施 | 设计 |
|---|---|
| **心跳** | MCP 有 `ping`；网关侧**主动周期轮询**，不能只依赖被动读超时 |
| **自动重启** | 指数退避 + 上限；**重启后必须重新求值 T0/T1 契约**（进程换了，版本可能变） |
| **熔断** | 连续 N 次失败 → 打开熔断 → **直接驱动能力矩阵降级**（与 `doctor` 同源） |
| **主动回收** | Julia 子进程启动慢且占内存 → 按**空闲时长**回收（而非等它崩）；阈值按引擎分别标定 |

**★ 失败语义（关键设计决策）**：

| 组件 | 失败策略 | 理由 |
|---|---|---|
| 引擎进程崩溃 | **fail-closed** | 该引擎标记不可用，调用直接拒绝。不得返回可疑结果 |
| 契约引擎崩溃 | **fail-loud but non-blocking** | 不阻塞调用，但界面明确标注"**契约状态未知**"，且未知态入审计 |

> ❌ **绝不允许契约引擎静默 fail-open** —— 那会退化成"没有契约引擎"，
> 用户以为有保护实际没有，**比明确的故障更危险**。

### 11.4 审计存储：NDJSON + SQLite WAL 分离

**WAL 是必要不充分的**：WAL 允许单写多读，但**写仍串行**；高频审计写入依然争用。

| 数据 | 存储 | 理由 |
|---|---|---|
| **审计证据流**（append-only 事件） | **NDJSON 追加文件** | OS 保证小写入的 append 原子性；**无跨写者锁争用** |
| **会话元数据**（需查询 / 事务） | SQLite **WAL** | 需要索引与事务语义 |

补充：**单写线程 + 内存环形缓冲**批量 flush；背压按 §2.3 通道分级；审计文件按会话切分。

### 11.5 安全与合规（v3 重写）

#### (a) 商业许可 —— 已随范围收窄整体移除

v2 的"许可暴露风险"（EULA 红线、遥测暴露、并发复用）**在本版全部不适用**：无商业软件、无许可服务器、无许可遥测。

**但新增一个轻量的开源许可证合规点**：

| 项 | 说明 |
|---|---|
| 事实 | 9 个引擎的上游许可证**未在本仓库中声明**（各引擎目录内无 `LICENSE` 文件） |
| 风险 | 若各引擎许可证不一致（如存在 GPL 类传染性许可），**合并分发**可能有合规含义 |
| 处理 | ⚠️ **列为待核实开放问题**（§十二-4），**不得在未核实前断言**全部可自由分发 |
| 设计影响 | 前端**不做许可证展示**（与商业许可不同，开源许可不影响运行时可用性） |

#### (b) 危险操作二次验证 —— 用「影响面预评估」替代通用弹窗

**危险操作在开源侧依然存在**，且 `edits` 机制在 PowerIO 与 surge 中都有：
`set_branch_in_service: false`（断线）· `set_generator_in_service: false`（切机）· `set_switch_closed: false`

**★ 用影响面计算替代弹窗**：

| 步 | 动作 |
|---:|---|
| 1 | 断开前先算**连通性** → 是否产生孤岛 / 失负荷 |
| 2 | 用 **LODF / PTDF** 快速估算越限（本项目 case30 已验证） |
| 3 | 影响面超阈值才要求二次确认，且**显示具体后果** |

```
❌ 通用弹窗：  "确定要执行该修改吗？"          → 用户无脑点确认
✅ 影响面提示："将断开支路 12（端点 9–11），
              导致母线 8 失负荷 30 MW（全网最大负荷点），
              唯一备用通路 8–28 额定仅 32 MVA。"
```

> **关键优势**：**复用已验证的 PTDF/LODF 能力**（case30 三条独立证据链），**不新增算法**。
> 且 **surge 原生提供 `compute_lodf` / `compute_ptdf` / `get_islands`** —— 实现路径已在开源侧就绪。

**RBAC** 是粗粒度前置（角色 → 允许的 edits 子集）；影响面预评估是细粒度后置。两者互补。

### 11.6 缓存与可重现性：内容寻址 + 契约快照

```
cache_key = H(算例拓扑 + 引擎版本 + 工具名 + 规范化参数 + PowerIO IR 版本)
```

- **内容寻址而非会话寻址** → 刷新 / 回退会话**不触发重算**
- 复用 PowerIO IR 已有的 **provenance**

**★ 与契约耦合**：`cache_entry = (结果, provenance, 契约快照)`

| 情况 | 处理 |
|---|---|
| 契约快照一致 | 正常复用 |
| 契约状态已变（引擎升级 / ✅→⚠️） | 标注"**结果来自旧契约状态**"，**不得静默复用** |

> 缓存因此从"性能优化"升级为"**可重现性基础设施**"。

### 11.7 易被忽略的 5 个问题

| # | 问题 | 严重度 | 处理 |
|---:|---|:--:|---|
| ① | **多步工作流的部分失败与回滚** —— 已产生的副作用如何处置？**比超时更严重** | 高 | 工作流级事务（§11.2-3） |
| ② | **契约引擎自身的失败语义未定义** | 高 | fail-loud but non-blocking（§11.3）；**严禁静默 fail-open** |
| ③ | **事件乱序** —— 多引擎结果到达顺序不确定 → 一致性视图可能**静默给出错误结论** | 高 | 单调序列号 / 逻辑时钟；按序渲染 |
| ④ | **审计完整性 vs 背压的矛盾** | 中 | 双通道物理分离（§2.3） |
| ⑤ | **Julia 子进程的生命周期** —— HOPE / GenX 启动慢、占内存，与 Python 子进程语义不同 | 中 | 独立超时与按空闲时长回收（§11.3） |

> ⚠️ **③ 最易被忽略而后果最重**：不报错、不变慢，只**静默给出错误的一致性结论**——
> 恰是 §5.2 中「求解成功却报失败」那类状态映射契约问题**在界面层的重演**。

## 附：与选题的关系（一句话）

> 本方案把 §5.2 的 **8 类接口契约**从"调研报告里的表格"变成"**工程师屏幕上可读、可审计、可承接风险的界面**"。
> 它是 L2（可形式化验证的性质）的可视化层，也是 L3（校验套件）的呈现层 —— **而不是一个通用聊天前端**。
>
> **范围收窄的净影响**：8 类契约的实测证据中 **7 条完全来自开源引擎**，
> 契约研究的实验基础**不依赖商业软件**；唯一代价是**电磁暂态能力出现硬缺口**（§4.6）。
