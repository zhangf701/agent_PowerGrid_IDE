PowerMCP 实践指南

让 LLM 真正操作电力仿真软件

仓库：Power-Agent/PowerMCP　｜　许可：MIT　｜　代码：约 26,000 行 Python　｜　当前版本：powermcp 0.4.0（Alpha）
定位：电力系统软件的 MCP 服务器集合，把 PSS/E、PowerWorld、OpenDSS、pandapower 等 16 款软件的 API 封装成 LLM 可直接调用的工具
适用读者：电网工程师、新能源开发商技术团队、电力 AI 应用开发者

一、这个项目到底解决什么问题

1.1 电力 AI 最硬的那道墙

假设你让一个通用大模型回答："把 IEEE 39 节点系统的 L7 线路断开后，哪条线路会过载？"

它可能会给你一个听起来很专业的答案。但你无法验证它是真的算过，还是编的。

原因很直接：电力行业的核心仿真工具（PSS/E、PowerWorld、PowerFactory、PSCAD、PSLF）几乎全部是闭源商业软件，LLM 无法访问、无法调用、无法验证。模型再聪明，也只能停留在"文本层面"，无法触及"物理真实"。

PowerMCP 的解法很朴素但很彻底：为每一款电力软件写一个 MCP 服务器，把软件的底层 API 变成 LLM 可以直接调用的工具。

用户提问
  ↓
LLM（Claude / GPT / 本地模型）
  ↓  MCP 协议
PowerMCP 服务器（16 个）
  ↓  调用厂商 API
PSS/E · PowerWorld · OpenDSS · pandapower · PyPSA · ANDES ...
  ↓  返回真实计算结果
LLM 基于物理结果作答          ← 而不是基于想象
MCP 是什么：Anthropic 提出的 Model Context Protocol（模型上下文协议），作用是给 AI 应用提供统一的工具连接标准。你可以把它理解为"AI 世界的 USB-C 接口"——不论什么模型、什么软件，都通过同一个协议对接。

1.2 一句话总结价值

PowerMCP 的价值不在于让 LLM 更聪明，而在于让 LLM 的结论第一次变得"可验证"。

三、安装与配置（实操）

3.1 最简安装路径

# 1) 安装核心（含 pandapower + PyPSA + PowerIO，无需任何配置）
pip install powermcp

# 2) 运行交互式向导
powermcp install

向导会依次完成三件事：

  1. 让你勾选工具（↑↓ 移动，空格键切换选中，回车确认）
  2. 采集闭源软件的本地安装路径（如 PSS/E、PSLF 的 Python 库路径）
  3. 自动写入 MCP 客户端配置（支持 Claude Desktop、Claude Code、Codex CLI 三类）
注意：在勾选界面直接按回车，只会保留预选项（pandapower + PyPSA + PowerIO）。一定要用空格来增减选择。

3.2 命令行直选（不想用勾选界面）

powermcp install --tools psse,andes     # 核心 + 指定工具
powermcp install --all                  # 当前平台所有可用工具
powermcp install --dry-run              # 只预览改动，不实际写入
powermcp install --yes                  # 非交互，只装核心

一个重要特性：重新运行 powermcp install 时，上次已安装或已配置的工具会被自动预勾选，所以它是"更新"而不是"重置"。这对逐步扩充工具集的团队很友好。

3.3 安装衍生工具包（可选）

pip install powermcp[psse]              # PSS/E 支持
pip install powermcp[andes,opendss]     # 一次装多个
pip install powermcp[opensource]        # 全部开源工具
pip install powermcp[all]               # 全部（闭源软件仍需本地安装）
实测提醒：pip install powermcp[opensource] 会一次带入 7 个开源 extra，其中 egret 会额外拉入 pyomo（较重）、surge 是 pyo3/maturin 轮子（仅支持 Python 3.12–3.14）。若只想要其中几个，用逗号直选更省事。
另有一个反直觉的实测结论：[genx] extra 不增加任何新包——它声明的 matplotlib / pandas 已由核心的 pandapower 传递带入。

3.4 闭源工具的路径配置

这些工具包装的是本地安装的商业软件，PowerMCP 需要知道它们在哪。配置存储在 ~/.powermcp/config.toml。

3.5 验证安装

powermcp doctor        # 逐个检查工具的依赖与路径配置
powermcp list          # 列出可用工具、extras、平台限制

doctor 是排查问题的第一站。如果某个工具报错，先看它，再决定是装依赖还是配路径。

doctor 报 ok 不等于工具可用：doctor 只检查两件事——依赖包能否导入、配置路径是否存在。它不验证工具真的能被调用。本指南第六章给出的可用性结论，是在 doctor 之外另外做了运行时核验（实际拉起 server、调 list_tools 取真实返回值）得到的。

工作区陷阱（值得单独提醒）：有用户报告 Windows 上的 Codex Desktop 应用会覆盖 ~/.codex/config.toml。如果你同时使用 Desktop 和 CLI，Desktop 改过配置后需要重新运行一次 powermcp install。Codex CLI 本身不受影响。

3.7 不用安装，直接从克隆运行

每个服务器都是独立脚本，克隆仓库后可直接跑：

python pandapower/panda_mcp.py
python PSSE/psse_mcp.py         # 会读取 ~/.powermcp/config.toml
python -m powerio.mcp           # powerio 自带服务器
推荐做法（本指南的实测环境即如此）：用一个隔离的虚拟环境安装，而不是装在系统 Python 里。实测做法是 uv venv .venv --python 3.12 后 uv pip install -e ".[hope,surge]"，全程未触碰任何 conda 环境或系统配置。原因是 PowerMCP 的依赖有版本上界（如 pypsa>=0.35.2,<2、pandas>=2.0,<3），与既有环境混装容易冲突。

四、各工具能力速查

本章按 server 逐个列出工具清单。工具数为仓库静态统计 + 运行时核验的结果；标注 ★ 的 server 已做过运行时 list_tools 核验。

4.2 PSS/E（含独门绝技：命令动态桥接）

PSS/E 有一个别的工具都没有的能力——不只是暴露固定工具，还让模型自己能查、能调 PSS/E 的底层命令：

层级工具说明
基础open_case(case)打开案例
基础solve_case()求解潮流
发现search_psspy_commands(query, category)按关键词搜索 PSSPY 命令
发现lookup_psspy_command(function_name)查某个命令的完整签名
执行run_psspy_command(function_name, arguments)执行任意 PSSPY 命令

这是 PowerMCP 里最重要的设计选择之一。别的工具只能做开发者预设的那几十件事；PSS/E 这条链路等于把 PSS/E 数千个 API 全部开放给模型。代价是需要模型先搜索、再查签名、最后执行——但能力上限完全不同。

使用纪律（来自官方技能文档）：
  • 不要把 run_psspy_command 当搜索工具用——先 search 或 lookup
  • 每条执行的命令都要绑定一个研究目标，而不是"试试这个 API"
安全设计（值得知道）：PSS/E server 内置 22 条命令禁止清单，拦截"启动任意程序、执行命令文件、注入 Python 代码、加载原生库、读取含 Python 的 RAS 文件、I/O 重定向"等类别。拦截点早于引擎启动。设计动机写在源码注释里：路径围笼并不能让可执行输入变安全。此外 PSS/E 的 2184 份 PSSPY 命令规格以 JSON 形式随包分发，是本仓最大的文件量来源。

4.3 surge（开源输电网全流程，44 个工具）★

如果不想买商业许可，surge 是目前覆盖最全的开源选择：

案例 I/O → 潮流(AC/DC/FDPF) → 灵敏度(PTDF/LODF/OTDF)
        → OPF(DC/AC/SCOPF) → N-1/N-2 故障分析
        → NERC/AC 可用输电能力 → SCED/SCUC 调度
        → 检查/导出/图分析 → 网络构建与编辑

系统依赖（容易踩坑，先装好）：

平台命令
Ubuntu / Debiansudo apt install libhighs-dev coinor-libipopt-dev
macOSbrew install highs ipopt
Windows（实测可行路径）conda create -n powersolvers -c conda-forge highs ipopt，再把库目录指给 HIGHS_LIB_DIR
关键提醒：pip install highspy 单独安装不满足 HiGHS 的运行时链接要求，必须装系统库。库在非标准路径时，设置 HIGHS_LIB_DIR 和 IPOPT_LIB_DIR。Gurobi、COPT、CPLEX 是运行时插件——有许可就自动检测使用，没有则回退到 HiGHS/Ipopt。
Windows 上的实测边界（重要）：
  • HiGHS 可靠可用：设好 HIGHS_LIB_DIR 后 DC OPF 连续 3 次运行结果完全一致（cost=125948.01），确定性通过。
  • Ipopt 未能可靠解决：试遍别名 / IPOPT_LIB_DIR / PATH / 预加载共 7 种组合均失败；有一次不可复现的成功，另一次尝试中进程静默崩溃。故 AC OPF 在 Windows 上暂不可用，需要 AC OPF 时请走 pandapower 的 runopp（见 6.3 节）。
  • Gurobi 路径另有两重阻塞：surge 只支持 Gurobi 13.x，而本机为 11.0.3；且许可已于 2026-03-31 过期。改 DLL 名行不通——旧版本 API 不兼容，会在符号解析阶段崩溃。

4.4 ANDES（动态分析）

工具作用
run_power_flow(file_path, dyr_path=None)潮流求解，可选附加 .dyr 动态模型文件
run_time_domain_simulation(step_size=0.01, t_end=10.0)时域仿真
run_eigenvalue_analysis(file_path)特征值（小信号）分析
get_system_info()系统信息

run_power_flow 返回的两个关键字段（很容易被忽略，但很重要）：

  • n_dynamic_generators：实际加载的动态发电机模型数量（汇总 ANDES 的 SynGen、RenGen、DG 三组）
  • dynamic_models_loaded：布尔值

这是一个设计得很诚实的细节：dynamic_models_loaded 是根据实际加载了什么推导出来的，而不是根据你是否传了 dyr_path。原因是 ANDES 的 PSS/E dyr 解析器会跳过它不支持的模型类型——所以即使你传了 .dyr，系统仍可能没有任何动态模型。反过来说，像 kundur_full.json 这种自身内嵌动态的案例，不传 .dyr 也会报告 True。

实践含义：想跑时域仿真或特征值分析前，必须先确认 dynamic_models_loaded 为 True，否则你算的是一个没有动态的静态拓扑。

4.5 PyPSA（规划与优化）★

环境要求：PyPSA >= 0.35.2 且 < 2；至少一个 LP 求解器（推荐开源 HiGHS；商业可用 Gurobi 学术版）。

两个实测陷阱：
  • 不要传 linearized=True：PyPSA 1.2.4 的 optimize() 没有这个参数，实参落进 **kwargs 被静默忽略，你以为在跑 DC OPF，实际跑的是 AC OPF。关键参数请先核对函数签名。
  • 不要读 Network.status：该属性在 PyPSA 1.2.4 中已移除。用 hasattr 判断会得到 False，从而误报"未收敛"——而求解器实际返回的是 ('ok','optimal')。正确做法是从 optimize() 的返回值取状态。

五、核心机制：PowerIO 跨软件案例翻译

这是 PowerMCP 工程上最有价值的设计，值得单独一章。

5.1 问题：每种软件说自己的"语言"

.raw（PSS/E）、.pwb / .aux（PowerWorld）、.dss（OpenDSS）、.nc（PyPSA）、.m（MATPOWER）……格式各不相同。过去要跨软件分析，只能靠人工导出导入。

5.2 解法：一个统一的 IR 传输格式

PowerIO 作为核心依赖（不是可选组件）内置于 PowerMCP，承担"翻译层"职责。交换格式是 PowerIO IR generation 2（"schema": "pio-ir"，"version": 2）——一个带类型、带来源信息、带诊断的文档：

parsed = parse(path="case9.raw")          # powerio server：解析成 IR
ir = parsed["powerio_ir"]

summarize(powerio_ir=ir)                  # 摘要：元件数 / 拓扑 / 参考母线
diagnostics(powerio_ir=ir)                # 诊断：code / severity / target / 建议动作
calc_matrix(matrix="ptdf", powerio_ir=ir) # 直接建矩阵（行列带母线/支路标识）

load_network_from_json(powerio_ir=ir)                        # → pandapower
import_case_from_json(powerio_ir=ir, output_path="case9.nc") # → PyPSA
load_model_from_json(powerio_ir=ir)                          # → Egret
load_network_from_json(powerio_ir=ir, out_path="case9.m")    # → ANDES
emit(format="psse", destination="case9.raw", powerio_ir=ir)  # → 落盘给只认路径的软件
核心思路：解析一次，在工具调用之间传递返回的 IR 字符串，只在后端确实需要文件时才落盘。network_json 是 powerio_ir 的别名，两者等价。
边界（官方明确声明）：PowerMCP 自身从不重新解析、重新校验或重新计算 PowerIO 所声明的任何东西——它只负责把已声明的值路由给能接受它的消费者。

5.5 一个体现工程严谨性的设计：拒绝静默求解

这是 PowerMCP 里最值得称赞的一个安全设计。

场景：包内存储了多个运行状态，但调用方没有指定用哪个。

# 静态包可以直接加载
import_case_from_json(powerio_ir=pkg, output_path="case9.nc")

# 含多个存储状态的包，必须显式选择
import_case_from_json(
    powerio_ir=pkg,
    output_path="dispatch.nc",
    scenario_id="high-demand",   # ← 必须显式指定
    time_index=3,                # ← operating_point 是它的别名
)

load_network_from_json(powerio_ir=pkg, study_commit=1)   # pandapower

如果调用方不选，PowerMCP 会报错，而不是默认求解基础模型。同样的保护还有两处：

保护机制行为防止的问题
未选状态拒绝含多状态包未指定 → 报错悄悄求解错的运行点
多导体包拒绝平衡求解器拒绝多相包，除非显式降维配电网到输电网的有损归约被隐式执行
路径预检显式与旧式派生的 CSV 写入目标都做预检越界写文件
为什么这很重要：在电力工程里，一个悄悄算错的结果比一个明确的报错危险得多。报错你可以修；算错了你可能直接拿去做决策。PowerMCP 选择了"宁可报错也不猜"——这是一个成熟的工程设计取向。

配电网场景下，多导体值会被平衡求解器拒绝，直到调用方主动要求转换：传 to_balanced=True（并给 base_mva），响应里会带 PowerIO 的就绪报告；也可以先调 powerio server 的 to_balanced_report 与 to_balanced。保留某元件不等于所选求解器能建模它。

5.6 路径沙箱

PowerIO 的 MCP 工具只接受本地路径和 file:// URI，非本地 URI 方案一律拒绝。可通过环境变量限定可访问目录：

export POWERIO_MCP_ALLOWED_ROOTS="/data/cases:/home/user/projects"

策略实现不在本仓，而是直接复用 powerio.mcp.sandbox——避免两份策略实现走样。关键性质是先解析、后比较，所以 .. 段和指向根外的符号链接都逃不掉（"被比较的是真实目标，而不是拼写"）。

不设置这个变量的后果（实测）：路径围笼会退化为"服务进程启动目录"，doctor 对此报黄色警告而非错误。其注释直言：这个默认值"比操作者通常想要的更窄，而且没有写在任何地方"。所以只要你的算例不在 server 启动目录下，读文件就会被拒——这是策略问题，不是 bug。
诚实的技术说明（官方文档中明确写出）：这些是预检（preflight）检查，不是完全隔离。另一个进程理论上可以在检查之后、后端打开文件之前替换掉那个条目。这是"降低风险"而非"消除风险"。

除了路径围笼，本仓还有一层更硬的控制：AST 静态强制检查。测试用 ast.parse 解析每个 server 的源码，断言"每个接收模型路径参数的 tool 真的调用了 checked_path"。这不是单元测试，而是契约一致性门禁——新增一个接收路径的 tool 却忘了走围笼，CI 会直接红。

5.7 特殊案例：PowerWorld 显示文件

PowerWorld 的 .pwd 显示文件需要单独解码：

display(path="...")     # 返回图纸画布 + 每个变电站的显示坐标

一个解释纪律（避免误读）：母线 35 的 1.0636 pu 恰等于该处发电机的电压设定值——它是 PV 母线，由机组维持在设定点。所以"有 7 个母线高于 1.05 pu"反映的是算例数据的设定值偏高，而不是求解异常。报告措辞必须区分这两者。

8.3 逐步详解（含提示词）

步骤 1 — 环境预检

目的：先确认哪些 server 真能跑，避免在不可用的路径上浪费时间。

先用 powermcp doctor 检查本机环境，然后给我一份表格，列三组：
(1) 依赖 ok 的 server；
(2) 报 missing 的 server 及缺失的包名；
(3) 报 vendor engine / 需要配置路径的 server。
先只做检查，不要安装任何东西、不要改配置。
另外单独告诉我 surge 的 DC OPF 是否可用（看 HIGHS_LIB_DIR 是否已设）。

验收判据：能明确区分"可用 / 装得上≠跑得动 / 需商业授权"三类。

步骤 2 — 打通路径围笼（最容易漏的一步）

目的：让 server 能读到目标目录下的文件。

我后面要分析的算例放在 D:\GridData 下。
请先确认 POWERIO_MCP_ALLOWED_ROOTS 环境变量当前是否已设置、是否包含 D:\GridData。
如果没设置或不包含，只告诉我应该怎么设置，先不要动系统环境变量、不要改配置文件。
同时说明：不设置的话，哪些操作会失败、失败时的报错大概是什么样。

验收判据：明确知道围笼当前状态 + 是否需要设置。

纪律：修改系统环境变量属高危操作，必须用户确认后才执行。若报"路径不在允许根内"，说明围笼未包含目标目录——这是策略问题，不是 bug。

步骤 3 — 盘点目录 + 工具名核对（防坑双检）

目的：①搞清算例有哪些文件；②确认后面要用的工具名真实存在。

两件事，都只读不改：

第一，列出 D:\GridData 下的全部文件（含大小、扩展名、修改时间），
并判断哪些是算例文件、哪些是附属数据（如负荷曲线、故障表、地理信息）。
如果有多个候选算例，按"最可能是主算例"排序并说明理由，先不要解析。

第二，对 powerio、pandapower、pypsa、surge 四个 server 各调一次 list_tools，
把工具名清单完整给我。我要用这份清单核对我后面要调的工具名是否真实存在。

验收判据：拿到文件清单 + 四份真实工具名清单。

步骤 4 — 解析为 PowerIO IR（统一数据契约）

目的：把任意格式的算例转成跨 server 通用的统一表示。后续所有引擎都从这一份 IR 出发，避免"各引擎各读各的格式"导致结论不可比。

用 powerio server 的 parse 工具解析 D:\GridData\<第 3 步确定的主算例文件>。
要求：
1) 把返回的 powerio_ir 完整保存下来（后面每一步都要复用同一份，不要重新解析）；
2) 告诉我返回的 schema 与 version；
3) 告诉我 value_type 是什么（BalancedNetwork 还是多导体/其它）；
4) 如果返回里带 diagnostics，先原样贴出来。

先不要做任何求解。

失败处理：若是多导体网络（配电网），平衡求解器会拒绝，需先调 to_balanced_report / to_balanced 降维；若是已退役格式，需重新 parse 原始算例。

步骤 5 — 摘要与诊断（先判断算例是否可用）

目的：在花时间跑潮流之前，先看这份算例本身有没有问题。这是最省钱的一步。

对刚才那份 IR 调 summarize 和 diagnostics，给我：

A. 摘要：母线数 / 支路数 / 机组数 / 负荷数、连通分量个数、参考母线、是否辐射状。
B. 诊断：逐条列出全部 diagnostics 记录（code、severity、target、suggested action）。

然后给结论：
- 如果 severity 里有 error 级别的问题，停下来，先告诉我要不要继续；
- 如果只有 warning，继续，但把 warning 记下来，后面解释结果时要带上。

为什么这一步重要：后面所有数值结论都建立在"算例可信"之上。算例数据自身不自洽是有先例的——IEEE 39 算例里机组 5 的电压设定值 1.0636 高于该母线上限 1.06。

步骤 6 — 基态潮流（建立基准）

目的：得到基准工况。后面所有的"越限""恶化"都是相对这一基准而言的。

把这份 IR 用 pandapower 的 load_network_from_json 导入，然后 run_power_flow。
报告以下内容，全部要给具体数值和元件编号：

1) 是否收敛；
2) 最低电压：数值 + 母线编号；最高电压：数值 + 母线编号；
3) 最重载线路：编号 + 负载率（%）；
4) 低于 0.95 pu 的母线有几个、分别是哪些；
5) 高于 1.05 pu 的母线有几个、分别是哪些；
6) 过载（>100%）的支路有几个。

最后做一个守恒校验：总发电 −（总负荷 + 网损）= ？给出残差数值。

验收判据：收敛 = True；守恒残差 ≈ 0（IEEE 39 实测为 0.0000 MW）；电压与负载率均有具体数值和元件编号——不接受"有若干越限"这种模糊结论。

步骤 7 — 跨引擎交叉校验（科研级必做）

目的：用第二个独立引擎复算，证明结果不依赖于某一个求解器的实现。

用同一份 IR（不要重新解析）调 pypsa 的 import_case_from_json 导入，再跑一次潮流。

然后做逐项对比：
- 母线电压 vm_pu：两边逐个母线比
- 支路首端有功：两边逐条支路比

关键：两侧的元件编号约定不同（pandapower 用 0-based 整数索引，
pypsa 沿用 IR 里的 1-based 标识）。请自动探测编号偏移，
搜索使最大残差最小的那个偏移量，不要按字面键直接对比——
按字面比会拿不同的物理元件做对比，得出假差异。

给出：最大偏差、平均偏差、以及是否落在 1e-06 pu 的判定阈值内。

验收判据：编号偏移探测结果明确（IEEE 39 实测为"pypsa 键 = pandapower 键 + 1"）；最大偏差落在机器精度量级（实测 电压 6.98e−11 pu / 有功 2.25e−07 MW）。若出现 0.0x pu 量级的"差异"，先怀疑编号错位，而不是物理差异。

步骤 8 — PTDF / LODF 灵敏度矩阵

目的：从"单点结果"升级到"结构性认识"——哪些线路对哪些注入最敏感。

用 surge 对这份算例计算 PTDF 和 LODF。

给我：
1) 两个矩阵的维度、非零元个数、稀疏度；
2) PTDF 里对几个关键母线注入最敏感的前几条支路；
3) LODF 里的 Inf / None 有多少个，并解释它们对应什么物理场景。

然后做物理自洽性核对（这是正确性的证据，不是可选步骤）：
- LODF 对角线是否 = -1.0？为什么？
- 同一对母线之间的并联支路，LODF 是否互为相反数？

验收判据：LODF 对角线 = −1.0（开断自身即全失）；同母线并联支路互为相反数；Inf/None 有物理解释（实测 506 个，对应开断后成孤岛、LODF 无定义）。

为什么自洽性核对重要：矩阵算错了也能给出"漂亮的数字"。只有物理约束能证伪它。

步骤 9 — N-1 故障扫描（找关键故障）

用 surge 的 run_n1_branch_contingency 做 N-1 扫描。

给我：
1) 总共扫描了多少个场景、多少个场景出现越限、越限条目总数；
2) 线路负载率 >100% 的故障有几个，按最大负载率降序排前 5，
   每个都要给出：断号、支路两端母线、最大负载率、对应 flow (MW)；
3) 母线电压 <0.95 pu 的故障有几个，最低电压是多少、在哪条支路；
4) 越限类型有哪些（ThermalOverload / VoltageHigh / Islanding 等）。

注意：Islanding 类型可能没有支路定位信息，遇到时请容错标注，不要报错退出。

验收判据：Top-N 故障有断号 + 数值，不接受"有几个故障越限"这种不可排序的结论。

实测参照（IEEE 39）：46 场景 / 23 越限 / 52 条越限；Top-1 branch_26（Line 21→22）161.84%、flow = 958.49 MW；低电压故障 2 个，最低 0.9361 pu。

步骤 10 — 越限 → 自动匹配缓解手册

目的：把"发现问题"推进到"知道下一步做什么"。这是 PowerSkills 的核心价值。

根据第 6 步和第 9 步的越限结果，对照 powerskills-tool 技能里的 Escalation triggers 表，
告诉我每个越限应该匹配哪个 powerskills-engineering 缓解手册，并说明匹配依据是哪条具体规则。

预期映射：
- 母线电压 < 0.95 或 > 1.05 pu  → voltage-violation-mitigation
- 支路负载率 > 100%              → thermal-overload-mitigation
- N-1 有 binding contingency      → contingency-mitigation
- 潮流不收敛                      → convergence-failure-mitigation

然后按手册给出的顺序列出建议措施（先试什么、再试什么），
并说明每一项措施需要改动哪些元件、预期改善哪个指标。
先只给方案，不要动手改算例。

验收判据：每个越限都映射到具体手册 + 具体规则；措施有先后顺序，而不是一堆并列选项。

步骤 11 — 实施缓解措施并复算（用结构化变更）

目的：验证措施是否真的有效，且变更过程可审计。

我要试验第 10 步里的第 N 项措施。

请用 PowerIO 的 typed edits 把这次改动写成结构化的变更列表
（例如 set_branch_in_service / set_switch_closed / set_transformer_tap_ratio /
set_generator_active_power 等），而不是直接改文件。

要求：
1) 先告诉我你打算下发的 edits 列表（op + 目标元件 + 新值），等我确认；
2) 确认后再执行导入，并报告返回的 edits 报告（按应用顺序列出被改动的元件）；
3) 在同一份新网络上重跑基态潮流 + N-1 扫描；
4) 给出"措施前 vs 措施后"对照表：最重载支路、最低电压、越限故障数。

注意：edits 是整批先校验、再按顺序应用的，请确认列表本身没有内部矛盾。

验收判据：返回的 edits 报告按应用顺序列出变更元件（可审计）；措施前后对照表有具体数值。若措施无效，如实报告无效，不要换个说法让它看起来有效。

步骤 12 — 运行优化（AC / DC OPF，含一致性闸门）

现在做最优潮流，AC 和 DC 各做一次。

路径说明：本机 pandapower server 没有 OPF 工具，PyPSA 的 optimize_network
对 IR 导入的算例返回 infeasible（成因未定位）。所以这里走 pandapower 的
runopp / rundcopp，这是 Python 侧调用、不是 MCP 工具调用。

为保证结论对 MCP 侧成立，请先做一致性闸门：
1) 从与 MCP 相同的那个算例文件本地重建网络；
2) 逐母线比对基态潮流电压与第 6 步的 MCP 结果；
3) 若最大偏差 > 1e-06 pu，中止，不要在来历不明的网络上做优化。

闸门通过后给我：
- AC OPF：目标函数值、网损、电压范围、线路最大负载率；
- DC OPF：目标函数值、线路最大负载率；
- 两者目标值之差及其占 AC 的比例，并解释这个差是否合理；
- 达到出力上限的机组清单（这是容量规划的直接依据）；
- 节点边际电价 lam_p 最高的前 5 个母线。

最后做守恒校验：AC 的"发电 −（负荷 + 网损）"、DC 的"发电 − 负荷"，给出残差。

验收判据：闸门偏差 ≤ 1e-06 pu（实测 0.000e+00 pu）；三项守恒残差 ≈ 0（实测 0.0000 MW）；AC 目标值 > DC 目标值且差值可解释。

实测参照（IEEE 39）：AC 目标 41,872.30 / 网损 44.18 MW / 最高电压 1.0600；DC 目标 41,263.94；差 608.36（+1.474%）；LMP 最高母线 38 = 14.1064。

十、能力边界：PowerMCP 不做什么

理解边界和理解能力同样重要：

PowerMCP 是PowerMCP 不是
工具接入层——让 LLM 能调用软件✗ 决策层——不会自己判断该做什么分析
暴露各软件的原始能力✗ 不替代专业的电力分析软件
提供标准化的调用协议✗ 不做工作流编排（那是 PowerWF 的事）
提供跨格式翻译（PowerIO）✗ 不做领域知识与处置经验（那是 PowerSkills 的事）
关键认知：PowerMCP 给了智能体"手"，但没有给"经验"。一个拥有全部工具的智能体，可能一上手就跑 N-2 分析，而实际上基态潮流都还没收敛——这是初级工程师的典型错误。
解决这个问题的是 PowerSkills（技能层，教智能体"先做什么、验证什么、何时升级"）和 PowerWF（编排层，把工具串成业务流程）。三者配合才构成完整的解决方案。
建议的搭配顺序：PowerMCP（能调用）→ PowerSkills（知道怎么做）→ PowerWF（成流程）。

场景 3：AC / DC OPF 对比与网损影响量化

实测产出可直接作为论文素材：AC 目标 41,872.30 vs DC 41,263.94，差 608.36（+1.474%）——这个差值正是 AC 计及 44.18 MW 网损的结果。同时可给出节点边际电价的空间分布（LMP 最高母线 38 = 14.1064，前 5 高集中在母线 38/8/0/7/6）。校验手段：三项守恒校验残差均为 0.0000 MW。

场景 4：跨求解器一致性与转换保真度

实测产出：同一份 PowerIO IR 经 pandapower 与 PyPSA 两个独立求解器，母线电压最大偏差 6.98e−11 pu、支路有功 2.25e−07 MW——保真度达到机器精度。使用陷阱：两侧编号约定不同（0-based vs 1-based），必须自动探测偏移，否则会拿不同物理元件对比（首次曾误报 0.068 pu）。

场景 5：潮流不收敛的成因诊断（真实研究素材）

素材：PyPSA 自带 case39.nc 潮流发散（p0 达 1e38 量级），而 optimize() 返回 ('ok','optimal')——LOPF 可解、PF 不可解。

已做的排除（6 项，均为实测）：pf() 本身可用（极简 2 节点网络正常）、网络连通（1 个连通分量）、无零阻抗支路、容量无缺失、LOPF 可解、手动设 control='Slack' 仍不收敛。

已定位但不充分：build_case39.py 中的 slack 机组从未设置 control="Slack"，网络无参考母线。

诚实边界：根因未完全定位——实测把该机组手动设为 Slack 后潮流仍发散，故它不是充分原因。这是一份"根因未定位"的真实素材，适合作"求解器鲁棒性与数据自洽性"的研究起点。不得把"根因未定位"写成"已定位"。

场景 7：LLM 调用电力工具链的失效模式研究

这是本项目实测中最有独特价值的研究点。已有 5 类可量化的失效模式（全部有实测记录）：

  1. 误报失败——Network.status 不存在 → hasattr 为假 → 打印"未收敛"，而求解器实际返回 ('ok','optimal')
  2. 静默忽略参数——不存在的 linearized 落进 **kwargs，跑的一直是 AC OPF，"DC 路径从未被真正测试"
  3. 工具名冲突——多 server 同名工具无法靠名字消歧
  4. 无降级路径——依赖缺失只有调用才失败，无 mock 降级
  5. 编号约定不一致——字面键对比拿错物理元件（首次误报 0.068 pu）

产出：可量化的失效模式分类 + 对应的缓解设计（一致性闸门、可用性预检、显式 server 指定、编号偏移探测）。

报告措辞纪律：母线 35 的 1.0636 恰等于该处机组电压设定值（PV 母线维持设定点），反映的是数据设定偏高而非求解异常——报告必须区分这两者。

答案：软件装了不等于能自动化。实测案例：PowerWorld 已安装，但为 Simulator GOS Education 23 版，不注册 SimAuto COM 类，即便装上 esa 也无法工作。探查输出为 [SKIP] PowerWorld COM/License unavailable，缺失项：SimAuto COM 注册, esa 包。

工程价值：避免在不可自动化的资产上浪费排期——这类"看起来能跑、实际跑不动"的坑，只有在真正调用时才会暴露。

场景 3：算例格式批量迁移

实测保真：跨引擎 Δ = 6.98e−11 pu，转换不引入可观测误差。

前提注意：Package / model-json / package_json / study_commit 为已退役格式，需重新 parse 原算例。已知限制：IR → PyPSA 导入不携带 q_min_pu/q_max_pu（无功能力限值）。

场景 4：检修方式编排与 N-1 校验

用 PowerIO 的 typed edits 把检修状态写成结构化变更（set_branch_in_service / set_switch_closed / set_transformer_tap_ratio 等 12 类 op）→ 导入求解器 → N-1 扫描。

工程价值：检修方案先验后执行，且变更可审计——返回的 edits 报告按应用顺序列出被改动的元件。

场景 6：越限问题的标准化缓解流程

实测映射：loading_percent > 100 → thermal-overload-mitigation；vm_pu < 0.95 → voltage-violation-mitigation。

工程价值：把"资深工程师的经验顺序"固化成可执行、可复用的 SOP，降低对个人经验的依赖。边界：手册给出的是措施顺序，具体效果仍需重算验证。
