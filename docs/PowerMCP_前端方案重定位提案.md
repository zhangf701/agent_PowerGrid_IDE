## 一、问题陈述

### 1.1 现有方案的实际定位（原文可复核）

| # | 出处 | 原文 |
|---|---|---|
| 1 | 《前端设计方案》文末 | 该前端「是 L2（可形式化验证的性质）的可视化层，也是 L3（校验套件）的呈现层 —— **而不是一个通用聊天前端**」 |
| 2 | 同文 §十二-3 | Web UI「建议定位为『**需要审计时的专用界面**』，而非日常入口」 |
| 3 | 同文 §十二-5 | 前端「只有在**作为 L3 校验套件的可视化层**时才与选题绑定」 |
| 4 | 《UI 设计规范》P1 | **契约状态是第一公民**；防的是「把前端做成又一个电力数据的图表工具」 |
| 5 | 《前端设计方案》§八 | 实施路线 P1/P2/P3 **每一阶段均标注「对应选题 L2 / L3」** |

**结论**：v3 是「MCP / agent-tool 接口标准化」这一论文选题的**垂直切片**。它与张老师要的**水平平台**（不限方向的通用研究工具）目标函数不同。

### 1.2 最硬的一条证据：PowerSkills 不在方案内

张老师点名要用「powermcp、powerskills」。实测词频：

| 文档 | `skill` 出现次数 |
|---|---:|
| `docs/PowerMCP_前端设计方案.md` | **1**（仅为契约 2 的比对对象 `SKILL.md` vs `list_tools`） |
| `docs/PowerMCP_UI设计规范.md` | **0** |

PowerSkills 的 **11 个软件工作流技能 + 10 个缓解手册**在方案中**没有任何视图、组件或入口**。
其中「**Escalation triggers**」（观测值 → 手册的数字驱动映射，审计为 10/10 引用完整、无悬空）是仓库中最扎实的设计，也是「研究方法」最直接的载体，却被完全遗漏。

## 二、目标定义

新定位：**通用电力系统研究工作台** —— 用 PowerMCP（9 引擎 / 117 工具）与 PowerSkills（21 技能）支撑任意方向的电力研究。

研究者在本工作台上的 **6 类活动**（依据 13 步全流程与 20 个场景归纳）：

| # | 活动 | 对应 13 步 | 对应场景 |
|---|---|---|---|
| A | 确认**能跑什么** | 1–3 环境就绪 | 前置条件检查清单 |
| B | 把算例变成**可信的统一表示** | 4–5 算例解析 | 科研 4 · 工程 3 |
| C | **提问并拿到结果** | 6–12 | 科研 1/2/3/5/6/7 · 工程 1/4/5/6/7 |
| D | **批量跑并沉淀数据** | — | 科研 8（39/118/300 × 负荷水平 × 故障集） |
| E | 知道**遇到问题该用什么方法** | 10–12 | 10 个缓解手册 + Escalation triggers |
| F | **留痕与产出** | 13 归档 | 全部 |

## 三、定位变更：契约从「第一公民」降为「可开关的校验层」

| 维度 | v3 | **v4（本提案）** |
|---|---|---|
| 第一公民 | 契约状态 | **研究流程** |
| 契约的角色 | 主界面的中心对象，占 5 视图中的 4 个 | **一等、可开关的校验覆盖层**（默认开，折叠为状态条，不占主区） |
| 能力取舍 | — | **能力一个不丢**：契约面板 / 跨引擎一致性 / 能力矩阵 / IR 检查器全部保留，只改变**层级与默认呈现** |
| 与论文关系 | 绑定的交付载体 | **解绑**（张老师裁决） |

> **为什么不是删掉**：契约层解决的是「结果可不可信」——这对**任何**研究方向都是刚需（科研 4/5/6 直接就是它的产物）。它的问题不是**存在**，而是**占据了主界面**。

## 四、新信息架构：5 主视图 + 1 可开关校验层

| # | 视图 | 职责 | 优先级 |
|---|---|---|---|
| ① | **环境就绪** | 能跑什么：server / 引擎 / 求解器 / 依赖 / 路径围笼 | **P1** |
| ② | **算例库** | 研究什么：算例载入 → PowerIO IR → 诊断 → 摘要，含版本与来源 | **P1** |
| ③ | **对话分析** ★ | 怎么研究：自然语言 + 工具轨迹 + 内联结果（**主界面**） | **P1** |
| ④ | **实验矩阵** | 批量与可复现：参数扫描 + 任务队列 + 结果表 + 导出 | **P2** |
| ⑤ | **技能手册** | 方法与经验：21 技能目录 + Escalation triggers 可视化与唤起 | **P1** |
| ⑥ | **校验层**（可开关） | 原契约面板 / 跨引擎一致性 / 能力矩阵 / IR 检查器 | **P2** |

### 4.1 ① 环境就绪

- **能力**：`powermcp doctor` 三类分诊（依赖 ok / missing / 需配置）· 求解器可用性（如 surge 的 `HIGHS_LIB_DIR` 未持久化）· 路径围笼（`POWERIO_MCP_ALLOWED_ROOTS`）· 引擎状态（心跳/熔断，依赖子项目 4）
- **依据**：13 步的 1–3；「落地前的前置条件检查清单」6 条
- **数据来源**：`GET /health`（已有，含 `audit`）· `GET /servers`（已有）· **新增** `GET /environment`（聚合 doctor + 求解器 + 围笼）
- **要点**：**「装得上 ≠ 跑得动」必须显式区分**（工程场景 2 的实测结论）

### 4.2 ② 算例库

- **能力**：算例登记（路径 / 格式 / 来源 / 标签）· 解析为 PowerIO IR · 诊断与摘要 · 版本与 hash
- **依据**：13 步的 4–5；科研 4（IR 往返保真 Δ = 6.98e−11 pu）· 工程 3（格式迁移）
- **数据来源**：**新增** `GET/POST /cases` · `POST /cases/{id}/parse` · `GET /cases/{id}/diagnostics`
- **★ 关键缺口**：现在**只有 session 粒度，没有 case / project 一级对象** —— 研究无法「组织」。这是本提案引入的**新一级实体**
- ⚠️ **硬约束**：算例库的存储**不得改动 `PowerMCP/`**（*zero source mutation*）。建议独立目录 `~/.powermcp_gateway/cases/`，不写进 `~/.powermcp/runs/`
- ⚠️ 已知限制：IR → PyPSA 导入**不携带** `q_min_pu` / `q_max_pu`（须在界面上标注）

### 4.3 ③ 对话分析（主界面）

- **能力**：自然语言交互 · 工具调用轨迹 · 内联结果（表 / 图 / 数值）· 会话恢复（server 组合 / provider / model / 算例）
- **数据来源**：`POST /sessions` · `GET /sessions/{sid}/events` · `POST /sessions/{sid}/tools/call`（**均已交付**）
- **变更点**：
  - 保留 `ToolCallRow`，但**契约标注默认折叠**（原为常驻）
  - 结果呈现以「研究结论」为中心，不再强制「契约状态先于图表渲染」（v3 P1 的落地条款）
- **依据**：13 步的 6–12

### 4.4 ④ 实验矩阵

- **能力**：参数网格定义（算例 × 因子 × **步骤序列**）× 串行执行 × 逐格进度 × 结果表 × 失败逐格可见 × 导出；V2 增加提案校验、资源预览、commit 冻结、Observation 与确定性分析
- **★ 定位（2026-09-28 核实补记）**：**内核通用能力，不与任何具体研究方向绑定**。抽象只有「算例 × 因子（标签维度）× 步骤序列（显式声明的工具调用）」。跨引擎一致性（`cross-engine-consistency`）与 N-1 排序（`n1-ranking`）都是**可插拔模块**，**不是**实验矩阵的前提；无任何模块时实验矩阵依然可用。指标由内核**通用提取**（不发明派生量），领域列定义由模块声明。
- **V2 研究层（✅ 2026-09-28 已交付 MVP）**：`ExperimentProposal → validate/preview → explicit commit → immutable Experiment → Observation Store → deterministic analysis`；提案不会自动 commit，commit 时固定算例身份、展开格子和 `cell_id`。
- **依据**：科研 8（批量算例扫描与数据集构建，🚧 需先构造数据集）+ Agentic Research Experiment V2 规格
- **数据来源**：V1 `POST /experiments` · `GET /experiments` · `GET /experiments/{id}` · **`POST /experiments/{id}/run`** · `GET /experiments/{id}/results` · `GET /experiments/{id}/export?format=csv|md`；V2 `POST/GET /experiment-proposals*`、`GET /experiments/{id}/summary|design|observations|analysis`、`GET /experiments/{id}/cells/{cell_id}`、`POST /experiments/{id}/cancel`（V2 MVP 已交付）
- ✅ **2026-09-27 视图已交付**：`views/ExperimentsView.tsx` + `components/ExperimentGrid.tsx`（导航「实验矩阵」，
  深链 `#experiments/<eid>`）。UI 规范 §4.7.5 三条约束逐条落地：失败逐格可见 / 结果绑 `cache_key`
  （`never_run` + `orphaned` 显式标注）/ 串行优先（无并发控件）。
- ★ **一格 = 一条显式声明的步骤序列**（2026-09-27 契约扩展）：引擎是**有状态**的
  （`surge.run_n1_branch_contingency` 只接 `monitored_branches`，跑的是进程内已加载的网络），
  故一次 N-1 分析 = `load_network` → `run_n1_branch_contingency` 两步，且**全部步骤须同一 server**。
  执行时**一格一个会话**（会话是引擎状态的边界）。
- ⚠️ **依赖前置**：**串行版不需要** §11.2 并发隔离（方案 §4.4 已裁决「先串行跑通，再评估并发」）；
  §11.2 的「命名空间加 session 维度 + 租约锁 + 工作流级事务」只在**引入并发前**必须完成。
  ⚠️ 多步实验**要求会话池**（`POWERMCP_SESSION_POOL=1`），否则显式 503（不静默降级）。
- **★ 导出必须按用户级规则**：PDF 走「单文件 HTML + Chrome headless 渲染 + PyMuPDF 叠页码」，**禁用 pandoc**。
  网关侧只出 CSV / Markdown 文本（渲染属界面层）。

### 4.5 ⑤ 技能手册

- **能力**：21 个技能目录（11 工作流 + 10 手册）· 每个技能的范围 / 先暴露工具 / 升级路径 · **Escalation triggers 可视化**（观测值 → 手册）· 手动唤起
- **依据**：`能力与场景总结` §3.1–3.4；13 步的 10–12
- **数据来源**：**新增** `GET /skills`（索引 `PowerSkills/**/SKILL.md` 的 name / description / 工具清单 / escalation 表）
- **★ 这是本提案最重要的新增视图** —— 它是「研究方法」的显式化，也是 v3 完全遗漏的部分
- **设计要点**：**双轨** —— ① 目录可浏览、可点选唤起；② LLM 在 escalation 触发时自动建议（把现有隐式行为**变得可见**）
- ⚠️ **诚实边界**：技能健康度审计实测 🔴 阻断 3 / 🟠 事实不符 4 / 🟡 引用错误 1。**界面必须显示技能健康状态**，不得让用户以为 21 个技能都是可靠的（如 pypsa 的 `Network.status` 会**误报失败**，比崩溃更隐蔽）

### 4.6 ⑥ 校验层（可开关）

- **能力**：完全保留 v3 的契约面板 / 跨引擎一致性视图 / 能力矩阵 / IR 检查器
- **变更**：作为**覆盖层**呈现（默认开启但折叠为顶部状态条；可一键展开或整体关闭）
- **依据**：v3 §4.2 / §4.3 / §4.4 / §4.5
- **数据来源**：`GET /contracts/t0`（已有）· `GET /sessions/{sid}/events` 的 `contract_violation` / `contract_unknown`（已有）
- ⚠️ **开工须知（沿用交接文档）**：契约 3 在事件流上有**两个 kind**，payload 同为 `ContractFinding` 同形；Zod 入站边界须**按 `kind` 分派、按 `state` 汇入双轨汇总**
